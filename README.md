# 项目需求与设计 Skill

## 技能入口与维护位置

技能入口为当前技能包根目录的 [SKILL.md](SKILL.md)，本文中的文件链接均相对于当前包。维护源码时使用实际源码目录，检查已安装技能时使用实际安装目录；二者均与被分析项目的业务材料位置分开。

保留的 `source-manifest.json` 是历史文件哈希快照，不代表当前文件清单或验证结果，不用于安装完整性校验。

面向研发管理者，从新项目想法、已有实现或需求变化出发，按需探索需求、设计模型、验证架构，并形成可交付研发和测试的用户故事、验收条件与任务计划。

四个主阶段可以独立进入、往返修订。业务系统、开发工具、SDK、数据处理或跨系统项目按实际需要选择分析维度，保留建模方法和技术方案的适配器机制，不绑定某套元模型。

| 主阶段 | 主要结果 |
|---|---|
| [需求探索与澄清](references/stages/discovery.md) | 可独立理解的现状或需求概要，关联目标、场景、能力与规则，明确范围、成功标准、约束和未知 |
| [领域与数据模型探索设计](references/stages/modeling.md) | 本轮模型全视图、现状／目标差异、优化重构及演进方案 |
| [技术架构探索与验证](references/stages/architecture.md) | 技术取舍、架构与关键链路、最小 demo 或已有验证证据及限制 |
| [需求细化与交付推进](references/stages/delivery.md) | 用户故事、可验证验收条件、研发测试任务、交付批次及实际结果 |

全局先有概要，近期范围逐步深入。完整分析默认先形成领域与逻辑模型，以业务边界、规则和数据关系驱动架构，再结合技术选择与验证完善物理模型。模型与架构可以往返，决定需求能否成立的技术风险可提前专项验证；交付反馈可以修订需求和设计，不要求全项目设计完毕再开始交付。“可交付研发测试”和“已完成交付”分别判断，后者需要实现与验证证据。

持续分析时，各阶段按用途整合当前有效内容：需求关联目标与能力，模型解释语义与规则，架构解释取舍与协作，交付关联用户结果、验收与执行安排。来源、验证样例、实际证据和历史通过明确引用关联，正文不能只是对话摘录、孤立的映射表或任务目录。日常编辑、实质需求／设计变更、进展更新与基线发布分别维护，不以对话轮次增加修订版本。具体规则见 [工作与交接契约](references/shared/working-contract.md#内容归属与当前正文)。

## 职责划分

| 内容 | 职责 |
|---|---|
| [SKILL.md](SKILL.md) | 描述技能用途、输入产出，以及什么时候使用什么能力 |
| `references/` | 具体分析方法、方案适配和必要的工作约定 |
| 本地 `项目上下文.md` 或远端“项目上下文”章节 | 需求管理系统、文档、代码及分析产物的位置与来源约定 |
| 被分析项目的文档 | 业务事实、需求、设计、有效决策与交接状态 |

本技能不附带 AGENTS.md 接入模板，也不要求用户修改项目 AGENTS.md。项目已有指令按宿主规则正常生效，不由本技能替换。

## 在项目中引入

GitHub 仓库：[FarmerLi/project-design-skill](https://github.com/FarmerLi/project-design-skill)。技能名称为 `project-design`，安装目录也使用这个名称。

默认将下面的提示词交给 Agent，自动安装或更新最新正式 Release。版本由 Tag 标识，使用 GitHub 自动提供的完整源码包；安装不要求逐文件比对哈希，也无需 Git 子模块或克隆仓库。执行细节见 [安装与更新指引](安装与更新.md)。

安装或更新时：

```text
请读取 https://github.com/FarmerLi/project-design-skill 仓库中的《安装与更新.md》，将 project-design 安装到当前项目；已有安装则更新到最新正式版。请按指引直接完成版本检查、必要的整包下载、备份替换和安装校验，并报告版本与安装位置。
```

默认安装到当前项目的 `.agents/skills/project-design/`；个人全局安装或固定 Tag 时，在请求中明确说明。尚无正式 Release 时，需要先发布，或明确要求安装默认分支的开发版。引入本技能无需修改项目的 `AGENTS.md`。

## 使用

源码目录存在 `SKILL.md` 不代表技能已经安装或被当前会话发现。先区分文件校验通过、宿主已发现、显式调用成功和自然语言选择正确这几种状态；未发现时按安装指引处理，或使用下方实际文件路径读取方式。手动读取入口只能验证执行流程，不能证明自动触发生效。

在需要分析的项目中打开 Codex；技能已被发现时，可以在会话中使用：

```text
$project-design 帮我分析当前项目。本轮先澄清目标、用户和范围，已有资料位于……
```

也可以明确指定实际入口，例如项目内安装后：

> 请读取当前项目的 `.agents/skills/project-design/SKILL.md`，帮我分析这个项目。本轮只澄清目标：……

安装在其他位置时，将入口替换为实际路径，例如 `/实际位置/project-design/SKILL.md`。

提供已有项目或资料时，也说明实际位置。首次持续分析可要求助手按已知资料建立项目配置，具体内容见下节。有本地项目目录时，分析草稿默认保存到该项目的 `docs/project-analysis/`；纯远端项目可直接使用已授权页面，不要求建立本地仓库或副本。不要把业务资料写入技能包。

## 项目上下文文件

有本地项目目录时，用根目录的 `项目上下文.md` 记录必要的稳定信息；纯远端项目可使用已授权项目页面的“项目上下文”章节或已有配置页：

- 需求管理系统名称、项目链接、空间／项目 ID 和需求定位方式；
- 业务文档、设计文档与代码的位置；
- 分析产物目录，以及概览、决策和交接文件的实际位置；
- 需求状态、详细规则和当前实现分别以哪些来源为依据。

首次持续分析时，助手根据已知资料从 [模板](assets/项目上下文模板.md) 在适用且已授权的位置建立配置；也可以手动复制并填写。未知项保留待核实，无需一次填完全部信息；已有等价配置可以沿用。

配置记录资源位置、任务与文档维护规则，不重复保存需求正文、工作进展或业务决策。使用规则见 [项目上下文配置](references/shared/project-context.md)。

所有新建分析产物使用中文文件名，例如 `项目概览.md`、`决策记录.md`、`交接记录.md`、`01-需求探索与澄清.md`、`02-领域与数据模型探索设计.md`、`03-技术架构探索与验证.md`、`04-需求细化与交付推进.md` 和 `用户故事-001.md`。独立图源、图片及表格等导出文件也使用中文名称，保留实际格式的扩展名。完整约定见 [工作与交接契约](references/shared/working-contract.md#工作目录与最小材料)。

## 能力

```text
SKILL.md
references/
  entry/context.md              既有项目现状、材料缺口和继续分析
  stages/discovery.md           第一阶段：需求探索与澄清
  stages/modeling.md            第二阶段：领域与数据模型探索设计
  stages/architecture.md        第三阶段：技术架构探索与验证
  stages/delivery.md            第四阶段：需求细化与交付推进
  stages/feasibility.md         第一阶段子方法：价值与可行性
  stages/outline.md             第一阶段子方法：需求概要与范围
  stages/detail.md              第四阶段子方法：用户故事与验收细化
  stages/collaboration.md       跨阶段的协作影响分析
  changes/impact.md             任意阶段的变更分析
  selection/                    建模方法选择、技术选型
  adapters/                     应用选定的建模方法与技术方案
  shared/project-context.md     项目资源配置的读取和维护
  shared/working-contract.md    结论、决策版本与交接约定
  shared/analysis-spec.md       信息、操作、规则、协作、口径与契约的最小规格
  shared/readiness.md           按交接用途检查充分性及证据
  shared/design-input.md        设计输入索引、双向追溯与变更传播
  examples/analysis-slices.md   跨系统、统计与无状态 SDK 的分析示例
assets/项目上下文模板.md 项目上下文模板
agents/openai.yaml               技能展示与调用信息
```

这些是可组合的能力，不是每次必须走完的顺序：

- 新项目只有目标，可以从需求探索中的目标与价值讨论开始。
- 已有概要，可以直接细化近期用户故事和验收条件。
- 技术路径有关键未知，可以直接进入架构验证；明确要求 demo 时完成授权范围内的实现、运行与证据记录。
- 只需理解模型或重构时，可以直接梳理现状、目标及演进路径。
- 既有项目新增能力，先了解有关现状，再分析增量。
- 修改已约定的需求，先定位变化及影响，再局部修订。
- 选型和应用方案分开；建模方法和技术方案分别选择。

适配器包括轻量模块设计、本体设计和技术方案适配。本体适配器使用用户实际选定的外部规范，本包不再包含特定元模型映射；正式输出特定格式时需要读取选定规范。详见 [适配器目录](references/adapters/catalog.md)。

## 通用分析如何做到可检验

- [通用分析规格](references/shared/analysis-spec.md) 明确相关维度要定义到什么程度，并允许说明不适用，避免只输出功能名称。
- [协作与影响链](references/stages/collaboration.md) 独立检查跨边界影响、失败后果、重复和反向变化，技术实现由适配器决定。
- [就绪检查](references/shared/readiness.md) 以证据和实际交接范围判断充分性，区分业务确认、设计就绪和运行验证。
- [设计输入与追溯](references/shared/design-input.md) 固定输入版本和权威定义，双向连接需求、设计、验收及变更影响。

例如“导入后自动可检索”需要说明保存成功与索引成功的区别、失败如何恢复、删除与晚到结果如何处理；一个无状态函数则可以只交付调用契约与验收案例。详见 [分析切片](references/examples/analysis-slices.md)。

## 继续分析

持续分析通过项目文档保存有效结论，而不依赖聊天历史完整保留。恢复时可以说：

> 请使用项目需求与设计技能。项目位于……，先读 `项目上下文.md`，再依据当前概览和交接继续下一项工作。

纯远端项目提供实际页面或交接链接，先读取其中的“项目上下文”及有效材料即可，不要求提供本地项目路径。

[现状与恢复方法](references/entry/context.md)说明读取顺序，[工作约定](references/shared/working-contract.md)说明状态和交接内容。普通一次性咨询不要求建立全套文档。

## 旧版接入

旧的多技能入口改用根目录 SKILL.md。此前如果手动合并过本包的 AGENTS 片段，可移除该片段；保留项目自身规则。更新技能包不会自动修改其他项目的配置。

已有项目需求、决策和交接文档仍可使用，不必重新生成。旧的价值评估与方案概要归入第一阶段，旧的需求细化与交付规划归入第四阶段；原文件名与编号继续沿用，新模型及架构阶段按需要补充。第二、第三阶段调换后，既有模型与架构材料仍按内容及有效版本识别，不强制改名或重做。

## 验证与来源

维护时检查技能格式、UI 元数据，以及包内 Markdown 的本地文件引用和内部锚点；安装时按 [安装与更新指引](安装与更新.md#安装校验) 检查解压内容、安装记录与实际位置。验证报告应说明实际版本、执行范围和未执行项；格式、引用和场景推演不代表真实访谈效果、独立模型行为或第三方平台兼容性已验证。

修改触发、路由或完成标准后，使用 [行为验证用例](tests/行为验证.md) 检查对应场景及相邻反例。用例供技能维护使用，不作为业务分析时的运行依赖；记录实际执行方式与证据，未执行的行为测试不标为通过。

本包独立编写，方法参考包括 [AI 需求探索与确认提示词 V9.0](https://github.com/sharptoolbox/ontology-driven-dev/blob/main/references/AI需求探索与确认提示词V9.0.md)。当前 [工作契约](references/shared/working-contract.md#对话与范围控制) 保留先草拟再澄清、区分依据与建议、分批处理关键问题及维护有效结论的方法，适用于四个阶段；上游资料不作为本包的运行依赖。

未引入专属模型、单体同步限制、固定 UI、产物数量和逐阶段强制确认；没有依据时不强行推荐业务政策，有业务价值的交互要求予以保留。
