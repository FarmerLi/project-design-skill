# 第一阶段技能修改预案

日期：2026-10-22。状态：已实施技能修改并完成本次静态与行为验证；实际结果见[修改验证记录](../tests/第一阶段修改验证记录.md)。以下保留本次批准执行的修改范围与验收设计。

本预案针对 `project-design` 第一阶段“需求探索与澄清”的方法和产物质量。依据为 Product2Ontology 的三份指定文档、关联验证报告，以及技能源码中的阶段方法、工作契约和维护规则。产品材料仅作为问题证据，不作为技能的默认业务模型。

## 一、修改目标与判断

第一阶段应将零散想法、对话和材料整理成一份能独立阅读的产品需求概要。读者无需了解对话经过、比较历史版本或拼接专项设计，就能回答：为谁解决什么问题，期望什么结果，产品有哪些能力，这些能力如何协作，当前做什么和不做什么，如何判断目标达成。

当前问题主要是需求综合、内容归属和持续维护机制不足。修改需要同时做到：

1. 将输入提炼为产品结论，保留来源与确认状态，避免用对话转述代替需求分析。
2. 按产品逻辑维护当前有效正文，让历史、候选、设计和验证材料各有归属。
3. 分清产品本身、被接入系统和验证样例，避免将样例的领域对象固化为平台能力。
4. 按实际语义变化维护修订，区分日常编辑、需求变更和基线发布。
5. 以完整认知、定义一致和场景闭环检查质量，不能只检查章节或条目是否齐全。

预案编写阶段仅形成修改方案。后续已按用户指令实施技能源码修改并开展隔离验证；Product2Ontology 的已安装技能及业务文档保持原样，下面的正式文档迁移仍作为后续整理路径。

## 三、需求提炼方法的修改

### 1. 先明确分析对象与术语归属

第一阶段先识别“正在设计什么”和“输入材料描述什么”，再定义角色、对象和能力。

以本次平台项目为例：

| 层面 | 应表达的内容 | 不能直接推导的内容 |
|---|---|---|
| 平台产品 | 接入材料、辅助理解、编辑本体、图谱预览、能力映射、Agent／问数使用等产品结果 | 不因某个样例存在订单，就固定内置订单管理能力 |
| 被接入系统 | 由接入材料识别的领域概念、角色、业务规则与能力，其表达应支持不同系统 | 不预设所有系统都有商户、档口或相同管理员模型 |
| 验证样例 | 某系统的具体对象、字段、接口、账号类别、测试数据和观测结果 | 不把样例字段或枚举升级为平台规范定义 |

同样区分平台使用者、目标系统的业务主体和实际执行身份。它们可以有关联，但不能仅因都叫“管理员”就合并。

这是按实际对象选择分析边界的方法，不要求所有项目增加三层模型。若设计对象本来就是商户业务系统，商户当然可以是正式业务概念。

### 2. 将原始输入综合为需求

在现有工作方法中补入以下整理动作；它们是分析依赖，不是固定访谈轮次：

1. **归类输入。** 区分问题、目标、能力诉求、明确约束、设计建议、现状证据和验证样例；一段输入可以拆成多类。
2. **提取产品含义。** 说明谁在什么情境下要完成什么任务，产品应提供什么结果和边界；补出的价值解释若无依据，保持为分析假设。
3. **合并与消歧。** 合并重复表述，区分同名不同义，识别新增信息是在补充、纠正还是替代既有定义；解决不了的冲突登记为待决。
4. **建立整体关系。** 将目标、场景、能力、关键规则和范围关联起来，推演从输入到结果的完整路径，识别缺失能力和无目标依据的功能。
5. **组织当前正文。** 按主题修订有效定义，同步处理旧措辞、范围和待决项；历史与证据只保留必要引用。
6. **检查可理解性。** 从陌生读者视角阅读，核对是否仍需依赖对话、历史补丁或验证样例才能理解产品。

单项能力需求可采用“角色／情境 → 任务或问题 → 产品行为与可观察结果 → 关键边界”的表达。ID、来源、确认状态和验证状态按实际追溯需要附加，不要求每段都套长表格，也不在第一阶段补齐开发级字段与所有 AC。

### 3. 保留来源，但改变来源的呈现位置

- 主体说明产品应具备的行为、结果、约束及当前有效的待决边界。
- 需求条目用简短来源引用关联原始输入、材料或有效决策，确认状态可见且不与测试状态混用。
- 对话原文只有在解释歧义或取舍时才摘录到来源／决策记录，不默认保存完整聊天。
- 明确要求在等价整理后继续有效，无须重新确认；整理中新增的行为或取舍仍为建议。
- “用户要求”不是禁用词。问题在于转述替代了分析，或让来源叙述支配正文结构。

### 4. 代表性改写方向

以下用于说明预案，不是对原需求的正式替换或新增确认。

| 当前表达类型 | 产品需求应表达的内容 | 另行维护的内容 |
|---|---|---|
| “本轮用户明确支持不同版本 OpenAPI、Word、PDF、Markdown” | 支持已确定类别的接口材料接入；使用单种受支持材料可开始建模，并能识别不支持或缺失的内容 | 原始要求及状态在来源索引；版本／特性与实现批次单列；本次 Swagger 样例结果在验证报告 |
| “文档参数、返回值和注释不能预设可信” | 对材料中的不一致与不确定含义保留可追溯依据，使建模人员能核对、修订，并辨别相关能力是否具备使用条件 | 冲突对象结构、依赖算法和处理组件属于设计；具体字段冲突属于样例证据 |
| “Agent 通过本体执行，需要映射关系” | 应用基于本体语义使用业务能力，并能通过映射关联目标实现；保留上层不得绕过本体的明确执行约束 | 执行器分层、映射 schema、适配器和版本组织属于设计；具体接口绑定属于验证方案 |
| “档口属于商户、查询档口销售统计” | 若要进入平台需求，应提炼为领域关系表达、语义能力到目标实现的映射等有目标依据的通用能力 | 档口、商户、shopId 和销售字段保留在该样例的领域分析与映射中 |

明确的技术或执行约束可以属于需求，不能机械地将所有涉及“本体、映射、权限”的内容移走。区分依据是内容承担的责任，以及它是明确约束、待选方案还是样例细节。

## 四、需求主体与支撑材料的组织

建议第一阶段以一份需求概要作为阅读主线；复杂内容按主题拆分时，主文档仍要提供足够的概括和清晰导航，不能只剩链接。

| 正文主题 | 读者应获得的认识 |
|---|---|
| 产品定位、问题与目标 | 产品解决什么问题，价值如何观察，已有项目的相关现状是什么 |
| 目标用户与核心场景 | 谁在何种情境中完成什么任务，主要结果和边界是什么 |
| 产品边界与关键概念 | 产品、外部系统和样例的关系；理解后续内容所需的术语 |
| 核心流程与能力全景 | 从触发到结果如何衔接，各项能力分别承担什么责任 |
| 能力需求与关键规则 | 产品应提供的行为、用户可见结果和不可违反的约束；关联目标与场景 |
| 范围、优先级与取舍 | 产品目标范围、近期交付范围、延后及排除内容；与验证范围分别说明 |
| 成功标准与质量要求 | 如何判断有用、正确和可接受；无数值依据时保留测量方式 |
| 待决问题与依赖 | 尚缺什么、影响哪部分、何时需要解决；已解决问题退出当前待决清单 |
| 支撑材料与修订摘要 | 设计、来源、验证及变更记录的导航；简短说明实质变化 |

这是一种推荐的信息顺序，不是所有请求必须填满的模板。局部需求只维护相关主题；只有现状探索时保留现状用途。单项定义有一个维护位置，摘要通过引用关联，避免主文档、专题和概览分别维护不同版本。

内容归属按责任决定：

| 内容 | 维护位置与关系 |
|---|---|
| 产品目标、场景、能力、行为、范围和关键约束 | 当前需求主体；候选和条件性内容明确标识 |
| 来源依据、关键取舍、确认状态及被替代理由 | 来源／决策记录，按需求 ID 或位置关联；必要摘要可留正文 |
| 组件责任、处理机制、映射结构与技术方案 | 架构／模型／专项设计，引用需求定义 |
| 样例对象、具体字段、接口映射、样例权限及测试账号类别 | 验证方案或样例分析；通用设计引用其作为例子，不依赖它才能成立 |
| 环境、输入快照、执行过程、实际结果和适用限制 | 验证报告及材料；不能承担需求定义责任 |
| 变化范围、替代关系和下游处理情况 | 修订摘要或独立变更记录；正文仍表达当前有效结果 |

需求中的成功判据、待验证问题可以保留。应移出的主要是具体样例及执行细节，不能把所有“验证”相关内容从需求中删除。

## 五、修订与变更机制

采用“当前正文持续整合，历史按变化范围维护”的方式。文档保存不等于发布一个新需求基线，实际版本机制优先复用项目现有约定。

| 变化类型 | 正文处理 | 修订与版本处理 |
|---|---|---|
| 措辞、结构、引用、重复内容整理 | 原位修订，不改变需求含义和状态 | 可更新编辑时间或利用平台历史；不要求新增正式需求版本 |
| 补充事实或解决未知，产品行为不变 | 更新事实、关闭对应问题，检查关联表述 | 有需要时记录澄清摘要；若改变设计成立前提，仍需标明影响 |
| 新增或改变能力、规则、范围、验收含义 | 变化已确定则整合进有效正文；尚在讨论则保留为候选 | 按同一变更主题归并记录；需要稳定交接时形成可追溯修订，不按对话次数机械升版 |
| 正式评审、阶段交接或约定的基线发布 | 保存当时的完整有效内容与状态 | 按既有机制固定版本；不新增无依据的审批流程 |
| 样例、验证环境或实际结果更新 | 更新相应验证材料 | 维护验证记录；只有影响产品结论时才触发需求变更 |

修订记录至少能回答：为什么变、变了哪些定义／章节、替代什么、影响哪些下游、哪些已处理及哪些需复核。可用简表：

`变更 ID／日期 → 变化及理由 → 影响的需求与章节 → 来源与决定状态 → 下游处理情况 → 历史位置`

局部变化在文末保持简短摘要；跨多个文档或需要持续跟踪时，复用现有 `changes/` 约定建立独立记录。完整旧正文保存在平台历史、版本控制或归档中，不与当前规范并列。没有版本控制的项目在重构前保存可恢复快照，但不要求每轮复制整套文档。

每次有效更新都检查被替代结论、旧待决项、重复定义、范围说明和引用。保留稳定 ID；合并或废弃时记录承接关系。未复核的下游仍保留其实际输入版本并标为需复核，不能通过统一替换版本号伪装同步完成。

## 八、行为验证与验收标准

验证关注实际产物和更新行为，不以删除某些词、固定标题或文件数量作为通过条件。

| 用例 | 输入与操作 | 可观察的通过条件 |
|---|---|---|
| D-01 对话提炼 | 分多轮提出重叠功能、体验和约束要求，要求持续维护概要 | 形成按产品逻辑组织的完整正文；重复要求合并；来源可追溯；未按轮次堆积补充章节 |
| D-02 当前定义替代 | 初期未有样例，后续提供真实材料并解决部分待决 | 正文采用当前事实；旧待决退出清单；历史可查；无需读旧版本才能判断有效范围 |
| D-03 样例隔离 | 平台材料中提供带有特定行业对象和权限字段的接口样例 | 产品能力能独立成立；样例术语归属清楚；未成为平台固定内置模型；真实来源仍可定位 |
| D-04 范围区分 | 产品要求多格式，当前只有一种格式样例，且仅做了局部检查 | 产品目标、实现批次、验证计划和实际覆盖分别表达；不删除既定范围或夸大支持程度 |
| D-05 约束保真 | 明确要求应用通过语义层执行，同时提供具体底层接口 | 需求保留明确执行约束；实现分层归设计；具体绑定归样例；不以抽象为由删除约束 |
| D-06 修订节奏 | 连续进行措辞整理、事实补充、同主题能力澄清，再改变一项业务规则 | 普通编辑不强制发布新基线；实质变化可追溯；同主题可归并；下游影响与复核状态真实 |
| D-07 完整认知 | 只向读者提供当前需求主体及必要术语，不提供聊天与样例报告 | 能准确说明问题、用户、目标、能力协作、范围和成功标准；正文内部无未解释的重复或冲突 |
| D-08 局部请求反例 | 仅澄清一个功能；另例明确要求保存访谈原话 | 局部请求不扩成全套文档；原话按请求保留并标明用途，与产品规范区分；不机械禁用来源叙述 |

D-07 还要核对：每项当前范围能力有目标或用户任务依据，每个核心场景有能力承接；未知能够定位到具体影响。不能只读一段泛泛的产品介绍就判完整认知通过。

实施时在隔离会话／项目中执行相关用例，记录请求、输入、技能版本、实际产物和结果。格式与链接检查、人工规则推演、真实行为验证分别报告；本次实际执行结果与限制见开头的修改验证记录。

## 九、建议实施顺序与交付

1. 修改第一阶段方法及必要公共规则，确保提炼、归属、更新、修订和就绪判断使用同一套约定。
2. 补充简短示例和行为用例，检查入口可达、规则冲突及包内引用；不以静态检查代替行为验证。
3. 在隔离目录用多轮输入及本次材料验证，评估完整性、约束保真和样例边界，修复实际观察到的问题。
4. 交付技能差异、行为验证结果与限制，以及既有产物试整理结果；项目安装副本更新和正式文档修复按后续实际任务范围执行。

最终验收重点是：用户能从一份当前有效的需求主体形成完整产品认知，新增对话能够改善这份认知，历史和样例仍可追溯但不再支配产品文档结构。
