# 贯穿全流程的变更分析

适用于目标、范围、业务规则、质量要求、建模方法或技术方案的变化，不必等到交付阶段。读取 [工作契约](../shared/working-contract.md) 中的状态和版本约定。

## 确定变化的性质

区分“想讨论是否要改”和“已明确要求修改”。探索候选时保留当前基线，不将提议覆盖为已生效需求；用户明确决定后直接记录，不要求再重复确认。

先定位：

- 为什么改，预期改善什么；
- 之前的有效结论是什么，有何来源；
- 新结论与旧结论具体差在哪里；
- 是业务变化、实现缺陷、文档纠正，还是技术方案替换。

不清楚旧基线时先做有边界的 [现状分析](../entry/context.md)。不要假设原先不存在规则。

## 按影响扩展读取范围

从直接变更项出发，沿明确引用检查：

- 用户场景、业务规则、信息和状态变化；
- 权限、外部接口、兼容性及其他相关质量要求；
- 模型、技术设计和必要的验证；
- 验收案例、交付批次与依赖。

只扩大到合理相关范围。引用不完整时做针对性搜索，并说明影响清单的证据边界；没查到引用不等于没有影响。

以 [设计输入与追溯](../shared/design-input.md) 中的映射定位下游。规则改变时同时检查它在操作、流程分支、查询口径和验收中的使用；状态或数据处置改变时，重新检查 [协作与影响链](../stages/collaboration.md) 的正向与反向后果。文档中引用旧版本的项要保留原版本并标为需复核，不能只统一替换版本号。

## 处理结论

输出变更前／后的差异、受影响项、理由、拟处理方式与尚未解决的问题。较大取舍给出少量选项及代价；没有资源依据不编造工作量或时间承诺。

变更已确定时：
1. 更新有效业务结论或技术选择，保留被替代项的 ID 和理由。
2. 标记受影响但未复核的场景、设计与验收为“需复核”；不受影响项保持有效。
3. 按问题回到目标、价值、概要或细化方法，不重跑整个流程。
4. 切换适配器时按 [适配器契约](../adapters/catalog.md) 处理旧设计，不继承旧方法专属假设。
5. 更新概览和交接，列明已经改了什么、还没改什么。

局部调整直接记在关联产物的修订记录。涉及多处且需要追踪时建立 `changes/CHG-xxx.md`；内容包含请求来源、决策状态、影响项、处理结果和验证状态。

完成标准是变化及影响已明确、必要修订已完成或有明确交接。需求文档更新不代表代码已修复或回归测试通过。

交接时按 [就绪检查](../shared/readiness.md) 明确“影响已分析”和“受影响项已复核”分别覆盖哪些范围；存在尚未处理项时不能宣称整个变更已闭环。
