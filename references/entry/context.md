# 入口识别、现状与恢复

用于新项目入口不明、既有项目需要了解现状，或恢复材料不足的情况。已明确任务且输入足够时可跳过。

持续分析的项目已确定时，按 [项目交付配置](../shared/project-context.md) 定位本地 `项目上下文.md` 或远端配置章节，以其中的任务系统、正式文档目标和交付规则定位材料。没有配置时在适用且已授权的位置建立；没有本地项目目录时可以从指定远端页面或交接链接开始，不先要求建立仓库。临时咨询不要求建文件。

## 选择最短有效路径

| 项目基础与请求 | 先做什么 | 后续入口 |
|---|---|---|
| 新项目，只有目标 | 澄清用户问题、价值与成功标准 | [需求探索与澄清](../stages/discovery.md) |
| 已有需求或概要，尚未实现 | 判断本轮输入缺口和有效版本 | 按请求进入模型、架构、原型与交互设计或交付推进 |
| 已有产品新增能力 | 找出相关现状与新增目标的差距 | 第一阶段增量探索，或第四／五阶段原型验证及故事细化 |
| 只探索技术实现或验证想法 | 定位关键链路、约束和待验证命题 | [技术架构探索与验证](../stages/architecture.md) |
| 梳理模型或设计重构 | 区分已有结构、业务语义和目标差异 | [领域与数据模型探索设计](../stages/modeling.md) |
| 已有页面或流程，需要改善任务、状态、反馈或设计规范，或需要用原型验证需求 | 核对现状、用户目标、规则、技术边界及项目上下文中的原型工具 | [原型与交互设计](../stages/prototype-interaction.md) |
| 已有故事，跟进研发测试 | 核对有效需求、关联任务与实际执行证据 | [需求细化与交付推进](../stages/delivery.md) |
| 改变已约定行为或范围 | 明确原结论与提议差异 | 变更分析 |
| 继续上次工作 | 读取最新交接并核对输入版本 | 交接指定的下一项任务 |
| 实现和需求不一致 | 区分缺陷、过时文档与需求变化 | 先澄清预期；纯修复按用户任务处理 |

新项目也可能修改需求；既有项目也可能只做价值讨论。分类用于确定读取与分析范围，不作为互斥模式。

## 有边界地了解现状

先读用户指定材料、项目概览和直接相关文档。只有具体问题需要时，读取相应代码或运行结果；遵循仓库指令和探索预算，不自动全仓扫描。

把三个层次分开：

- **实际行为**：从实现、运行、用户观察等获得，并说明证据和覆盖范围。
- **已约定行为**：有效需求、设计或既有决策，说明版本和适用范围。
- **目标行为**：本次希望达到的结果，区分已决定与候选。

文档与代码冲突时保留差异，不能认定代码天然正确，也不能认定旧文档仍有效。用户没有材料时，可基于描述开展条件性分析，并标记证据缺口，不等待不必要的完整资料。

记录与本轮有关的用户、流程、功能、依赖和约束。技术环境只是现状事实，不等于用户选择沿用所有设计；是否保留某约束，按本次目标判断。

现状结论足以支持本轮决策即停止探索。小任务放在相关阶段的“现状”段；需要持续引用时建立 `现状基线.md` 并在项目概览登记。

## 恢复

先通过项目配置定位正式概览及独立辅助区中的交接、有效决策；读取材料顺序与状态含义见 [工作契约](../shared/working-contract.md)。发现交接过期，以更新后的有效决策与文档为依据，识别变更后再继续；保留未解决冲突，不偷偷选择一个版本。

恢复出的工作目标、已做动作与下一步安排留在交接中；需要改变正文的有效结论才归并到相应主题，不把恢复过程写进组件设计。材料整理遵循 [文档结构规范](../shared/document-structure.md)。

方法规则因历史压缩而不清楚时，重读相应 reference。文件不可访问时列出确切缺口，只暂停依赖它的部分。
