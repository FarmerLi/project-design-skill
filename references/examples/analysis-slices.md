# 通用分析切片示例

仅在需要校准分析深度、处理联动／口径问题时读取。以下均为虚构示例，只演示方法，不是实际项目事实、默认需求或通用组织政策。

## 示例一：文件导入与外部检索

示例用户已明确：上传的文件保存后建立检索索引；索引失败保留文件、允许重试；删除后不能再搜索到文件。用户只要求需求分析，尚未选择技术。

### 信息与范围

- `REQ-01`：保存文件并使其可搜索；`REQ-02`：索引失败可恢复；`REQ-03`：删除后不能再搜索到文件，包括对应标题、摘要等检索条目。
- `OBJ-01` 文件是源数据，索引是可重建的派生数据，不把二者当成同一条记录。索引成功不替代文件保存成功。
- 文件的有效／已删除状态与索引的待处理／成功／失败状态分开。它们只是候选表示；需求要求的是可观察结果，最终字段由设计决定。
- `OPEN-01`：哪些人可上传、查看、删除哪些文件？阻塞正式权限设计。
- `OPEN-02`：从文件保存到可搜索允许多长时间？阻塞完整性能验收，但不阻塞定义功能结果。
- `OPEN-03`：外部检索是否支持删除及完成状态查询？这是需验证的外部能力，不向用户索取其无法知道的内部实现。

### 操作与影响

| 操作 | 本操作结果 | 后续影响 | 失败／反向语义 |
|---|---|---|---|
| ACT-01 保存文件 | 文件已保存，有稳定标识 | LINK-01 请求建立索引 | 索引失败不能抹去文件已保存的事实 |
| ACT-02 建立／重试索引 | 派生索引建立或失败结果可见 | 更新检索可用结果 | 同一文件版本重复处理不产生重复检索结果；该去重方案为建议，需记录选择依据 |
| ACT-03 删除文件 | 文件已删除，不再出现在面向用户的检索结果中 | LINK-02 清理对应索引 | 清理失败或旧索引请求晚到时，也不能使已删除文件重新出现在检索结果中 |

`RULE-01` 是“当前文件仍有效且待索引内容为有效版本”的判断，不执行删除或写索引。`LINK-01` 在调用前检查它；如果外部返回与删除并发，还要在结果生效及检索返回时保证 REQ-03，不能只依赖调用前的一次检查。

影响矩阵需要同时覆盖保存、重试和删除，而不只画“上传 → 索引成功”的主链。删除是反向变化；索引服务故障时“删除后不能再搜索到”的要求仍需承载。

### 设计输入和缺口

已确认的业务语义是“索引失败保留源文件、派生结果可重试、删除后不能再搜索到”。队列、同步请求、索引 tombstone 或检索返回前过滤均属于后续候选设计。

若外部系统只能最终完成清理，设计可评估在检索返回前过滤已删除文件，再清理派生数据，并验证所有相关检索入口都能满足 REQ-03。仅阻断点击访问、仍显示标题或摘要不满足原要求；不能擅自降级为“最终消失”，也不将标题可见性重新当作尚未决定的业务政策。确实无法承载时记录能力冲突，提出替代方案或范围调整建议；变更获决定前保留原需求。直接访问文件的处置是另一项待明确的要求，不能用它替代检索不可见。

| 验收 | 给定 → 动作 → 预期结果 | 状态 |
|---|---|---|
| AC-01 | 文件保存成功 → 索引失败 → 文件仍存在，可看到失败并重试 | 已定义；未执行 |
| AC-02 | 文件已删除 → 旧索引请求随后返回成功，再执行相关检索 → 结果中不出现该文件的标题、摘要或其他对应条目 | 已定义；未执行 |
| AC-03 | 同版本被重复提交处理 → 完成两次 → 无重复检索结果 | 候选规则对应案例，尚不能算已确认验收 |
| AC-04 | 无权限调用者请求删除 → 请求被拒绝，文件无变化 | 权限矩阵明确后补充具体角色及数据范围 |
| AC-05 | 文件原先可搜索 → 删除完成后再次检索 → 结果中不出现该文件的对应条目 | 已定义；未执行 |
| AC-06 | 文件已删除且索引清理失败 → 再次检索 → 结果中仍不出现该文件的对应条目 | 已定义；未执行 |

追溯示例：`REQ-02 → LINK-01／ACT-02 → 拟定技术设计的恢复章节 → AC-01`；`REQ-03 → ACT-03／LINK-02 → 拟定技术设计的检索过滤与清理章节 → AC-02／AC-05／AC-06`。此时能交付功能语义草稿和设计候选；权限、检索不可见的技术承载能力及时间目标仍有缺口，不能宣称整个功能可直接开发。

### 用户故事与研发测试交接

`US-01` 草稿：作为上传文件的用户，在索引失败时，我希望保留文件并重试索引，以便恢复检索而无需重新上传。关联 `REQ-02`、`ACT-02` 和 `AC-01`；用户可操作的数据范围仍由 `OPEN-01` 阻塞，不默认“上传者拥有全部权限”。

拟定研发任务为索引失败反馈与重试实现，输入是上述故事、有效权限规则及相关设计；拟定测试任务围绕 `AC-01` 准备已保存文件和可复现的索引失败条件，检查失败时文件保留、反馈可见和重试结果。两项任务均引用故事和验收条件；未创建远端任务，不编造 key。

权限、重试后的可检索时限及相关设计未齐备时，此故事仍是条件性草稿。即使用替身 demo 证明了“索引异常不会删除文件”，也不能证明真实索引服务恢复正常或整个故事已经交付。验收条件定义、demo 结果和最终测试结果分别记录。

## 示例二：两组明细汇总

示例要求：按项目显示累计预算和实际支出，两类明细各自独立，只有有效记录计入。这里重点是信息和口径，可以没有审批、状态机图或界面模型。

一项目有预算明细 40、60 和支出明细 10、20、30。正确结果是预算 100、支出 60。若先把两组明细直接连接再汇总，会得到预算 300、支出 120。

应把结果粒度“每项目一行”、有效记录筛选规则、金额单位、时间归属、空项目显示规则定义清楚；采用分别汇总后关联或其他保持粒度的方案。上述数值样例成为可执行的验收输入，不能只写“统计金额准确”。金额币种不明时登记待决项，不默认跨币种相加。

这是查询正确性检查，不要求先选对象模型、生成 SQL 或新增报表平台。

## 示例三：无状态 SDK 参数校验

示例请求：SDK 新增解析函数，将用户给定的 ISO 日期文本转换为日期值；非法输入返回明确错误，保持旧接口不变。

可以直接细化调用契约：支持的输入格式、时区处理、空值和非法输入、输出类型、错误形式、兼容要求与样例。时区缺失的语义未知时提出一个具体问题，已有明确要求不再确认。

在没有持久化、跨系统调用和角色要求的证据时，对象生命周期、审批和跨对象联动均不适用。交付一份函数契约与正常／边界／错误验收案例即可；不为了“严谨”扩成完整业务系统规格。若请求研发测试交接，可在同一文档中以 SDK 调用方为角色补充故事价值与范围，关联实现和兼容性测试任务，无须另外创建故事文件或数据库模型。
