# 需求文档维护

用于保存、更新或发布本轮需求与设计结论。先按 [交付配置](../shared/project-context.md) 读取目标项目的本地配置或远端“项目上下文”章节，确定正式维护位置、已有文档、允许更新范围和执行约定。无本地项目目录时，直接从用户指定的远端目标及已有授权开始，按需在授权范围保存最小配置与恢复入口，不以创建本地文件作为写回前提。

## 按目标维护

| 目标 | 定位与维护 |
|---|---|
| 本地 | 按实际目录和文件名更新；各阶段默认文件名仅用于未约定位置的情况 |
| Notion | 按父页面或数据库、已有页面 ID／链接定位，先读取相关内容和结构，再使用可用连接器／技能写入 |
| Confluence | 按站点、空间及父页面／已有页面定位，先读取当前内容和版本，再使用可用工具更新 |

具体 API 和连接方式以当前环境与平台能力为准，不预设安装了连接器。只加载本次目标所需的工具或平台技能，不加载所有平台。

## 更新流程

1. **定位并读取。** 查找已有文档，读取当前内容、相关定义及可用版本信息；没有关联时按配置建立。先确认本轮允许的维护范围，保留其他人的无关内容；发现并发变化先核对差异，不用整页覆盖规避合并。
2. **提炼并归并。** 将输入整理成有效结论、候选和未决项，按 [内容归属](../shared/working-contract.md#内容归属与当前正文)确定需求、设计、样例、证据和历史的落点。比对已有定义，判断新增、补充、纠正或替代，不直接复制聊天或按轮次追加专题。
3. **整合当前正文。** 更新对应主题，合并重复内容；检查相邻段落及相关引用中的旧范围、失效结论和已解决问题。正文保留当前有效结果及必要条件，旧定义移交历史；复杂内容拆分后，主文档仍有完整概貌和必要导航。
4. **维护变化与影响。** 按 [版本约定](../shared/working-contract.md#版本完成标准与变更)区分编辑、语义变更、基线及验证记录。实质变化归并记录原因、范围、替代关系和下游处理；未复核项标明需复核并保留实际输入版本，不随意统一升版。
5. **执行并核实。** 按本轮要求或已有持续保存约定写入，不重复新建同名文档或索取已有授权。只有地址而无写回约定时先准备可审阅内容，缺失授权或目标按实际情况处理。检查实际保存结果；失败或不明时先核实再重试。
6. **回读并交接。** 从保存后的当前正文检查整体可读、定义一致、术语归属、范围与证据边界，以及链接和状态是否正确。记录实际路径／ID／URL、维护范围和可定位修订或更新时间；保存成功只证明已写入，不代替内容就绪或测试通过。

临时咨询不执行保存步骤。局部更新只展开相关内容及合理影响范围；大幅重组且没有可恢复历史时先保存快照，不以本流程自动扩展为全项目重写。

## 与项目材料、任务关联

正式需求在远端时，本地如保留内容应标为草稿、缓存或交接索引，不能再默认为另一份正式版本。阶段的 `01-需求探索与澄清.md`、场景文件等可对应远端页面／章节，按配置记录映射，不强制同名本地副本。

概览、决策、交接可沿用项目已配置的实际位置。将新文档链接登记到当前产物索引，任务引用通过实际链接和需求 ID 关联。维护任务内容时另读 [任务落地](task-tracking.md)。

若平台不可访问，明确尚未写回，保留可交付草稿或在对话中给出内容；没有本地草稿位置时不擅自建立长期镜像。不得把已生成正文描述成远端已保存。
