# 任务落地

在用户要求将拆解结果建入任务系统、更新关联任务，或已有明确持续同步约定时使用。先按 [交付配置](../shared/project-context.md) 读取目标项目的本地配置或远端配置，定位实例、项目、父项、任务类型和字段约定。没有本地项目目录时可从指定页面或父项开始，按授权在远端保存配置与任务映射，不要求先建立本地仓库。

## 准备与执行

1. 从已有需求与场景形成可独立交接的故事，写清本次目标、范围、详细行为和验收条件，再拆分研发和测试任务。每个任务说明具体范围、输入／契约、输出、依赖、完成判据及证据；测试任务关联 AC、数据／环境、验证步骤和预期。共享技术任务只建一份并关联所支撑的故事或质量目标。拆分方法见 [需求细化与交付推进](../stages/delivery.md)。
2. 检查配置与目标系统实际能力，确认项目、父项、允许的层级和必填字段；不要把示例中的 Epic／Story／Sub-task 当成所有 Jira 项目的固定配置。
3. 使用可用连接器、CLI 或平台技能。没有对应工具时完成任务草稿和关联计划，明确尚未创建；不编造任务 key。
4. 先查询已有需求／场景到任务的映射及关联任务，避免重复创建。只有名称相似时不能直接认定为同一项；结合项目、来源 ID 和父项确认。
5. 在既有授权范围内创建或更新，保留任务原有的无关内容。负责人、版本、状态等不明且属于必填项时才询问，不随意填人或猜测状态。
6. 读取返回结果或回查，记录已成功创建／更新的任务 key、URL 与对应需求／场景／故事 ID 及 AC。部分成功时保留成功映射，只处理缺失项。

请求超时或返回不明确时先查询结果，再决定重试，避免一次拆分生成多套任务。

## 关联与继续开发

任务正文引用需求文档及稳定需求／场景／故事 ID，研发和测试任务保留各自验收或验证条件。目标系统没有 Story 类型时用现有任务及关联字段表达，不擅自修改平台层级配置。若文档暂未发布，明确标记来源草稿和待补链接，不伪造远端地址。

任务系统是故事与任务的正式维护位置时，故事正文或系统内关联条目必须承载完整目标、行为、验收和研发测试安排；仅创建标题、状态及外部文档链接不算交接完成。必要设计和共享规则仍引用各自正式来源。回查时检查正文、关联任务及依赖是否完整，不只确认 key 存在。本地总览仅索引实际任务及批次，不并行维护另一份正式故事／任务正文。

工具不可用、未获写入授权或部分写入失败时，保留可评审草稿和真实成功映射，明确哪些故事／任务尚未落地；不把草稿标为远端维护完成，也不擅自切换正式维护位置。

将映射保存到配置指定的关联记录；未指定时放到交付计划的任务映射段，不为每个任务重复建立全套文档。需求文档需要反向关联时，按 [文档维护](document-maintenance.md) 在已授权范围补充相关任务链接。

后续开发读取关联任务与有效需求，不因进入新阶段再次创建任务。状态变更依据真实实现和验证证据；定义了验收标准、创建测试任务或关闭任务都不等于实现与测试通过。读取实际版本、测试执行结果和遗留问题，再在授权范围内同步状态。开发本身由用户当前任务或其他能力承担。

配置目标与任务创建、状态变更、发送评论的授权分别判断。已有明确授权不重复索取，但不额外发送评论或消息。
