# 任务落地

用户要求创建／更新任务，或已有持续同步约定时使用。从已指定项目／父项、已有任务或配置定位目标，复用实际字段和关联；没有本地目录可直接使用远端任务，不先建配置。

## 准备与执行

1. 先核对 [本期业务范围](../stages/issue-delivery.md#开始前先决议本期需求边界)，只为范围内的交付结果拆分执行 Issue／等价任务。已有明确范围和写入授权直接沿用；写入授权本身不补足缺失的业务决定。先按 [Issue规范入口与目标表达](../stages/issue-delivery.md#issue-规范入口与目标表达)读取项目规范，并按父项或执行项角色及[交接内容](../stages/issue-delivery.md#研发与测试交接包)写清目标需求、范围、AC、必要约束和验证方式；简单需求可直接用一个任务，不强制独立故事或分设 DEV／TEST。共享技术任务只维护一份并关联所支撑的结果。
2. 检查配置与目标系统实际能力，确认项目、父项、允许的层级和必填字段；不强制 GitHub、Jira 或任何类型／层级；项目已有其他任务来源时直接适配。
3. 对复杂目标按 [父子 Issue 规则](../stages/issue-delivery.md#父-issue-与-sub-issue) 建立父项与子项，核实平台是否支持原生 sub-issue；支持时优先使用并回查真实关系，不支持时记录等价关联与限制。维护父整体验收到子范围／AC 的覆盖关系，不在父项复制子状态。使用可用连接器、CLI 或平台技能。没有对应工具时完成任务草稿和关联计划，明确尚未创建；不编造任务 key。
4. 先查询已有需求／场景到任务的映射及关联任务，避免重复创建。只有名称相似时不能直接认定为同一项；结合项目、来源 ID 和父项确认。
5. 在既有授权范围内创建或更新，保留任务原有的无关内容。负责人、版本、状态等不明且属于必填项时才询问，不随意填人或猜测状态。
6. 读取返回结果或回查，记录已成功创建／更新的任务 key、URL 与对应需求／场景／故事 ID 及 AC。部分成功时保留成功映射，只处理缺失项。

请求超时或返回不明确时先查询结果，再决定重试，避免一次拆分生成多套任务。

## 关联与继续开发

任务正文引用必要需求和设计，沿用已有 ID，关系简单时直接用链接。实现与测试可放同一任务，独立执行需要时再拆分；没有 Story 类型时使用已有类型，不修改平台配置。

任务系统是执行来源时，任务正文维护本次目标、范围、验收、必要实施／测试安排及实际状态，通过具体引用关联长期定义。仅有标题与整篇链接不足以交接；沿用已有 ID，固定输入需要时才补修订。总览和映射只维护必要关系，不复制任务详情和状态。

工具不可用、未获写入授权或部分失败时，在当前回复、已有任务或记录保留可评审内容与真实成功映射，说明未落地项；无需专建辅助草稿或交接文件，不擅自切换正式来源。

迁移前核对既有任务的实际含义，复用同一执行项；保留旧 US／AC／DEV／TEST 到 Issue／规范章节的映射，说明拆分或合并的承接关系，不丢失历史 AC、测试版本与结果，不把旧通过状态赋给新定义。未落地时保留原来源，核实成功后同步索引与唯一来源约定。

关联关系优先保留在任务和原需求／设计引用中；项目已有映射则更新实际变化，关系很多才用独立覆盖表。必要反向链接按 [文档维护](document-maintenance.md) 在授权范围补充，不复制一套执行台账。

已成功落地的内容核实后，按 [材料清理规则](../shared/document-structure.md#更新与清理) 处理失去用途的中间任务草稿，保留真实映射及失败证据；不在正式故事目录混放工具日志和交接。

后续开发读取关联任务与有效需求，不因进入新阶段再次创建任务。状态变更依据真实实现和验证证据；定义了验收标准、创建测试任务或关闭任务都不等于实现与测试通过。读取实际版本、测试执行结果和遗留问题，再在授权范围内同步状态。开发本身由用户当前任务或其他能力承担。

父项关闭前还须核对整体 AC、必要子项完成及跨子项验证证据，不能只数已关闭子项；延期或取消子项先处理父目标及覆盖变化。

配置目标与任务创建、状态变更、发送评论的授权分别判断。已有明确授权不重复索取，但不额外发送评论或消息。
