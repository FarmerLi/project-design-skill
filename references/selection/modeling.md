# 建模方法选择

## 用途与边界

仅在用户需要比较方法，或方法选择实质影响当前设计时读取。目标是确定：当前问题需要什么表达能力、采用什么方法及深度、为什么值得付出维护成本，以及如何验证选择成立。单纯需求访谈不要求先选方法。

用户已明确选择时，跳过开放式比较，检查其适用范围和必要输入后按 [适配器目录](../adapters/catalog.md) 使用。只有出现具体表达缺口、约束变化或用户要求重新评估时，才提出局部补充或更换建议；不因个人偏好重开选型。

区分四类决定，避免把名称或工具当成完整方案：

| 决定层次 | 要回答的问题 | 示例与边界 |
|---|---|---|
| 建模方法 | 按什么原则组织概念、责任、行为和规则？ | 轻量模块、领域建模、本体驱动；可按范围组合 |
| 模型视图 | 当前需要看清哪些信息？ | 概念关系、生命周期、逻辑数据、接口契约；按问题选取 |
| 表达形式 | 用什么让目标读者准确理解或处理？ | 术语表、关系表、状态转换表、图、结构化文件；画图不等于规则完整 |
| 规范与工具 | 哪份定义约束格式，谁负责检查？ | 用户规范及版本、schema、校验器、生成器；工具存在不等于适合业务 |

方法选择不能代替业务规则澄清，也不替用户决定语言、数据库和部署方式。与技术方案有兼容要求时联合评估，但分别记录决定。

## 最低输入与问题定位

复用对话、有效需求和已有设计，不要求先完成所有前序阶段。至少明确本轮范围、模型用途，以及足以说明主要困难的场景或现有材料。输入不足时先交付条件性比较，只追问会改变推荐的缺口。

按相关性提取以下证据，不把每一项变成必填问卷：

- **用途与读者**：用于业务沟通、边界设计、研发交接、数据治理，还是机器校验与生成？谁读取、谁维护，什么结果算有用？
- **核心困难**：术语是否有歧义，关系是否复杂，状态与规则是否相互制约，跨模块／跨系统责任是否清晰？引用具体场景，不只写“业务复杂”。
- **范围与演进**：新建、局部增量还是重构；哪些既有模型仍有效，哪些定义会变化，是否涉及历史数据或调用方兼容？
- **实际约束**：团队已有实践、交付时间、维护责任、可用规范及工具、必须兼容的设计和交付格式。
- **自动化要求**：只需可读文档，还是必须解析、校验或生成？具体校验什么、生成什么、生成物如何维护？“以后可能自动化”先作为假设。

分别标明事实、已定约束、偏好和待验证假设。例如“团队熟悉关系图”影响维护成本，但不能证明关系图足以表达撤销规则；“已有数据库表”也不能证明领域边界正确。

## 先判断建模投入是否必要

优先采用能消除当前歧义、支撑后续工作的最小表达。复杂度依据规则和协作的耦合程度判断，不按页面数、表数量或项目名称推定。

| 已观察到的信号 | 优先补足的表达能力 | 不必因此自动引入 |
|---|---|---|
| 局部功能，输入输出和规则可直接列清 | 场景、契约、规则及验收示例 | 独立模型文件或完整对象体系 |
| 职责交叉、数据维护方不清、协作易遗漏 | 模块责任、依赖和数据归属 | 微服务或分布式架构 |
| 同一词在不同业务范围含义不同，规则归属混乱 | 统一术语、上下文边界及规则归属 | 全项目统一为一个概念模型 |
| 状态多、允许操作随状态变化、存在撤销或补偿 | 状态转换、前置条件、失败与反向路径 | 工作流引擎或事件存储 |
| 标识、关系、历史口径或统计粒度频繁出错 | 概念／逻辑数据模型及约束 | 特定数据库和提前完成的物理表结构 |
| 跨系统概念映射困难，需要机器理解或一致性校验 | 显式语义、映射及可校验约束 | 特定本体元规范、知识图谱或 AI 能力 |
| 普通场景推演不足以检查关键不变量 | 对关键局部做精确规格与可执行检查 | 对整个系统形式化建模 |

“不增加显式模型”是有效结论，但仍需保留必要的规则与契约。说明现有表达为什么够用，以及出现什么问题时需要补模型；不能用“简单项目”省略已存在的复杂规则。

## 构造有意义的候选

围绕主要困难比较少量实际可行方案。既有项目先把沿用或局部补充现有方法作为基线；新项目保留轻量方案作为成本参照。没有实质差异时不为凑数量制造候选。

下表是候选方向，部分可以组合，不是要求逐一评估的菜单，也不表示本包为每一种方向内置了适配器。

| 候选方向 | 值得考虑的情形 | 最小有用表达 | 主要代价或不足 |
|---|---|---|---|
| 不增加显式模型 | 局部规则清楚，场景和契约已足以交接 | 场景、规则、输入输出及验收案例 | 复杂关系和变化可能散落在文字中，需要明确补模信号 |
| 轻量模块设计 | 主要问题是责任、协作与数据归属 | 模块职责、协作关系、关键数据责任 | 深层语义和复杂生命周期需要补充表达，机器校验能力取决于格式 |
| 领域建模／DDD 的适用部分 | 核心概念、上下文及规则归属复杂，团队需要一致业务语言 | 术语、边界、对象关系与关键不变量；按需细化聚合等结构 | 需要持续业务参与和边界维护；不能由 DDD 名称推导出微服务或全套战术模式 |
| 数据／关系建模为主 | 主要风险在数据标识、关系、历史和查询口径 | 概念或逻辑数据模型、约束及数据来源 | 静态结构不足以完整表达行为、权限与失败语义 |
| 状态／流程建模为主 | 核心困难在操作顺序、生命周期和跨角色协作 | 状态转换或流程、条件、责任及异常路径 | 单独使用难以覆盖数据语义；状态与流程需避免重复定义同一规则 |
| 本体驱动 | 需要显式语义和跨系统映射，且可获得并维护所需规范 | 概念关系、语义约束、映射及所选规范要求的模型 | 规范适配、工具和版本维护成本较高；不能默认覆盖所有行为或质量要求 |
| 关键局部的形式化／可执行规格 | 某些不变量或状态组合需要比人工推演更精确的检查 | 有边界的状态、约束、检查命题及结果 | 需要相应工具与能力；结论受抽象、假设和探索范围限制 |
| 用户指定或既有方法 | 组织已有规范、有效资产或明确交付约束 | 复用现有表达，补本轮缺口 | 核实实际版本、可用能力及与当前范围的匹配，不仅依赖方法名称 |

组合时说明主方法、补充视图及各自职责。例如用轻量模块设计说明责任，用状态表描述订单生命周期，用逻辑数据模型说明标识和关系。每条规则保留一处权威定义，其他视图引用或映射，不分别复制维护。

若不同模块采用不同方法，明确边界、共享术语及交接契约。只有跨边界语义确实需要统一时才建立共同规范，不要求全项目使用同一种深度或格式。

## 比较与最小验证

### 先检查适配底线，再比较收益

对候选按本轮需要检查：

1. 关键场景、关系和规则是否可表达；缺口能否由明确的配套规格承接。
2. 是否兼容用户已定约束、有效业务定义和需要交付的格式。
3. 需要的规范、维护能力和工具是否实际可获得；要求机器处理时，解析、校验、生成链路是否有依据。
4. 对既有项目，是否有可解释的映射与演进路径，是否会破坏仍需保留的语义或契约。

明确无法满足必要条件的候选记录不适用理由，不用低成本或综合评分抵消。证据不足的候选可以保留评估，但相关推荐应带条件；对已定方法发现问题时说明影响和补充选项，不静默替换。

再比较能够影响决定的维度：语义与规则覆盖、读者理解成本、变更与追溯成本、团队维护负担、自动化收益，以及引入／迁移成本。每项判断关联证据或假设，避免只填“高／中／低”。只有权重有明确依据且评分尺度可解释时才量化，不用无依据的总分制造精确结论。

推荐应回答：解决了哪个主要困难；比最简单可行方案多付出的成本为何值得；哪些局限仍存在；什么新证据会改变结论。若两个方案的差异尚不能判断，指出关键未知和最低成本的区分方式。

### 用同一业务切片验证表达能力

当主要差异无法仅靠已有材料判断时，用同一组有效业务事实做最小试建模。选能暴露争议的场景，而非只选最顺利的创建流程；按相关性覆盖状态变化、关系变化、跨边界协作、异常或反向操作，不设固定数量。

试建模应明确：

- **待判断命题**：例如某种表达能否同时说明取消条件、数据归属及对下游的影响，而不丢失既有规则。
- **最小产物**：只建能判断命题的片段，不展开全部领域设计或生产实现。
- **通过与失败信号**：关键规则有明确落点，读者能判断允许／禁止行为，各视图无矛盾；出现无法表达、必须修改业务规则或无人可维护的部分时记录缺口。
- **变化检验**：用已有变更请求或明确标注的假设变化，检查需修改哪些定义、映射和下游产物；避免只评价首次绘制是否方便。
- **验证证据与限制**：区分人工语义核对、实际读者反馈、解析／schema 校验、生成结果检查和真实运行验证。未发生的评审或工具执行不能写成已通过。

机器处理是关键目标时，核对规范版本与工具输入输出，并在已有授权范围内执行必要的最小检查。格式可解析不证明语义正确，schema 校验通过不证明业务完整，生成成功不证明生成物行为正确。工具或规范不可用时交付映射草案和缺口，不能承诺已具备自动化能力。

选型请求通常止于材料比较或最小表达验证。若需要安装工具、调用外部服务或实现原型，按实际授权和任务范围执行；未执行的验证计划不作为选择已验证的证据。

## 决策记录与完成标准

交付结论应让后续设计者可以直接使用；简单情况用短段落，复杂比较才用独立文档。按相关性保留：

| 记录项 | 内容 |
|---|---|
| 范围与用途 | 本轮对象、读者、设计深度、采用的输入及有效来源 |
| 方法与组合 | 主方法、必要补充视图、适用边界及规则的权威定义位置 |
| 比较与理由 | 主要候选、保留或排除依据、相对轻量基线的收益与代价 |
| 规范与能力 | 实际采用的规范及版本、已确认可用的适配器／工具、能力缺口；不依赖专门规范时说明即可 |
| 状态与依据 | 候选／评估中／已选择／已替换；用户决定或委托选择的依据 |
| 验证与未决项 | 实际完成的检查、证据、限制、待补信息及其影响范围 |
| 演进与复评 | 必要的迁移或兼容安排，以及会触发复评的具体变化 |

选择状态与验证状态分别记录。“已选择”不等于模型已经设计完成或工具已经验证。用户决定后记录“已选择”；用户明确委托在约束内选择时可直接选择并解释依据，不追加形式确认。仅提出推荐时仍保持候选。

在本轮范围内满足以下条件，可认为选型分析完成：

- 需要解决的问题与所需表达能力清楚，投入深度有依据。
- 已有方法得到复用评估，比较对象之间存在实际差异；不适用项和关键未知有解释。
- 推荐、条件性建议或暂缓决定均有证据支持，适用范围与限制明确。
- 关键表达缺口有处理方向，待验证事项有可执行的下一步，不以选型完成掩盖设计阻塞。
- 后续能识别应采用的规范、必要输入及可推进范围，选择和验证状态未混淆。

有关键未知时可以完成条件性比较并结束本轮，但不能宣称方法适配已证实。需要保存时按项目配置维护决策，本地默认使用 `决策记录.md`；复杂比较可放在 `design/建模方法选择.md`，临时咨询不强制建文件。

## 设计交接与重新选择

仅请求比较或选择时，交付结论后结束。本轮还要求应用所选方法时，进入 [领域与数据模型探索设计](../stages/modeling.md)，并只加载 [适配器目录](../adapters/catalog.md) 中对应说明。当前内置建模适配器为轻量模块和本体设计；其他方向使用用户提供或已可用的规范／外部 skill，没有专用能力时说明可完成的通用分析和需要补充的实现，不虚构适配器，也不自动安装工具。

交接范围、有效业务输入、已选方法及组合边界、规范版本、代表性映射和未决项。技术方案尚未确定时可继续概念与逻辑层设计，物理承载和工具相关结论保持条件。模型要求与技术能力冲突时，列出调整方法、技术方案或需求范围的选项，不能静默删减需求。

复评由具体变化触发，例如新增跨系统语义映射、生命周期无法可靠表达、必须机器生成而现有格式不支持，或维护成本已使模型持续失真。先判断局部补充能否解决，再比较整体更换的收益及迁移成本。

更换时保留中立需求和仍有效的业务约束，记录旧方法的适用范围与替代关系，按 [变更影响分析](../changes/impact.md) 核对模型、规则引用、验收与下游实现。旧验证仅在条件仍成立时可复用，不能随新方法自动继承为通过。

## 典型判断示例

以下用于说明判断方式，不替项目预设方法或政策。

| 情境 | 合理的结论与边界 |
|---|---|
| 无持久化的格式转换工具，输入、输出和错误明确 | 可不增加显式模型，用契约和边界案例交接；不为了完整性建立领域实体或生命周期 |
| 订单业务规则复杂，但团队只需要清晰交接 | 比较领域语义、状态和数据的必要表达；复杂度本身不足以推荐本体或代码生成 |
| 多个系统对“客户”定义不同，需要统一统计 | 先确定概念差异、统计口径和映射责任；比较术语映射与更正式的语义模型，不能仅凭跨系统就认定需要本体 |
| 用户已选本体并要求生成模型，但未提供元规范 | 复用方法选择，明确规范缺口；可推进概念与映射草案，不猜测 schema 或声称生成物合规 |
| 已有关系模型总体有效，新增撤销规则难以表达 | 优先补状态与规则视图，核对与现有数据的对应；不因一个行为缺口重建全项目模型 |
| 用户委托选型，机器校验为必要条件，但校验器不可用 | 可继续比较语义覆盖与可用规范，明确自动化未验证；不能把人工检查当作机器能力已满足的证据 |
