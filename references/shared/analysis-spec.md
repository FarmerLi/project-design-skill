# 通用分析规格

在概要、需求细化或交接时，按相关维度使用。这里规定“需要说清什么”，不规定必须选择何种模型，也不要求每个项目生成全部表格。

## 选择分析维度

从本轮用户结果出发，判断下列维度属于“需展开”“已足够”或“不适用”。省略会改变范围、正确性、成本或验收结论的维度时，必须说明理由；尚不知道不能写成不适用。小任务可用一段话记录，完整项目分析在概览中维护覆盖表。

| 维度 | 应展开的信号 | 最小定义 |
|---|---|---|
| 目标与范围 | 所有任务 | 问题、使用者、期望变化、成功判据、范围内外 |
| 信息与关系 | 共享数据、输入输出、业务概念易歧义 | 含义、来源、维护责任、约束、关系及生命周期 |
| 操作与规则 | 有用户任务、系统处理或决策 | 输入、前提、动作、判断、结果、失败 |
| 协作与流程 | 多角色、多步骤、跨模块／系统或连锁变化 | 责任、因果、分支、终点、时效、失败恢复 |
| 查询与计算 | 列表、搜索、报表、指标或数据分析 | 结果粒度、来源、筛选、计算口径、样例结果 |
| 权限与信息可见性 | 多角色、数据隔离或受限能力 | 谁能做什么、作用范围、限制条件及拒绝结果 |
| 外部契约 | API、文件交换、SDK、设备或第三方依赖 | 责任边界、输入输出、错误、兼容与恢复 |
| 质量与运行 | 性能、可靠性、安全、部署、迁移影响结果 | 使用条件、可测目标、测量方式及未决约束 |
| 交互 | 操作反馈、批处理、无障碍或终端限制 | 用户入口、反馈、错误、恢复与相关约束 |

业务系统可能重点展开对象与审批；SDK 可能重点展开调用契约和兼容；数据分析可能重点展开来源、口径与可复现性。不能用同一组业务单据模板覆盖所有项目。

## 共用的记录规则

跨章节使用的元素才分配稳定 ID；沿用项目已有编号。没有约定时可用 `REQ` 需求、`SCN` 场景、`OBJ` 信息对象、`ACT` 操作、`RULE` 规则、`LINK` 联动、`FLOW` 流程、`QUERY` 查询、`ROLE` 角色、`EXT` 外部契约、`NFR` 质量、`AC` 验收。前缀是示例，不是格式门槛。

每个有效定义能定位到来源、修订号和确认状态。规则只维护一份规范定义，其他表格、图、设计引用它；术语相同但语义不同先澄清，语义相同但名称不同建立别名。

以下模板可合并到场景章节，不要求逐项建文件。确实无相关行为可写“无”；不知道的部分关联待决问题，不能靠空白掩盖。

## 信息、对象与关系

对象可以是业务记录、文件、配置、消息、算法输入或分析结果，不等于数据库表。

- 定义业务含义、标识方式、产生与维护责任、权威来源。区分独立存在的信息与从属明细，不因页面上放在一起就认定同生命周期。
- 属性至少明确名称、含义、类型／格式、必填条件、合法值、默认值来源和唯一性范围。金额、比例、数量、日期说明单位、精度、舍入、时区或区间边界；只展开会影响本轮正确性的内容。
- 关系说明双方、方向、数量范围、可选性，以及新增、修改、删除、停用或归档时对另一方和历史记录的影响。引用数据变化后采用当前值还是历史快照，需要业务依据。
- 有生命周期才定义状态：初始／终止状态、迁移前提、触发操作、迁移结果、禁止路径；同一对象的审批状态和履约状态等独立维度不要混成互斥枚举。

| 元素／关系 ID | 定义与责任 | 关键约束或基数 | 生命周期／历史策略 | 来源与待决项 |
|---|---|---|---|---|

## 操作规格

每项操作按可观察结果拆分。一个用户任务可以组合多个操作；一次页面点击不天然等于一个业务操作，也不预设数据库事务边界。

| 字段 | 内容 |
|---|---|
| ID、目的与场景 | 为哪个用户结果服务 |
| 执行主体与触发 | 人、系统、时间或外部调用；权限和数据范围引用 |
| 主处理对象与输入 | 输入来源、必填信息和关联对象 |
| 前置条件 | 哪些状态、数据和依赖满足后可执行 |
| 规则引用 | 判断／计算的定义位置及调用时机 |
| 正常步骤 | 有业务意义的步骤；调用其他操作或流程时使用引用 |
| 本操作结果 | 输出、数据或状态变化；无变化时明确只读 |
| 后续影响 | 对其他对象、模块或系统的影响，引用 LINK；与本操作结果分列 |
| 失败与边界 | 校验拒绝、重复、并发、超时、取消或部分完成，按风险展开 |
| 验收 | 对应 AC，含可观察结果与副作用 |

## 规则职责与归属

按依赖数据和判断责任区分：单值约束、同一完整对象内部约束、跨对象／上下文判断、查询计算口径、流程局部分支。它们是分析层级，不强制对应独立模型文件或运行时规则引擎。

优先用属性定义表达类型、必填和枚举；其他判断在最接近其权威业务定义的位置维护。跨多个操作复用时引用同一规则，不复制一份近似表达式。仅被复用不等于必须提升为独立服务。

规则至少包含：ID、业务陈述、输入及来源、适用条件、判断／计算、输出、违反时结果、使用位置、来源与状态。重要阈值给出边界样例；无法确定数值时保留参数和待决问题，不编造组织政策。

规则回答“是否成立／算出什么”，操作回答“改变什么”。例如“余额足够则扣款”拆为余额判断和扣款操作；不能让判断是否满足本身产生扣款。技术实现可合并，业务语义仍要能分别验证。

明确条件为真、为假、输入缺失和求值失败的区别。条件为假可能是正常分支，不自动等于执行失败。结果曾成立后可能不再成立时，检查撤销、更正、冲销等反向路径。

## 流程与权限

流程描述从触发到业务终点的协作；操作描述局部结果，二者通过 ID 引用。多角色／多分支流程记录开始条件、活动、责任、分支条件、并行汇合、合法终点和异常退出。

需要审批时再展开审批对象、提交与决策权限、条件分级，以及通过、驳回、退回、撤回、重提的状态结果。职责分离、会签、代办等由实际要求决定，不能把“有权限操作”等同于审批，也不默认每项业务都要审批。

检查每个活动可从开始到达，每条路径有合法结束或明确的持续运行／等待语义。允许有出口的重试和返工循环；持续服务不要求虚构“全部结束”。子流程递归只有在方法允许且终止条件明确时才可采用。

权限表记录 `主体／角色 × 操作 × 数据范围 × 条件`。核对人工任务的执行角色确有授权，自动处理有执行身份和边界，查询与导出遵守数据范围。界面可见不代替实际操作授权；权限未知不能默认全员可用。

## 查询、统计与计算

不要把“支持统计”作为完整规格。定义使用目的、输出粒度、数据来源及时间范围、关系和筛选、结果列、公式、分组、去重、排序和必要的分页／导出。

业务指标还需说明纳入／排除哪些状态，空值和零值如何处理，时间采用发生时间还是处理时间，以及更正历史数据后如何重算。实时性和数据可见范围分别引用质量与权限要求。

多个一对多来源参与汇总时，用小样例验证不会因关联而重复累计。可先分别汇总再关联，也可采用其他已证明正确的方案；不把某种 SQL 写法当成业务需求。源数据、公式、报表文字和验收结果应一致。

只把有用户目标依据的查询列入正式范围；发现缺口可以提出候选，不设最低报表数量。

## 外部契约与质量要求

外部契约明确调用或交换目的、双方责任、触发方式、输入输出与版本、身份与数据范围、错误分类、超时后结果是否已生效、重复与顺序要求、恢复方式。行为未知时标为待验证，不凭“REST”“事件”推断业务保证。

质量要求采用：`使用场景／负载条件 → 目标或约束 → 测量方法 → 证据／待验证项`。比如延迟必须说明操作、数据规模、统计口径与测量环境；未知目标数值可作为候选，不能直接写成已承诺 SLA。

设计需要某种队列、缓存、数据库或部署拓扑时，由技术适配器论证。质量要求本身不授权安装、开发或上线。

## 视图与验收

关系复杂时用关系图，有状态的关键对象用状态图，多分支协作用流程图，角色较多时用权限矩阵。表格维护完整定义，图从相同定义生成；图中每个业务节点可回查，冲突必须修正。没有实际渲染过只报告语义核对，不声称可渲染。

验收用 `给定条件 → 执行动作 → 可观察结果`，引用需求和相关规则，覆盖主路径及会改变业务结论的拒绝、边界、权限、失败恢复和反向路径。区分“案例已定义”“样例推演通过”“测试执行通过”；三者不能互相替代。

遇到跨系统派生结果、统计重复累计或需要判断裁剪深度时，可读 [分析切片示例](../examples/analysis-slices.md)。不要将示例的规则、状态或技术候选复制成当前项目事实。
