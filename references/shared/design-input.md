# 设计输入与双向追溯

当需求交给适配器、开发规划或另一位协作者时读取。输入包是有效定义的索引与交接契约，可以是现有文档中的一节，不是要求另建一套模型或抄写一份需求。

## 确定本次输入

记录分析范围、目的、输入来源、适用约束、已确定的选择、仍有效的假设、期望设计深度及需要保存时的输出位置。有文档时记录实际位置与修订号；仅有对话或观察时记录可定位的来源，不补造版本或要求先生成前序文档。正式交接前按[就绪检查](readiness.md)判断；尚有关键缺口时可做方案探索，但不能交付为确定设计。

按相关性索引：

| 输入类别 | 交接的规范定义 |
|---|---|
| 目标与场景 | 用户结果、范围、优先级、正常与异常路径 |
| 信息与状态 | 关键概念、属性口径、关系、责任、生命周期与历史策略 |
| 操作与规则 | 输入输出、前后条件、规则定义和调用位置 |
| 协作与流程 | 影响矩阵、条件分支、交接责任、时效与失败恢复 |
| 查询与权限 | 数据粒度与计算口径、角色操作及数据范围 |
| 接口与质量 | 外部契约、兼容性、运行约束及验证条件 |
| 验收与未决 | AC、证据状态、阻塞关系和条件性假设 |

表中只放定义的引用及版本，不复制正文。下游不能在生成设计时无声重新拆分业务、添加审批、修改统计口径或选择失败后果。发现输入矛盾返回具体缺口；可以提出修订建议，待决定生效后更新相关定义。

## 可追溯关系

沿用项目已有追溯工具或表格；没有时按当前范围维护：

| 需求／场景 ID | 规则／操作／契约引用 | 设计元素／章节 | 验收 ID | 输入修订号 | 覆盖状态／缺口 |
|---|---|---|---|---|---|

关系允许一对多、多对一，不施加特定框架的一对一约束。不需要建模时，设计列可引用直接实现说明，或说明本轮不需要设计；有必要设计但未做时记为缺口，不能误记为不适用。

正向核对：当前正式需求是否都有承载位置与验收方式，遗漏项是否显式登记。反向核对：设计、界面操作、接口和任务是否都有需求或必要技术约束依据，是否引入未决定的业务能力。技术支撑项可以关联所支撑的用户结果与验证方式，不必编造用户需求。

进入实现阶段后可补实际模块／接口／任务／测试位置；分析阶段只填写已存在或明确标为拟定的落点，不伪造代码链接和任务编号。

## 方法与技术适配

将同一输入包交给[适配器目录](../adapters/catalog.md)选中的方法。方法决定如何表达和组织设计，技术适配器决定如何利用实际环境承载；二者都不能反过来覆盖已确认的需求事实。

适配器返回：采用的输入版本、设计与映射、选择及理由、覆盖缺口、冲突、实际验证与剩余验证。存在无法表达的需求时，选择配套规格、方法扩展或替换方法；保留原始需求与代价，不以“不支持”直接删除。

## 变更传播

变更生效后，从改变的定义沿上述关系追到场景、协作链、设计、验收和交付项。将尚未复核的项标为“需复核”，保留原输入修订号；复核完成后再推进版本，不先把全部版本号改成最新。

引用关系不完整时，针对被改术语及旧值做有边界的搜索补充影响判断；没找到引用不等于没有影响。详细处理沿用[变更分析](../changes/impact.md)。
