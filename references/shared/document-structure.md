# 文档结构、内容归属与材料管理

用于新建、更新或整理需求、模型、架构、组件、流程和交付文档。目标是让读者先理解当前主题的全貌，再按需要进入细节；来源与工作过程可追溯，但不参与拼装当前方案。临时咨询采用相同表达原则，不强制创建目录或文件。

## 从整体到局部

先确定本篇回答什么问题、读者需要据此做什么，再组织正文。通常沿“对象与范围 → 整体结论／方案 → 主要关系与关键场景 → 按主题展开 → 适用条件与必要引用”阅读；这是组织逻辑，不是固定标题模板。

- **主文建立整体认知。** 交代目标、边界、主要组成和协作、关键选择及成立条件。主体按能力、设计对象或责任展开，不按讨论日期、确认顺序或工具执行次序展开，也不能缩成只有链接的目录。
- **专题承接细节。** 协议、组件、算法、规则或流程细节归相应专题；主文保留理解全局所需的摘要、接口边界及引用，不复制专题完整定义。专题开头说明自己在整体中的位置、解决的问题及与相邻主题的分工，再展开本主题结构、协作和细节。
- **同一原则递归适用。** 组件专题、流程专题和子专题也先讲整体再讲局部。某段内容出现可独立说明的责任或契约、需要单独维护，或细节已使读者难以跟随主线时，先判断归属，再拆成子专题；原文留下结论、边界与入口。内容继续加深时允许进一步拆分，不限制固定层数。
- **拆分要改善理解。** 短小且紧密相关的内容保留在一篇，局部请求只展开本轮范围。按问题与维护责任拆分，不能按每次对话、每个技术名或固定字数生成文件。拆出后仍须能沿父文定位上下文，不能只把长文平均切段或留下空壳。

例如系统架构先解释主要组件怎样完成业务；组件设计再解释内部模块怎样协作；复杂的任务恢复可在该组件下另设专题。系统主文不展开每个队列开关，任务恢复专题也不能从参数清单开始，让读者猜测它服务哪个组件。

## 先判内容性质，再判维护责任

每次归并输入先回答：它定义什么，属于哪个范围，由谁维护？同一段话中混有需求、设计、来源和执行结果时拆开处理。

| 内容性质 | 唯一维护位置与正文表达 |
|---|---|
| 产品问题、目标、场景、行为、范围、成功判据及明确技术约束 | 需求正文；直接说明产品应达到的结果和边界。具体技术约束有真实来源时保留，不因其技术性而移走 |
| 概念语义、关系、状态与数据约束 | 模型或相应领域专题；关联场景与规则，物理实现按设计责任展开 |
| 组件、算法、协议、schema、存储及执行配置 | 对应架构或设计专题；说明机制、责任、输入输出和约束，不把工具选项冒充产品要求 |
| 跨组件的共同约定 | 共享契约专题；各组件只说明自己生产／消费什么、何时校验及如何处理结果，引用共同定义 |
| 用户故事、AC、研发测试任务与批次 | 按第四阶段约定在任务系统或本地独立故事中维护；总览保留边界、索引、依赖和批次 |
| 来源原话、确认经过、取舍与选择状态 | 来源或决策记录；正文只保留当前结论、适用条件及简短依据引用 |
| 环境、执行步骤、命令、日志、测量与实际结果 | 验证材料；正文只摘要与方案适用性有关的结论、限制和证据入口 |
| 本轮做了什么、谁受托、工具调用／审批、下一轮如何恢复 | 交接或工作记录；不进入需求、模型、组件设计正文 |
| 被替代方案、变化理由及下游处理 | 变更记录、版本历史或归档；当前正文清理旧规范和已解决问题 |
| 样例数据、替身、具体绑定及教学用例 | 样例或验证材料；已纳入正式范围的领域概念、实际集成契约仍归正式需求／设计 |

组件间的归属按责任判断，不能因为某项讨论发生在当前组件评审中，就把它的完整设计写在本组件。

例如执行组件提交后台任务时，其正文保留提交条件、固定输入、任务引用、结果核验、超时与续接边界；队列消费、定时触发、租约回收和解析隔离的实现由后台任务组件维护。跨双方的任务契约独立定义并互相引用。不能把相关内容一概移走，导致提交方缺少自己的交接与失败责任。

技术选型完成后，将语言、框架和关键机制按承载模块整合到当前方案。逐项确认表、讨论优先级和委托经过移交记录；影响实施的未决项在所属主题写清缺什么、阻塞什么、如何解决，不继续并列旧候选或“下一项再讨论”。独立选型报告本身可以比较候选，但仍按问题、比较依据、结论与条件组织。

## 正文使用对象语言

正式维护的正文直接陈述需求、设计及条件，不使用“用户提出／用户要求／用户希望”“本轮确认／本次讨论”“此前追问后决定”等对话转述作为结论句，也不以会话编号串起阅读主线。保留稳定需求／决策 ID 和必要引用即可；日期、版本与状态集中放在简短元数据中。

| 输入或过程记录 | 正文中的结果表达 | 依据放置 |
|---|---|---|
| 用户提出后台组件也做重任务 | 后台任务组件执行固定输入的有界作业，产出候选或结果；应用运行由执行组件推进 | 要求来源及选择状态归来源／决策记录 |
| 本轮确认某运行引擎，下一项讨论数据库 | 工件引擎采用已选运行框架；业务状态与框架检查点分别维护。数据库选择若影响实现，列具体缺口 | 确认次序和已关闭议题归决策／交接 |
| 未调用外部模型，调研委托尚未返回 | 不写入组件正文；如确实缺少支撑方案的证据，正文只说明相关选择的成立条件与缺口 | 委托及工具执行情况归交接 |

“用户”作为产品角色、用户故事的“我希望”等业务表达可正常使用。需要保留原话以解释歧义、访谈或决定依据时，放在独立来源材料／记录区，标明用途并关联整理后的定义；不因清理措辞删除确认依据，也不将候选润色为已确认要求。

区分**系统如何运行**与**代理如何完成工作**：设计中的任务领取算法、故障恢复步骤和业务时序属于机制说明；实际执行过的命令、测试输出、调研委托、写作过程属于记录。不能因“运行过程”四个字删掉必要的系统行为设计。

## 正式文档与辅助材料分区

按项目配置定位唯一维护位置。已有合适分区优先复用；未配置本地位置时，采用以下相邻目录，按需建立，不预建空目录：

```text
docs/
  project-analysis/                 当前需求与设计正文
    项目概览.md                      目标、边界、整体关系与阅读入口
    01-需求探索与澄清.md
    02-领域与数据模型探索设计.md
    03-技术架构探索与验证.md
    04-需求细化与交付推进.md
    requirements/                   必要的共享需求定义
    design/                         组件、协议、流程等专题及按需子专题
    stories/                        本地维护的独立故事
    scenarios/                      需要跨故事复用的场景
  project-analysis-support/         辅助材料，不承担当前规范定义
    决策/决策记录.md
    来源/资料依据.md
    交接/交接记录.md
    变更/变更记录-001.md
    验证/主题/验证报告.md             输入、环境、执行记录及结果
    附件/主题/                        可编辑图源、图片与其他附属文件
    草稿/                            尚未整合的片段、临时方案与工作表
    归档/                            必须保留且无版本历史可承载的旧材料
```

正式维护位置中的“草拟中”需求或设计仍可原位迭代；分区不代表已经批准或发布基线。辅助草稿是未整合的中间材料，不是另一份长期维护的规范。实验代码及可运行环境按项目约定放 `experiments/`，报告可原位引用，不为符合目录示例再复制证据。

远端文档按相同职责设置独立页面树或分组，正文页、交接页、验证页和附件入口分开。远端为正式来源时，本地仅保留已约定的草稿或索引，不能制造第二套正式正文。配置记录各区域的实际路径／页面。

正式正文可以引用辅助材料、嵌入附件图片，但不把报告、任务书或交接全文塞入组件目录。就绪摘要及有影响的证据结论可留在正文；完整检查过程及执行证据独立保存。

## 更新与清理

一次维护同时完成“归并有效结论”和“处理遗留材料”，不只在文末追加新段落。

1. 读取当前正文、相关专题和已有引用，按内容性质与维护责任确定落点；大幅重组且没有可恢复历史时，先在辅助归档区保存必要快照。
2. 把有效结论并入主题，移出对话、工作经过和完整执行记录；修正放错组件的内容，在双方保留各自责任和共同契约引用。处理旧范围、矛盾定义与已解决待决项。
3. 检查中间草稿：已整合且无独立价值的临时文件在本次维护范围内删除；必要来源、实验记录、交接和变化证据归入相应分区；有保留价值的旧材料才归档，不把全部临时文件永久堆入归档。无法确认用途的既有材料先查引用并标明归属待核实，保留原件，不据名称直接删除。
4. 同步配置、父文摘要、专题索引、图片／图源、任务及文内链接。迁移后不留两份有效正文，不靠同名副本维持旧链接。
5. 回读保存后的正文及必要规范引用，核对阅读顺序、归属、当前结论、图文一致和材料分区。完成汇报说明改动、清理与保留范围及真实验证状态；具体执行过程留记录。

既有目录只在请求和合理影响范围内调整，复用 ID 与有效内容；整理技能或方法时，样例项目仅提供问题证据，不能自动获得改写其产物的授权。

## 图示辅助理解

关系、协作或变化难以通过短段文字理解时使用图。第二、第三阶段分别遵循 [模型图输出](../stages/modeling.md#模型图输出) 和 [架构图输出](../stages/architecture.md#架构图输出)；专题与子专题沿用同一可读原则，图覆盖自己的范围，不要求每篇都有图或凑齐图种。

- 图前说明对象、问题、边界及现状／目标／候选状态；总览只画主要责任与关系，细节用与其对应的局部图，避免把组件、进程、库和操作步骤混成同层节点。
- 图后沿一个代表性场景带读对象如何协作或变化，指出关键约束、失败边界及定义位置。连线标明关系或交互，术语与正文一致；需要时附基数和图例，不只依赖颜色。
- 检查语法、关系方向、基数及图文一致。有渲染条件时预览文字、连线与展示尺寸；无条件时明确未预览，不将图源交付或语法核对描述为已展示、已通过视觉检查。定义变化时同步图及带读。

### Mermaid 与 SVG 的选择

先按图要表达的关系和版式要求选择制图方式，再按目标位置选择展示格式。Mermaid 图源可以导出 SVG；采用 SVG 展示不等于必须改用手工绘图，也不将 SVG 仅作为“不支持 Mermaid”的替代物。

| 情况 | 选择与交付方式 |
|---|---|
| 用户或项目已有明确图形规范、格式或可编辑工具要求 | 优先遵循已有要求；遇到实际展示限制时说明并提供适用格式，不擅自替换约定 |
| 主要表达结构关系、流程、时序、状态或数据关系，自动布局能清楚呈现，后续需要频繁修改关系并随文档维护 | 优先用 Mermaid 编写；目标支持且实际展示可读时，直接在正文或对话嵌入，不因文档属于正式设计就额外导出图片 |
| 需要精确控制分层／分区、对齐、节点尺寸、长标签、连线走向或页面比例；合理拆图后，自动布局仍妨碍理解 | 使用可控制版式的矢量方式制作并交付 SVG，保留可编辑源；适用于有这些版式需求的架构、部署或复杂专题图，不按图的名称一概指定格式 |
| 图本身适合 Mermaid，但目标不支持它，或要求在多份文档、导出文件中保持同一版式 | 保留 Mermaid 为源，渲染导出 SVG 用于展示；已有清楚的自动布局无需重新手绘 |
| 目标只接受位图或实际无法正确展示 SVG | 导出 PNG 作为展示副本，同时保留 SVG 或原始可编辑源；不把截图作为唯一维护源 |

复杂图先按整体与局部拆分，避免仅靠换成 SVG 或放大画布塞入全部细节。最终选择以实际展示尺寸下文字、分区、主路径和关系是否可辨为准；不以节点数量、阶段编号或“正文／附件”的位置机械决定格式。

同一张图只维护一个权威源：Mermaid 派生的 SVG／PNG 随图源重新导出，不分别手工维护；直接制作的 SVG 可以自身作为可编辑源，有额外生成源时记录对应关系。独立图源及导出文件放配置的附件区，用中文文件名，正文嵌入可展示版本并关联图源；引用图片不要求将附件放进正式正文目录。缺少所需渲染／导出工具时交付已有图源和正文，明确尚未生成或预览的部分，不宣称格式转换已经完成。

## 交付前的阅读检查

本轮需求、模型、架构、组件／流程专题或故事文档交付前，由**独立上下文的子 Agent**执行阅读评审。主 Agent 可以先自检，但自检不能替代该评审。检查只覆盖本轮文档及必要依赖，不扩成全项目审查，也不因局部任务而要求补齐其他阶段。

### 评审上下文与输入

- 创建不继承主会话历史、也未参与本轮编写的新子 Agent；不能复用编写者后只提示“假装第一次阅读”。工具支持时使用不复制历史的上下文模式。
- 固定待评审版本，使用提交／平台修订或只读快照定位；评审期间不改写同一版本。提供本轮交付用途、读者、范围、正文入口及其必要规范引用、图示和附件；临时在对话交付的文档可作为完整正文提供，不为评审强制建立长期文件。
- 不提供原对话、编写过程、旧方案、主 Agent 的自评、预期答案或预先指出的可疑问题。必要业务定义须来自正文引用的有效需求／契约，不能用作者口头补充替代文档缺口。子 Agent 不足以判断时报告缺失材料，不猜测补全。
- 子 Agent 只读所交付正文及其必要引用，返回理解、问题与证据，不修改原文、不扩展实施、不递归委派同类评审。仅使用当前环境允许的子 Agent 能力，不为完成评审擅自调用外部模型服务或外发材料。

### 阅读问题与返回结果

子 Agent 先用自己的话概括文档所表达的目标、边界、主要组成／关系及关键行为，再检查以下问题。不用标题齐全、词语扫描或文件数量代替内容判断：

- 首次阅读能否说明本主题是什么、在整体中做什么、主要结构与关系是什么？
- 能否按主文进入对应专题并继续理解，子专题是否仍先整体后局部，是否有过深细节淹没主线？
- 每个规范定义是否有唯一维护责任，跨组件内容是否只在本篇保留本方责任与共同契约？
- 移除聊天、确认经过、交接和执行日志后，当前方案是否仍完整，来源与状态是否仍可定位？
- 正式正文与辅助材料是否分区，中间文件是否已处理，必要证据与附件是否可访问？
- 图是否解释了重要关系，且与文字、表格和引用一致？局部任务不因这些检查被扩成全项目重构。

逐项返回可理解的结论、无法判断处及证据；问题定位到文件／章节或页面，说明缺什么、为何影响本轮用途、是否阻塞交付。图未实际查看、引用无法访问或上下文隔离无法确认时，明确标为未检查／无法确认，不能判为通过。阅读评审只证明本版本在所查范围的可理解性和一致性，不证明业务事实、实现或运行测试已验证。

### 修订、复评与记录

主 Agent 逐项处理意见：修正文档，或说明不采纳的依据及剩余影响，不能只回复“已处理”。影响整体理解、职责、关键行为或验收的缺口未解决时，不将相关范围标为可交付；需要业务决定的缺口沿既有范围处理，无依赖内容可继续。

修订涉及上述缺口或改变关键关系时，交给独立上下文子 Agent 复评修改后的版本及必要关联部分；保持同样的输入边界，不以主 Agent 的修复说明或自评代替回读。记录最后实际评审的版本与结果；同一版本无新增实质问题时不反复评审，后续实质修订不能沿用旧版通过结论。

评审范围、版本、上下文隔离方式、实际结果、意见处理及未检查项保存在辅助验证区，正文只保留必要状态和入口。纯评审任务的返回报告不再触发一轮同类阅读评审。若工具不支持独立上下文或调用失败，明确记录“独立阅读评审未完成”及原因，可以交付已完成的草稿与自检结果，但不能冒称独立评审通过，也不据此额外要求用户批准常规整理。
