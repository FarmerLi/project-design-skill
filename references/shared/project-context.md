# 项目上下文与技能交接

用项目根目录的英文隐藏文件 `.project-context.json` 保存项目定位、文档组织约定和交接入口，供 `project-design` 与 `coder-assistant` 共用。它回答“项目是谁、材料如何组织、有效材料在哪里、从哪里继续”，不承担需求正文、进展或详细平台配置。

## 定位与建立

先识别目标项目，读取已有 `.project-context.json`；查找时包含隐藏文件，不把技能开发目录当作业务项目。持续分析、跨技能交接或需要保存时，缺少配置可按 [JSON 模板](../../assets/项目上下文模板.json) 填入已知入口。单次咨询不要求建文件，也不为建配置补做其他阶段。

已有 `项目上下文.md`、`PROJECT_CONTEXT.md`、任务正文或远端配置页时先读取复用，不另建竞争来源。需要统一格式时，将必要入口转换为 `.project-context.json`，核对有效信息的承接位置并更新引用；详细约定仍留在所属文档，不因精简而丢失。升级技能不自动迁移业务项目。

## 最小共享字段

两个技能使用相同字段与含义；按当前工作需要填写，不要求填满模板，未使用字段可省略。

| 字段 | 含义 |
|---|---|
| `project.name`、`project.repository` | 项目名称／代号与实际仓库地址或项目入口，无代码仓库时可用远端项目 URL |
| `project.path_base` | 本地相对路径基准；配置位于项目根目录时为 `.`，本地其他位置显式指定；纯远端可省略 |
| `documents.formal_root`、`documents.support_root` | 当前需求／模型／架构／故事等正式正文入口，以及来源／决策／验证／附件等辅助材料入口；值为本地路径或实际远端 URL／ID |
| `documents.organization` | 本项目的目录／页面分组、命名及主文／专题组织约定。值为字符串，可直接写简短约定，也可注明所遵循的已有规范路径或实际远端 URL／ID，不要求另建规范文件 |
| `tasks.entry`、`tasks.mapping` | 任务系统项目／父项或本地故事入口，以及已有故事／AC／研发测试任务映射位置；未用任务系统时不强制接入 |
| `prototype.tool`、`prototype.source` | 需要原型时的实际工具与可编辑源路径或 URL／ID；预览、交互与设计规范从设计文档定位，不以截图代替源 |
| `handoff.design`、`handoff.development` | 设计侧与开发侧各自当前交接记录的路径或 URL／ID；可以指向同一份已有记录中的不同章节，不要求另建文件 |

配置使用 UTF-8 JSON 对象和上述英文键名，值可用中文；未知单值为 `null`，不得写入注释、Markdown 围栏或尾随逗号，保存后用 JSON 解析器回读。只补当前动作必需的入口与组织约定，保留不认识的已有扩展字段。入口字段及组织约定引用中的本地相对路径以 `project.path_base` 为基准，其自身相对本地配置所在目录解析；会话 worktree 中按对应项目根解析，不照搬其他会话的绝对工作区。

任务字段、平台参数、原型预览／规范、同步方向与操作范围按需从目标任务或相关文档读取，不在共享配置中展开整套配置表。不保存密码、令牌、业务正文、执行历史或授权开关；地址不代表写入授权，已有明确授权按范围沿用。

## 文档位置与组织约定

保存或整理文档前，读取 `documents.formal_root`、`documents.support_root` 和 `documents.organization`，沿已有索引定位当前主题。项目上下文决定实际目录／页面树、命名、主文与专题及各类辅助材料的归属；[文档结构规范](document-structure.md) 约束内容职责、阅读逻辑、唯一维护位置与材料清理，不提供可覆盖项目约定的固定目录树。阶段文件名和子目录示例只表达产物职责，不是未配置时的默认落点。

- **已有配置：** 直接沿用本次相关的有效位置与组织约定。没有 `documents.organization` 的旧配置仍可使用；从实际结构、索引和项目规范核实需要补充的约定，不因此搬迁文件。配置与现有材料不一致时核对有效来源，不按模板重建。
- **缺少配置或字段：** 先读取项目规范、现有目录／页面树和索引，将可核实的本次必要入口及组织方式补入同一份上下文，不覆盖其他字段。模板中的文档字段为 `null`，不代表默认采用 `docs/` 或任意其他路径。
- **确无既有约定：** 在当前保存授权和明确目标范围内，确定最小的正式／辅助位置及所需分组、命名，并在首次保存前记录到上下文。只有目标或组织方式存在无法推定且影响本次保存的选择时才询问；其余分析与对话草稿继续。配置中的计划位置不代表产物已存在，不预生成空目录或文件。

组织约定可以很短，例如“主文与专题按业务域分组，沿用现有中文文件名；交接、验证和附件分组保存在辅助入口；实验沿用项目现有实验位置”，也可以引用现有项目文档规范。只记录与当前工作有关的约定，不为填字段设计整套目录。正式与辅助区域可位于不同目录或远端页面组，不要求相邻；不因补配置迁移历史或建立第二套正文。

### 没有本地项目目录时

沿用已授权远端页面或父项中的“项目上下文”章节，以 JSON 代码块记录同一组必要字段，填实际 URL／ID，不虚构本地路径，也不要求建立仓库。已有等价配置页继续复用。不能保存时在回复中提供必要入口并说明未保存，只暂停依赖缺失信息的动作；不为交接复制一套本地正式正文。

## 与 coder-assistant 交接

- **设计交给开发：** 更新 `handoff.design` 所指记录，说明本次目标、范围与验收、有效需求／故事及相关模型、架构、原型／设计规范的具体来源和修订，以及阻塞与下一步。引用足够支撑当前任务的材料，不复制全部正文或要求五阶段齐备；分析完成不代表授权实现。
- **开发接收：** `coder-assistant` 读取同一配置，沿设计交接核对当前请求、有效输入和实际代码／测试；复用既有任务与 AC，不因技能切换重建任务或自动重跑设计流程。
- **开发反馈：** 开发侧维护 `handoff.development` 指向的实现、验收覆盖、实际测试及其代码状态、未完成项和下一步；业务或架构问题保留来源和影响，不静默改写需求。
- **设计继续：** 从开发交接读取实际证据，按 [工作契约](working-contract.md) 更新受影响的设计与追溯；旧交接不能覆盖更新后的有效规则，任务关闭或局部测试通过不等于业务已验收。

双方共用一份配置，只更新本次必要入口并保留另一侧字段；远端写回、任务操作和原型维护遵循各自实际授权。不要求两个技能同时安装，普通文档或任务也可提供同样的交接信息。

## 按需执行与更新

- 保存或更新文档时，按 [文档维护](../integrations/document-maintenance.md) 和实际正式位置更新已有内容；远端为正式来源时不另建本地正文镜像。
- 已授权创建／同步任务时，按 [任务落地](../integrations/task-tracking.md) 读取实际字段与映射，先准备可审阅拆分，再执行并回查，不重复建项。
- 制作或更新原型时，按 [原型与交互设计](../stages/prototype-interaction.md) 使用配置中的工具和可编辑源；工具不可用时如实说明未完成或替代稿，不擅自换正式源。

入口变化时同步受影响引用与交接。切换平台或保存位置不自动授权迁移历史、删除旧任务或重建正文。缺少工具、目标或权限时继续独立的分析和草稿，如实区分完成与未落地。
