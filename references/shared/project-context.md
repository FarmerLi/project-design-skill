# 项目交付配置

用 `项目上下文.md` 或远端“项目上下文”章节记录“任务建到哪里、文档维护在哪里、原型用什么工具、如何关联与更新”。它是任务、文档和原型操作的配置，不仅是参考资料地址索引。配置先说明项目及路径基准，再区分正式正文、辅助材料、原型源和任务目标；不把进展、确认经过或业务结论堆到配置开头。

## 定位与建立

先识别目标项目及已有配置入口，不把本地仓库存在与否当作项目身份的判断条件。有本地项目目录时，默认使用 `<项目根目录>/项目上下文.md`，不放在技能包或 docs/project-analysis 下。目标项目不明时才澄清，不把当前技能开发目录当作业务项目。

首次持续分析或需要落地任务／文档／原型时，若没有配置，使用 [模板](../../assets/项目上下文模板.md) 按已知资料建立，未知项按当前动作需要补充。已有配置中的相关信息可引用或迁入，不要求重复提供。多项目分别配置；临时咨询不要求创建文件。

已有项目仍使用 `PROJECT_CONTEXT.md` 或其他等价配置文件时，先读取并复用，不因中文命名另建一份。需要统一改名时，将文件改为 `项目上下文.md`，并更新所有入口及引用。

### 没有本地项目目录时

- 已指定远端项目页面且具有相应维护授权时，将模板内容作为该页面的“项目上下文”章节，或沿用其已有配置页；记录实际 URL／ID 和章节位置。项目概览、决策、交接与任务映射也可保存在已授权远端位置，不要求先建本地仓库或同名文件。
- 只有任务系统时，可在已指定且获授权维护的项目说明或父项中保留最小配置与关联索引。若用户已授权使用本地工作目录保存配置，也可在那里维护，并明确其对应的远端项目；不自动创建本地正式正文副本。
- 远端目标和写入范围已明确时，先利用本轮已知配置完成已授权写入，并将配置入口加入结果和交接；缺少本地根目录本身不阻塞写回。配置的保存仍限于已有授权范围；不能保存配置时，在回复中交付最小配置与实际链接并说明未保存，只暂停依赖缺失信息的动作。

本地相对路径以项目根目录为基准，配置放在单独工作目录时显式记录路径基准；远端使用实际页面／任务链接及 ID，不虚构本地路径。恢复时从用户给定的项目目录、远端页面或交接链接定位同一配置，不并行维护两份正式配置。以后建立本地项目时，优先保留指向远端配置的入口；迁移配置须有授权，并更新关联位置。

配置包含三组独立目标：

- **任务管理**：Jira 等系统的实例、项目、实际任务层级、父项、字段约定、执行时机与任务关联记录位置。
- **需求文档**：本地目录或 Notion／Confluence 的正式目标、文档组织方式、已有页面、更新范围、草稿和正式版本关系。
- **原型与设计**：原型设计工具、正式原型源、文件／页面 ID、预览方式、设计规范、组件库、素材位置和本轮操作权限。

原型工具由项目已有约定选择，例如 Figma、即时设计、Axure、Miro 或本地 HTML 原型。记录实际文件／页面和可编辑源，不只记录工具名称或导出图片；没有已指定工具时，可复用现有工具或采用本地可运行原型，并在配置中更新实际来源。工具地址或访问能力不代表已授权创建、发布、移动或删除原型，也不要用截图代替可维护源。

明确故事与任务的正式来源：已接入并获授权维护的任务系统承载故事、AC、执行任务、依赖和状态；本地维护则每故事独立文档，总览保留索引与批次。共享需求、模型、架构、原型与交互／设计规范仍在各自规范位置维护。不要因同时配置了文档平台和任务系统而建立两套故事正文；具体约定见 [第五阶段保存规则](../stages/delivery.md#保存与任务落地)。

明确原型与设计规范的正式来源：记录项目上下文中的原型工具、文件／页面 ID、可编辑源、预览入口及规范位置。原型和规范被多个故事复用时仍只维护一套权威版本，故事与任务引用其具体范围和修订。

### 正式正文与辅助材料的位置

记录两类独立位置：正式需求／设计／故事的维护根，以及交接、来源、决策、变更、验证、附件、草稿与必要归档的辅助根。已有合理分区优先复用，不能只配一个混合的“分析产物目录”。本地无约定时分别用 `docs/project-analysis/` 与 `docs/project-analysis-support/`；远端用独立页面树／分组。细节见 [材料分区](document-structure.md#正式文档与辅助材料分区)。

项目概览及阶段主文位于正式区；交接、决策和验证的实际位置记录为辅助入口，独立图源、原型导出预览和截图归附件区。原型工具中的正式文件／页面是可编辑设计源；稳定维护的草拟规范在正式位置原位迭代，辅助草稿只保存未整合材料。分区不等于业务已确认，切换位置时核对引用和唯一来源，不自动迁移所有旧材料。

选择某个目标后只保留有关配置，不要求用户同时填写所有平台。不在配置中重复需求正文、进度和业务决策，也不保存凭据。

## 使用配置

- 用户要求拆解后创建或同步任务，读取 [任务落地](../integrations/task-tracking.md)。先准备具体拆分，再按配置创建／更新；恢复开发时复用已关联任务。
- 需要保存或更新需求文档，读取 [文档维护](../integrations/document-maintenance.md)，按选定正式位置维护已有内容。各阶段默认文件名只是未配置时的本地约定，不强制再创建本地正式副本。
- 需要制作或更新原型时，读取 [原型与交互设计](../stages/prototype-interaction.md)，按配置中的工具、正式源和设计规范操作；工具或权限不可用时说明替代稿及未验证部分，不擅自切换正式来源。
- 已有明确的持续写回授权按约定执行，不每轮重复确认。仅记录系统地址不代表已要求写入。执行前先完成可审阅内容；若必须澄清，只询问阻塞目标定位、字段映射或授权范围的缺口。
- 需要访问某平台时，按当前环境实际可用的连接器、CLI 或相应技能执行，不假定有链接就能访问。配置也不授权额外评论、通知或消息发送。

缺少目标或权限时继续完成独立的分析和草稿，说明哪些尚未落地；不能把本地完成写成 Jira 已创建或远端文档已更新。

## 更新与来源

任务状态和需求正文可以分别以不同系统为准，不把二者当成重复副本。来源冲突时按已约定范围和版本核对；无依据则保留差异并澄清。

配置变更后更新受影响的交接和关联链接。切换平台或目标不是自动迁移授权，不自动复制历史文档、删除旧任务或重建全部内容。

配置按约定变化更新，结果状态和交接遵循 [工作约定](working-contract.md)。
