# 就绪检查与证据

在需求交给架构／模型探索、设计相互交接、用户故事交给研发测试、交付结果核对或变更结论准备交接时读取。检查本轮范围和实际下游用途，不要求所有远期需求同时完成，也不将阶段编号当作强制顺序。

## 分阶段判断

| 交接 | 要能回答 | 会阻塞的典型缺口 |
|---|---|---|
| 需求 → 架构／模型探索或故事细化 | 现状与目标、用户结果、价值依据、本轮范围及取舍、责任和约束是否明确，核心闭环与成立前提有什么证据；见[第一阶段](../stages/discovery.md#完成标准与交接) | 会推翻范围、价值或责任边界的前提未决，关键闭环断裂，必要承接无依据；可对假设做探索或验证，但不判为确定输入 |
| 模型 ↔ 架构 | 概念与逻辑模型中的语义、关系、规则及一致性要求是否足以支持当前架构决定，架构能否承载并支持物理设计完善；见[模型](../stages/modeling.md)与[架构](../stages/architecture.md) | 影响当前决定的业务边界或规则未明、架构与模型冲突、关键技术假设未获支持、规则与生命周期无法表达；架构探索不以物理模型全部完成为前提，不能以 demo 演示或结构图代替验证 |
| 仅交付故事与验收条件 | 业务意图、范围、关键规则与重要异常是否有依据，验收结果是否可判断；见[故事细化完成标准](../stages/detail.md#完成与回退) | 会改变预期行为或验收结果的业务问题未决；尚未开展的设计或任务拆分只影响后续研发测试交接，不自动阻塞本轮细化 |
| 故事细化 ↔ 设计 | 当前故事的规则、状态、依赖和失败结果足以设计吗，设计限制是否需要返回业务取舍 | 关键业务口径仍靠猜测、必要能力无落点、需求与设计冲突 |
| 故事与设计 → 研发测试 | 故事的价值与范围、必要设计、可验证验收条件、研发与测试任务及依赖是否足够执行；见[第四阶段](../stages/delivery.md#两类完成判断) | 重要规则或验收条件未定、必要技术验证未完成、测试数据／环境缺口阻塞相关工作；任务拆完不等于就绪 |
| 实现与测试 → 交付完成 | 当前版本是否满足约定验收，必要集成、迁移、回归和运行条件是否有证据，遗留问题如何处理 | 只有文档或任务状态、缺少测试结果、关键验收失败或尚未执行；需要业务验收／上线但没有对应证据 |
| 变更 → 新基线 | 哪些定义已改变，下游是否已同步复核 | 旧设计继续引用已失效规则、修订号错配 |

“可供设计”允许尚未决定实现技术；“可交付研发测试”不能用技术名称代替业务定义。远期或独立待决项不应阻塞已经清晰的范围。第一阶段内部的价值评估和概要收敛分别沿用其完成标准，不额外构成阶段门禁；缺少量化基线不必阻塞业务探索，但不能据此虚构收益或量化验收。

## 逐项记录结果

对适用项填写 `通过／未通过／待验证／不适用`，并附证据位置、输入修订号、问题及影响。不适用须有理由；没有执行检查用“待验证”，不能默认为通过。

| 检查 | 通过依据 |
|---|---|
| 整体认知与一致 | 当前正文及必要规范引用足以理解本轮结果：需求的问题、目标与能力闭环，模型的语义、关系及规则承载，架构的取舍、责任和关键链路，或交付的用户结果、验收、依赖与状态；按本轮用途检查，不要求补齐其他阶段。每项定义有唯一维护位置，无需要读聊天、历史、样例或运行日志才能消解的矛盾及陈旧待决项 |
| 目标与范围 | 所有正式需求有目标／用户任务依据，候选和范围外项未混入承诺 |
| 术语与信息 | 关键概念、字段口径、责任和关系一致，无未说明的同名异义或隐含生命周期；产品、外部系统与样例的术语和角色归属清楚，未将样例对象直接升级为通用规范 |
| 范围与验证边界 | 产品目标、近期交付、验证计划与实际覆盖分别表达；验证未执行或仅覆盖局部时未缩减既定目标或夸大已实现支持；需求、设计、样例和历史各自承担明确责任 |
| 操作与规则 | 输入、前后条件、判断、结果各自明确；规则有唯一规范定义，重要阈值有边界样例 |
| 状态与流程 | 操作后果与状态迁移一致；分支可达，结束／等待／重试语义明确，无未解释死路 |
| 跨边界影响 | 本轮变化操作均已检查；源结果与后续影响分开，链路、失败和反向路径有定义 |
| 查询与计算 | 粒度、来源、过滤、公式与样例结果一致，多明细关联不会重复累计 |
| 权限 | 执行角色、操作许可与数据范围一致；拒绝情形可验收，自动操作边界明确 |
| 外部依赖与质量 | 契约、责任、关键失败和可测目标有依据；未验证能力明确列出 |
| 技术验证 | 命题、通过条件、实际环境、输入与结果可定位，替身和规模限制明确，未把 demo 外推为生产保证 |
| 模型与演进 | 相关语义、行为和数据视图一致，现状／目标分开；关键元素有场景／规则或技术依据，平台模型、接入领域与样例映射的适用范围清楚；必要迁移、兼容和恢复条件有方案及验证方式 |
| 图示与图文一致 | 包含模型／架构设计时，已交付对应范围的总览图与场景／链路带读，必要局部图与总览可对应；关键关系、方向及边界可辨，节点、条件和状态可回查，图、表、文字不存在冲突；按展示位置提供可用格式，如实记录预览限制，见 [图示约定](working-contract.md#图示与阅读说明)。纯职责整理、契约核对、比较或局部验证不强制总览图 |
| 设计覆盖 | 每项当前范围需求有设计落点或明确缺口；每项设计决定有需求或技术理由，关键链路及失败后果有承接，未增加未授权业务范围，实验简化未无依据地成为正式方案 |
| 故事与任务 | 当前用户故事说明角色、情境、价值和边界；研发测试任务引用故事及验收条件，技术前置任务有目标与验证依据 |
| 验收覆盖 | 需求、关键规则和重要异常有可判断的 AC；条件、动作、可观察结果及验证方法明确，必要数据和环境有准备安排；判据不由单一样例反推，具体用例及执行结果不代替规范定义 |
| 交付证据 | 实现版本、测试执行范围、AC 结果和遗留问题可追溯；约定要求的集成、迁移、业务验收及上线状态有实际依据 |
| 版本与证据 | 来源及确认状态有效、引用可解析、输入版本匹配、未决事项与受影响项已关联 |

若某项不适用于当前交接深度，可以说明“需求探索仅识别查询目的，口径在故事细化时确定”，而不是假装已经完成详细规格。技术验证并非每次都需新 demo，已有有效证据可以复用；交付证据在准备交接时尚未产生，记为未执行，不因此阻止交接，也不判交付完成。

整体认知按本轮用途判断：局部请求只检查相关功能及必要上下文，现状探索不强制补产品规划。不能用一段泛泛介绍、完整的标题表或删除来源措辞作为通过依据；实际回读并核对需求的目标—场景—能力、模型的概念—关系—规则、架构的驱动—选择—协作或交付的故事—验收—任务，沿必要引用检查关键边界。术语归属不要求所有项目建立相同分层，也不移走产品本来就包含的业务概念、实际集成契约或明确技术约束。

## 业务确认与分析检查分开

用户明确要求、已确认决定和明确授权的委托选择可以直接使用，无须重复确认。整理措辞、编号、引用和等价视图由 AI 完成。

缺乏依据的企业政策、关键阈值、数据处置、失败后果或权限不能凭惯例确定。先做出可评审草稿，集中提出会影响下一步的 1～3 个问题。每题说明缺口、建议及依据（若有）、替代选项和影响；没有合理建议时说明所需事实，不编造“推荐政策”。

问题记录：`OPEN ID → 缺失事实／待决选择 → 影响的需求与产物 → 当前条件性假设 → 解决方式 → 是否阻塞哪一步`。用户沉默、未反对和超时不是确认；可以继续与它无依赖的分析。

## 交接结论

给出可用的范围、检查结果及证据、阻塞项、可继续事项和下次必读位置。存在关键未决项时交付条件性草稿，不给整个范围盖“完整”章；某个切片就绪时仅对该切片作结论。

持续分析时将结果保存在对应产物的“就绪检查”小节；跨多个文件时可单建 `就绪检查.md` 并由概览索引。无需为一次性小问答建立检查档案。

格式／引用检查只证明结构；样例推演只证明指定输入的逻辑；实际测试只证明指定环境和执行范围。报告具体做过什么，不能把文档自检表当成运行测试结果。
