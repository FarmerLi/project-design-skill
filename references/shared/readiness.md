# 就绪检查与证据

在目标交给价值评估、价值判断交给方案概要、概要交给细化、需求交给设计／开发、或变更结论准备交接时读取。检查本轮范围和实际下游用途，不要求所有远期需求同时完成。

## 分阶段判断

| 交接 | 要能回答 | 会阻塞的典型缺口 |
|---|---|---|
| 目标 → 价值判断 | 谁在什么场景下有什么问题，期望改善什么、如何观察，初步边界与已知约束是什么，剩余未知为何不阻塞判断；详见[目标阶段完成标准](../stages/discovery.md#完成标准与交接) | 分析对象不明、成功信号无法观察、影响当前判断的目标或约束冲突未解决；缺少量化基线或目标值本身不构成阻塞 |
| 价值判断 → 方案概要 | 哪个范围值得推进、依据与成立条件是什么，项目成立前提是否有支持证据，剩余风险如何承担与验证；详见[价值评估完成标准](../stages/feasibility.md#完成标准与交接) | 决定项目是否成立的前提未验证、相关硬约束冲突未解决，或剩余风险缺少接受依据与必要验证安排；评估完成、先验证或暂缓结论本身不代表概要就绪 |
| 概要 → 细化 | 核心结果、首期边界、主要协作和风险是什么 | 核心闭环断裂、关键依赖无人承担 |
| 细化 → 设计 | 行为、规则、状态、依赖和失败结果是否足够明确 | 关键业务口径仍靠猜测、后果未定 |
| 设计 → 开发规划 | 每项需求如何承载、哪里有缺口、如何验收 | 必要能力无落点、设计与需求冲突、验收不可判断 |
| 变更 → 新基线 | 哪些定义已改变，下游是否已同步复核 | 旧设计继续引用已失效规则、修订号错配 |

“可供设计”允许尚未决定实现技术；“可进入开发”不能用技术名称代替业务定义。远期或独立待决项不应阻塞已经清晰的范围。

## 逐项记录结果

对适用项填写 `通过／未通过／待验证／不适用`，并附证据位置、输入修订号、问题及影响。不适用须有理由；没有执行检查用“待验证”，不能默认为通过。

| 检查 | 通过依据 |
|---|---|
| 目标与范围 | 所有正式需求有目标／用户任务依据，候选和范围外项未混入承诺 |
| 术语与信息 | 关键概念、字段口径、责任和关系一致，无同名异义或隐含生命周期 |
| 操作与规则 | 输入、前后条件、判断、结果各自明确；规则有唯一规范定义，重要阈值有边界样例 |
| 状态与流程 | 操作后果与状态迁移一致；分支可达，结束／等待／重试语义明确，无未解释死路 |
| 跨边界影响 | 本轮变化操作均已检查；源结果与后续影响分开，链路、失败和反向路径有定义 |
| 查询与计算 | 粒度、来源、过滤、公式与样例结果一致，多明细关联不会重复累计 |
| 权限 | 执行角色、操作许可与数据范围一致；拒绝情形可验收，自动操作边界明确 |
| 外部依赖与质量 | 契约、责任、关键失败和可测目标有依据；未验证能力明确列出 |
| 图文一致 | 图中节点、关系、条件和状态可回查；图、表、文字不存在冲突 |
| 设计覆盖 | 每项当前范围需求有设计落点或明确缺口；每项设计决定有需求或技术理由，未增加未授权业务范围 |
| 验收覆盖 | 需求、关键规则和重要异常有可判断的 AC；验证方法与风险对应 |
| 版本与证据 | 来源及确认状态有效、引用可解析、输入版本匹配、未决事项与受影响项已关联 |

若某项不适用于当前交接深度，可以说明“概要阶段仅识别查询目的，口径在细化阶段确定”，而不是假装已经完成详细规格。

## 业务确认与分析检查分开

用户明确要求、已确认决定和明确授权的委托选择可以直接使用，无须重复确认。整理措辞、编号、引用和等价视图由 AI 完成。

缺乏依据的企业政策、关键阈值、数据处置、失败后果或权限不能凭惯例确定。先做出可评审草稿，集中提出会影响下一步的 1～3 个问题。每题说明缺口、建议及依据（若有）、替代选项和影响；没有合理建议时说明所需事实，不编造“推荐政策”。

问题记录：`OPEN ID → 缺失事实／待决选择 → 影响的需求与产物 → 当前条件性假设 → 解决方式 → 是否阻塞哪一步`。用户沉默、未反对和超时不是确认；可以继续与它无依赖的分析。

## 交接结论

给出可用的范围、检查结果及证据、阻塞项、可继续事项和下次必读位置。存在关键未决项时交付条件性草稿，不给整个范围盖“完整”章；某个切片就绪时仅对该切片作结论。

持续分析时将结果保存在对应产物的“就绪检查”小节；跨多个文件时可单建 `readiness.md` 并由概览索引。无需为一次性小问答建立检查档案。

格式／引用检查只证明结构；样例推演只证明指定输入的逻辑；实际测试只证明指定环境和执行范围。报告具体做过什么，不能把文档自检表当成运行测试结果。
