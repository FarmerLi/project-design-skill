# 就绪检查与证据

准备正式交接或需要判断成果能否支持后续工作时使用。普通分析按本轮问题判断完成，不对每次输出填写阶段和通用检查表。

## 分阶段判断

下表按交接用途选用，没有涉及的工作无需逐项声明不适用。

| 用途 | 需要足够明确的内容 |
|---|---|
| 需求探索 | 用户问题、关键场景、本轮范围与影响下一步的未知；有依据的暂缓或先验证建议也可以完成分析 |
| 模型设计 | 当前概念、关系、规则能支撑所需场景；物理存储与迁移只在当前用途需要时完善 |
| 技术比较或验证 | 选择依据、影响决定的条件、证据及限制；可以完成局部任务而不形成全系统方案 |
| 完整系统实施交接 | 主要机制、组件、所选技术、关键协作和必要运行部署清楚，影响当前实施的选择已处理 |
| 交互设计 | 当前任务的入口、操作、关键状态、反馈和恢复明确；已有公共规范适用，无实质冲突 |
| 故事／验收细化 | 行为与结果可判断，重要业务分支有依据；尚未安排实现不妨碍本轮细化完成 |
| 研发测试交接 | 执行项及必要引用能解释目标、关键行为、产出、验收、依赖和阻塞 |
| 实际交付 | 当前版本有约定验收、必要集成／迁移与运行条件的实际证据 |
| 变更处理 | 差异、影响与已修订／待复核范围清楚 |

交接深度由实际用途决定，关键缺口只限制相关工作。凭证缺少可以只阻塞真实集成，远期技术选择可以留到对应切片；不能把部分可做写成整体交付完成。

## 逐项记录结果

先回答“本轮结论是否足够支持预定用途”，再说明具体缺口和影响。通常在交付说明、当前文档或任务里用简短结论即可，不另存就绪报告，也不逐条标记通过／不适用。

复杂交接或项目要求检查记录时，只列会影响本轮用途的检查项、结论、必要证据和阻塞。重点检查业务语义、关键场景、设计协作与验收的一致性；标题、编号和图表齐全不能代替内容判断。

阅读检查默认自行完成；独立评审的适用条件及执行方式见 [阅读规则](document-structure.md#交付前的阅读检查)。普通任务没有独立评审，不构成未完成；实际要求的评审未执行则如实说明。

## 业务确认与分析检查分开

明确要求和已有授权直接复用。缺乏依据、会改变行为或验收的企业政策、阈值、权限和失败后果保持待决；先给可评审草稿并提出关键问题，不虚构推荐政策。

来源存在、用户未反对、设计核对完成都不代表业务决定已作出。关键未知记录在所属主题或当前任务，注明影响和解决方式，必要时保留已有 OPEN ID。

## 交接结论

说明本轮完成什么、哪些范围可继续、哪些事项仍受阻，以及实际做过的验证。正文、任务和证据已有入口足以恢复时直接引用，不再复制一份交接。

格式检查只证明结构，场景推演只证明指定逻辑，运行测试只证明所测版本、环境和范围。未执行不写为通过，文档完成不代表实现和实际交付完成。
