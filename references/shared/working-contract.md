# 工作与交接契约

本契约由单一技能入口及其能力文件共用。它约定状态与交接，不规定所有项目都必须生成同样多的文档。下面的产物路径相对于分析材料目录；用户指定路径优先。技能文件自身的 references 路径始终相对于技能包，不与业务项目材料混用。

## 工作目录与最小材料

持续分析或需要落地任务／文档时，先按 [项目交付配置](project-context.md) 读取被分析项目根目录的 `PROJECT_CONTEXT.md`，缺失则按模板建立。临时问答无需创建或补齐配置。配置记录任务管理系统与文档维护目标、创建／更新规则及关联方式；不是分析进度文件。下面的文件名是未指定正式位置时的本地默认值，配置的实际位置优先。

未配置正式维护位置时可使用被分析项目的 `docs/project-analysis/` 保存本地草稿。指定 Notion／Confluence 后，按 [文档维护](../integrations/document-maintenance.md) 更新对应页面或章节，不再强制建立同名本地正式副本。各阶段写入文件的约定均受此配置覆盖。先确认被分析项目，不能把业务材料默认写到技能包里。临时问答不强制落盘；持续分析或需要交接时逐步保存。

本契约及各能力文件中的“写入／更新”要求仅在本轮确需保存且符合用户授权时执行；临时问答在对话中交付相同内容即可。按需要逐步建立，禁止启动时生成一批空文档：

| 文件 | 用途 | 更新责任 |
|---|---|---|
| `project.md` | 项目基础、本次任务、目标、范围、阶段状态、建模与技术选择、关键约束、当前产物及版本索引 | 当前能力 |
| `decisions.md` | 有效决策、假设、待决问题及其来源 | 当前阶段，只维护相关条目 |
| `handoff.md` | 下一轮恢复入口，保留最新交接 | 当前阶段 |
| `baseline.md` | 需要持续引用的现状，区分实际／约定／目标行为 | 现状分析 |
| `01-discovery.md` | 目标、问题与成功标准 | 目标澄清 |
| `02-feasibility.md` | 价值、可行性、取舍与验证 | 价值评估 |
| `03-outline.md` | 产品／项目方案概要 | 方案概要 |
| `scenarios/SCN-001.md` | 单场景的详细需求和验收案例 | 需求细化 |
| `05-delivery.md` | 交付批次、依赖、验收与变更影响 | 交付规划 |
| `design/` | 所选适配器的独立设计产物 | 对应适配器 |
| `changes/CHG-001.md` | 跨多个产物、需要持续追踪的变化及处理状态 | 变更分析 |

信息、操作、规则、协作等共享定义优先用已有文档章节；确需拆分时按 [通用分析规格](analysis-spec.md) 组织到 `requirements/` 或配置的正式位置。设计交接索引和就绪检查也可内嵌到当前产物，不强制新增文件。

小项目可以合并阶段文档，用章节索引交接；复杂项目按场景拆分。不要复制已有定义，只引用规范所在位置。

`PROJECT_CONTEXT.md` 管“任务建到哪里、文档维护在哪里、按什么规则更新”；`project.md` 管“当前项目要做什么、进行到哪”；`handoff.md` 管“下次继续什么”。概览中的产物索引记录实际文档和任务关联及版本，不重复维护目标系统的配置。

## 需求基线

基线是当前有效的业务结论集合，可以分布在上述文件中。按本轮需要记录：
目标及成功标准、用户与场景、范围和优先级、业务概念和规则、状态及协作关系、外部依赖、质量要求、验收案例，以及事实／假设／待决事项。

核心需求不使用特定模型的字段作为必填项。技术约束如确实存在，应记录来源和约束性质；它们不是凭空排除业务需求的理由。

概要与细化按 [通用分析规格](analysis-spec.md) 判断维度覆盖，需求进入设计时使用 [设计输入与追溯](design-input.md)。有效需求定义是业务依据，设计是带版本的承载方案；已有实现是现状证据。三者冲突要定位并处理，不能用任意一层的“唯一真相”覆盖其余层。

建模方法与技术方案分别记录选择、状态（候选／评估中／已选择／已替换）和适用范围；“未选择”与“不需要额外建模”也都是有效结论。状态不用来替代业务确认或技术验证证据。

## 区分来源与确认状态

两个维度分别记录，不把“有出处”或“未被反对”当作“已确认”：

- 来源：用户明确陈述、指定文档（含路径／版本／章节）、现状观察、AI 推测。
- 状态：已确认、待验证假设、待决问题、已撤销／被替代。

用户的明确要求可以直接记为已确认，无须让用户再确认一次。未经确认的材料推导、AI 建议或默认值仍为假设。业务描述中事实与建议混杂时分开登记。

影响范围、规则、架构或验收的条目使用稳定 ID，例如 `DEC-001`、`ASM-001`、`OPEN-001`、`REQ-001`、`SCN-001`；不为每句话编号，不重用废弃 ID。

决策条目最小格式：

| ID | 内容 | 来源 | 状态 | 适用范围／影响 | 验证或解决方式 |
|---|---|---|---|---|---|

来源不足时明确写“依据不足”，不杜撰指标、访谈、预算、确认人或验证结果。历史方案放在归档段，恢复时只读当前有效项。

## 版本、完成标准与变更

需要保存的阶段产物头部记录：阶段、修订号、状态、采用的输入路径及修订号、更新日期。对话或现状观察没有文档修订号时记录可定位的来源，不虚构版本。正文不需要复制全部上游内容。

- 草拟中：结构或内容仍在形成。
- 待关键决策：存在影响本阶段结论的未决问题。
- 可供下阶段使用：当前交付范围足够明确，关键阻塞已解决；可以携带不影响下一阶段的待办。
- 需复核：引用的上游结论已发生相关变化。

状态表示准备程度，不代表用户对所有内容作了确认。完成标准依项目和阶段判断，不追求所有未知清零；记录剩余未知为什么不阻塞下一步，以及何时必须解决。

阶段切换采用 [就绪检查](readiness.md) 的适用项及证据。复杂需求不能仅凭“主路径已写完”标记可用；小任务也不因没有全套图表而被阻塞。

上游变更已确定时（提议尚在讨论时不覆盖有效基线）：
1. 修改有效结论，保留被替代项及理由。
2. 按引用关系找出受影响的场景、设计和验收案例，标为“需复核”。
3. 更新概览和交接，明确哪些内容仍然有效。
4. 不自动重写所有下游文档，不假装已经完成复核。

## 每轮恢复与保存

恢复顺序：技能入口 → 根目录 `PROJECT_CONTEXT.md` → 配置指向的概览与交接 → 相关有效决策与关联任务 → 当前能力和必要输入章节。配置缺失时从用户已给出的位置和历史材料补建配置，不重建已有需求或任务。发现版本不一致，先评估变化是否影响本轮，不让旧交接覆盖新文档。只读有效条目及其必要依据，不把历史备选方案整份带入。

持续分析或需要交接时，结束前按配置保存足以独立恢复的信息；临时问答只交付本轮结果和必要的后续说明，无需逐项建立交接档案：

```text
分析对象与当前阶段：
本轮完成：
本轮产物及修订号：
当前有效决策：
仍未解决的问题及是否阻塞：
下一步任务及完成标准：
下一步必读路径／章节／修订号：
可按需读取的补充材料：
建模方法与技术方案、对应适配器及状态：
```

交接摘要负责导航，不替代原始业务规则。规模增长时，把已关闭问题和废弃方案移至归档文件并保留链接，不在后续每轮重新加载。没有文件写入能力时，提供可复制的交接内容并明确尚未保存。

文件本身不会因对话压缩而改变，但不能假定其内容一直完整驻留上下文。方法不清楚时重读当前 reference；业务事实不清楚时读有效产物，不只依赖聊天摘要。宿主不能访问文件时明确限制。

## 对话与范围控制

先利用已有信息草拟，再问对推进最有影响的问题。通常每轮聚焦 1～3 个相关问题，有合理依据时给推荐答案和影响；涉及公司事实且无依据时，说明需要什么信息，不硬编推荐值。

交付节奏遵循本轮请求：只分析一个场景或一个阶段时，到该范围完成即交接；已授权连续分析时可以继续。不因存在独立的待决事项停下全部分析，但依赖该事项的结论保持条件性。

用户只提出想法时，不把候选功能默认纳入范围。目标可通过流程调整、采购或更小改动实现时，应纳入比较。分析任务本身不授权开发、部署、发送消息、购买服务或改动业务系统配置；分析材料的维护配置按前述 PROJECT_CONTEXT.md 约定处理。
