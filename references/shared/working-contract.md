# 工作与交接契约

在需要处理选择状态、版本或持续恢复时使用。普通分析遵循入口的默认工作方式；这里的记录规则只用于确有维护需要的信息。

## 工作目录与最小材料

需要保存时更新用户指定位置或已有主题，业务产物不写入技能包。[文档结构规范](document-structure.md) 决定内容怎样承载；已有项目配置可帮助定位，缺配置不阻塞保存，也不要求建辅助区或阶段文件。

## 需求基线

当前有效需求可以是一段对话、一份文档或分布在相关主题的定义。依用途明确目标、场景、范围、关键规则与约束；完整实施交接再补足相关规格。已有实现只证明观察到的行为，不能自动覆盖有效要求。

## 内容归属与当前正文

有效结论更新到原主题，理由、来源和简短验证结果可就近表达。历史、长日志与必要原始材料通过引用关联，具体见 [文档组织](document-structure.md)。

## 图示与阅读说明

按 [图示约定](document-structure.md#图示辅助理解) 选用帮助理解的图，图文同步。局部核对不补全项目视图。

## 区分来源与确认状态

区分明确要求、指定材料、现状观察和推测。用户明确要求与已有授权可以直接使用；建议、假设和待决问题保持可辨，不把沉默视为确认。

普通结论就近写清依据和未知，无需每条登记来源／状态表。重要取舍记录选择、关键理由与影响即可；只有后续需要稳定引用或管理多个待决项时，沿用／增加 ID。已有 DEC、REQ、OPEN 等 ID 和关系继续有效，不因精简重新编号或批量迁移。

## 版本、完成标准与变更

优先用 Git 提交、文档平台修订或已有发布机制定位历史。普通原位修改不额外分配基线号，也不为每次讨论建立变更条目。

- 等价措辞与结构调整：保持含义和有效状态，同步必要引用。
- 需求或设计改变：更新原主题，核对实际受影响项；重大跨文档、迁移或兼容变化再按 [变更分析](../changes/impact.md) 保留必要跟踪。
- 固定交接或正式发布：按项目约定标明有效输入与修订。旧版本的测试结果只证明原版本，未复核下游保留真实输入和具体缺口。

状态用来说明什么已经完成、什么尚待决定或验证，通常一句话即可。项目已有状态体系时沿用；阶段文件完成、业务决定、实现和运行结果分别判断，不要求为所有定义维护多套状态列。

## 每轮恢复与保存

恢复先读当前任务及其引用；入口分散时查 [项目上下文](project-context.md)，只在恢复实际进展需要时读取交接。核对当前正文与现场变化，过期交接不能覆盖有效结论。

保存首先更新正文。需要中断或转交，且任务现有内容不足以恢复时，复用一处交接说明：目标与有效入口、已完成／未完成、阻塞及下一步；实际运行证据给必要引用。设计和开发可以使用同一记录，不按轮次、阶段或技能切换建立新文件。

已有交接更新当前信息，历史沿 Git／平台修订保留。已经反映在正文、不会影响恢复的工作经过无需记入交接；不把原需求和全部决定再抄一遍。缺少保存工具时在回复交付必要信息并说明尚未保存。

## 对话与范围控制

利用已有材料直接给理解或可评审草稿。多议题时说明当前重点和推进顺序，单一问题直接处理，不为流程另建议程表。

只追问会改变当前业务结果、数据含义、范围或验收的事实与取舍，通常集中为少量问题。低影响命名和等价整理自主完成；关键业务政策缺乏依据时保留条件，继续无依赖部分。

结论满足当前用途后结束；已授权连续推进则继续可推进工作。讨论中的候选不自动纳入范围，分析也不自动授权应用开发、部署或无关外部操作。
