# 工作与交接契约

本契约由单一技能入口及其能力文件共用。它约定状态与交接，不规定所有项目都必须生成同样多的文档。产物名称仅说明职责，实际位置和命名由项目上下文约束。技能文件自身的 references 路径始终相对于技能包，不与业务项目材料混用。

## 工作目录与最小材料

持续分析或需要保存／落地时，按 [项目交付配置](project-context.md) 定位目标项目、正式文档与辅助材料区域。临时问答无需创建配置或文件；所有能力文件中的“写入／更新”均以确需保存且符合实际授权为前提。按需建立，不预生成空文档，也不将业务材料写入技能包。

目录、文件命名及专题组织按 [项目上下文中的文档约定](project-context.md#文档位置与组织约定) 确定；正文、辅助材料的职责和清理遵循 [文档结构规范](document-structure.md)。缺少配置先核实既有结构并补充，不以技能示例作为默认位置；可直接对应远端页面／章节，不强制建立本地副本。

| 材料 | 维护职责 |
|---|---|
| 项目根目录 `.project-context.json` 或远端配置章节 | 项目、文档入口与组织约定、任务、原型源及设计／开发交接入口；不保存进展或业务决策 |
| 正式区 `项目概览.md` | 项目目标、边界、主要组成与阅读入口，保留当前状态和必要索引；不堆积轮次汇报 |
| 正式区五阶段主文与专题 | 当前需求、模型、架构、原型与交互／设计规范及交付结论和成立条件；按主题维护唯一规范定义 |
| 正式区独立故事或任务系统 | 单故事目标、详细行为、AC、研发测试任务及依赖；总览只维护批次及索引 |
| 辅助区决策／来源 | 有效选择、假设、待决及确认依据，历史替代可追溯 |
| 辅助区交接／变更 | 恢复工作、变化及下游处理；不替代规范正文 |
| 辅助区验证／附件／草稿／归档 | 证据、图源及附属文件、未整合中间材料和确需保留的旧材料，分别管理生命周期 |

小项目可合并阶段章节；本地故事仍按 [第五阶段保存规则](../stages/delivery.md#保存与任务落地) 独立维护，已有满足深度的单故事场景可复用。共享定义不重复复制。旧编号、旧文件名和已有配置按内容及有效版本识别，不因升级技能自动迁移整个项目；授权整理时同步实际位置和引用。

## 需求基线

基线是当前有效的业务结论集合，可以分布在上述文件中。按本轮需要记录：
目标及成功标准、用户与场景、范围和优先级、业务概念和规则、状态及协作关系、外部依赖、质量要求、验收案例，以及事实／假设／待决事项。

核心需求不使用特定模型的字段作为必填项。技术约束如确实存在，应记录来源和约束性质；它们不是凭空排除业务需求的理由。

概要与细化按 [通用分析规格](analysis-spec.md) 判断维度覆盖，需求进入设计时使用 [设计输入与追溯](design-input.md)。有效需求定义是业务依据，设计是带版本的承载方案；已有实现是现状证据。三者冲突要定位并处理，不能用任意一层的“唯一真相”覆盖其余层。

建模方法与技术方案分别记录选择、状态（候选／评估中／已选择／已替换）和适用范围；“未选择”与“不需要额外建模”也都是有效结论。状态不用来替代业务确认或技术验证证据。

## 内容归属与当前正文

按 [内容性质与维护责任](document-structure.md#先判内容性质再判维护责任) 归并需求、模型、设计、故事、来源及证据；按 [从整体到局部](document-structure.md#从整体到局部) 组织主文、专题及必要子专题。正文表达当前对象及机制，来源和工作过程在独立记录中维护。跨组件的共同契约与各方责任分开，不能按讨论发生的位置归类。

## 图示与阅读说明

图的用途、层次、场景带读、保存及真实预览状态统一见 [图示辅助理解](document-structure.md#图示辅助理解)。第二、第三、第四阶段按实际设计范围交付所需模型／架构／原型视图；局部职责整理、比较或证据核对不因此扩大范围。

## 区分来源与确认状态

两个维度分别记录，不把“有出处”或“未被反对”当作“已确认”：

- 来源：用户明确陈述、指定文档（含路径／版本／章节）、现状观察、AI 推测。
- 状态：已确认、待验证假设、待决问题、已撤销／被替代。

用户的明确要求可以直接记为已确认，无须让用户再确认一次。未经确认的材料推导、AI 建议或默认值仍为假设。业务描述中事实与建议混杂时分开登记。

对话和材料先提炼为对象的行为、结果、机制与边界，等价整理不改变确认状态。来源原话及确认经过保存在独立来源／决策记录，正文通过 ID 或简短引用关联；遵循 [对象语言](document-structure.md#正文使用对象语言)，不把“用户提出”等会话转述写成规范句。原话用于访谈或歧义解释时仍保留其用途和依据，不复制到产品定义中。

影响范围、规则、架构或验收的条目使用稳定 ID，例如 `DEC-001`、`ASM-001`、`OPEN-001`、`REQ-001`、`SCN-001`、`US-001`、`AC-001`；不为每句话编号，不重用废弃 ID。

决策条目最小格式：

| ID | 内容 | 来源 | 状态 | 适用范围／影响 | 验证或解决方式 |
|---|---|---|---|---|---|

来源不足时明确写“依据不足”，不杜撰指标、访谈、预算、确认人或验证结果。历史方案保存在平台历史或辅助归档区，按需链接；恢复时优先读当前有效项，不在正式正文内设整段旧规范归档。

## 版本、完成标准与变更

需要保存的阶段产物记录状态、更新日期及采用的输入位置与可定位版本，阶段和已有修订标识按项目约定保留。对话或观察没有文档修订号时记录可定位来源，不虚构版本，也不为每次保存或对话自动分配一个需求基线号。正文不需要复制全部上游内容。

| 变化性质 | 正文与记录方式 |
|---|---|
| 措辞、结构、编号或引用等价整理 | 原位修改，保持需求／设计含义和确认状态，同步受影响图表及引用；使用编辑时间或平台历史，不强制发布基线 |
| 补充事实、解决未知，产品行为及设计不变 | 更新事实及问题状态；必要时记录澄清摘要，检查是否改变设计成立前提 |
| 能力、规则、范围或验收含义改变 | 已确定变化整合进有效正文，提议保留为候选；按变更主题归并变化范围、理由及影响，需要交接时固定可追溯修订 |
| 模型语义、结构、映射，架构责任、依赖或关键链路等设计改变 | 在对应设计维护修订与影响，即使需求未变也不能当作措辞整理；检查关联视图、兼容迁移及下游任务／证据，不因此自动发布新需求基线 |
| 任务进展或批次安排改变 | 更新对应状态、依赖与计划；完成判断保留实际证据。若改变承诺范围或验收含义，另处理相应需求／交付变更，不因进度更新给全部阶段升版 |
| 评审、交接或约定的基线发布 | 保存完整有效内容及其状态，按项目机制固定版本；不额外增加审批要求 |
| 样例、验证环境或实际结果变化 | 更新验证材料及证据版本；仅当改变产品结论或成立前提时传播到需求／设计 |

编辑历史、内容修订、需求基线和验证记录各有用途。已作为固定基线的标识不能继续用于指代改变后的内容；未发布基线的草稿交接可用平台修订、提交或更新时间与保存快照定位，不编造发布状态。同一变更可以跨多轮对话，也可在一轮内形成实质修订，以内容变化和交接需要决定记录粒度。

正文只保留必要的修订标识或简短摘要；变化过程放在辅助变更区，跨多个产物或需要持续跟踪时按 [变更分析](../changes/impact.md)复用独立记录。记录变化及理由、受影响的 ID／章节、替代关系、来源与决定状态、下游处理情况及历史位置，不在修订区再复制一遍完整需求。

- 草拟中：结构或内容仍在形成。
- 待关键决策：存在影响本阶段结论的未决问题。
- 可供下阶段使用：当前交付范围足够明确，关键阻塞已解决；可以携带不影响下一阶段的待办。
- 需复核：引用的上游结论已发生相关变化。

状态表示准备程度，不代表用户对所有内容作了确认。完成标准依项目和阶段判断，不追求所有未知清零；记录剩余未知为什么不阻塞下一步，以及何时必须解决。

阶段协作采用 [就绪检查](readiness.md) 的适用项及证据，不固定为单向流水线。第二、第三、第四阶段可以往返；第五阶段的规则细化和交付反馈可触发需求、模型、架构、原型或设计规范修订。复杂需求不能仅凭“主路径已写完”标记可用；小任务也不因没有全套图表而被阻塞。交接准备状态、原型走查、实现、测试及交付状态分别记录。

上游变更已确定时（提议尚在讨论时不覆盖有效基线）：
1. 修改对应主题中的有效结论，在变更记录／历史中保留被替代项、承接关系及理由；清理当前正文中的失效表述和已解决待决项。
2. 按引用关系找出受影响的场景、用户故事、架构、模型、验收及研发测试任务，标为“需复核”。
3. 更新概览和交接，明确哪些内容仍然有效。
4. 不自动重写所有下游文档，不假装已经完成复核。

## 每轮恢复与保存

恢复顺序：技能入口 → 本地或远端项目配置 → 配置指向的概览与交接 → 相关有效决策与关联任务 → 当前能力和必要输入章节。配置缺失时从用户已给出的位置和历史材料补建配置，不重建已有需求或任务；纯远端项目按实际页面／任务链接恢复，不要求本地文件先存在。发现版本不一致，先评估变化是否影响本轮，不让旧交接覆盖新文档。只读有效条目及其必要依据，不把历史备选方案整份带入。

持续分析或需要交接时，在辅助交接区保存足以独立恢复的信息，交接不进入正式正文目录；同时按 [更新与清理](document-structure.md#更新与清理) 处理已整合中间文件。临时问答只交付结果和必要后续说明，无需建立档案：

```text
分析对象与当前阶段：
本轮完成：
本轮产物及修订号：
当前有效决策：
仍未解决的问题及是否阻塞：
下一步任务及完成标准：
下一步必读路径／章节／修订号：
可按需读取的补充材料：
建模方法、技术方案、原型与交互设计、适用规范及状态：
```

交接摘要负责导航，不替代原始业务规则。规模增长时，把已关闭问题和废弃方案移至归档文件并保留链接，不在后续每轮重新加载。没有文件写入能力时，提供可复制的交接内容并明确尚未保存。

文件本身不会因对话压缩而改变，但不能假定其内容一直完整驻留上下文。方法不清楚时重读当前 reference；业务事实不清楚时读有效产物，不只依赖聊天摘要。宿主不能访问文件时明确限制。

## 对话与范围控制

开展探索、评审或方案取舍等讨论时，先组织讨论，再进入细节：

1. **先列目标与议程。** 利用已有信息说明本轮要解决的问题和预期结论，按目标列出待讨论项或推进步骤，依据依赖关系和优先级排序，标明当前先处理哪一项及其收敛条件。单一议题可用简短目标和一步安排表达；已有明确要求时直接推进，不增加清单确认环节。
2. **沿清单逐项推进。** 围绕当前项先给理解与可评审草稿，再处理最影响结论的缺口。多轮讨论复用清单，说明当前项的进展、结论或阻塞，不每轮重列完整议程；用户调整目标或范围时同步调整清单。
3. **按目标控制细节。** 只深入会影响当前目标、范围、关键结论或风险的细节；暂不影响这些内容的分支记入待后续处理的事项，回到当前项。必要的业务取舍不能以“以后再说”略过，缺少依据时保留相关未决项和结论的适用条件。
4. **逐项收敛。** 每项结束时明确已得结论、仍未解决的问题及其阻塞范围，以及下一项或下一步。达到收敛条件且没有新证据或目标变化时，不反复重开已解决细节；达到本轮目标后结束讨论。

先有范围和关键链路，逐步展开近期细节；技术命名、编号、格式和等价表达由 AI 完成，不让用户承担整理工作。

区分三类内容：

| 内容 | 处理方式 |
|---|---|
| 有效事实、明确要求或已授权决定 | 提炼并整合为有效定义，或执行已授权动作；保持来源、确认状态与适用范围，不重复确认 |
| 通用知识支持的候选或低影响表达选择 | 主动形成草稿；命名与整理可自主完成，新增字段或规则若改变行为则保留为建议，不因常见就视为项目事实 |
| 会改变业务结果的专属事实或取舍 | 先查已有材料；仍无依据时针对性提问或登记待决，相关结论保持条件性 |

判断是否必须补证，关注错误假设是否会改变业务行为、数据含义或交付结果。例如审批、删除与历史保留、失败后果、角色权限、金额口径及统计口径，不能仅凭行业惯例定案；仅在本轮相关且尚无有效依据时追问，不强制每个项目回答全部问题。

通常每轮聚焦 1～3 个相关问题，优先给可快速选择的答案及影响。有依据时逐题给建议和理由；无依据的企业事实直接说明需要什么信息，不为满足“每题必须推荐”而猜测。允许用户选择、修改建议或补充事实，不把建议、沉默或超时记作确认。

获得回复或验证结果后，更新对应有效定义、待决项及受影响引用，再继续相关工作，避免结论仅散落在聊天中。需保存时遵循本契约和项目配置；临时咨询更新对话中的草稿即可，不强制创建文件或发布远端文档。

把界面描述中的业务意图和体验约束提取出来：批量操作、排序含义、反馈、无障碍或离线要求不能一律丢弃。业务行为与状态归需求／模型，用户可见的流程、反馈、恢复以及原型验证归 [原型与交互设计](../stages/prototype-interaction.md)，颜色、布局和组件选择在项目有依据时收敛为设计规范；原型工具按项目上下文使用，不强制固定工具、控件或 UI 结构。

交付节奏遵循本轮请求：只分析一个场景或一个阶段时，到该范围完成即交接；已授权连续分析时可以继续。不因存在独立的待决事项停下全部分析，但依赖该事项的结论保持条件性。

用户只提出想法时，不把候选功能默认纳入范围。目标可通过流程调整、采购或更小改动实现时，应纳入比较。分析任务本身不授权开发、部署、发送消息、购买服务或改动业务系统配置；分析材料的维护配置按前述 `.project-context.json` 约定处理。
