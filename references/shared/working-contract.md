# 工作与交接契约

本契约由单一技能入口及其能力文件共用。它约定状态与交接，不规定所有项目都必须生成同样多的文档。下面的产物路径相对于分析材料目录；用户指定路径优先。技能文件自身的 references 路径始终相对于技能包，不与业务项目材料混用。

## 工作目录与最小材料

持续分析或需要落地任务／文档时，先按 [项目交付配置](project-context.md) 定位已有配置。有本地项目目录时默认读取根目录的 `项目上下文.md`；纯远端项目使用已授权项目页面的“项目上下文”章节或已有配置页，缺失则按模板在适用位置建立。临时问答无需创建或补齐配置。配置记录任务管理系统与文档维护目标、创建／更新规则及关联方式；不是分析进度文件。下面的文件名是未指定正式位置时的本地默认值，配置的实际位置优先。

未配置正式维护位置时可使用被分析项目的 `docs/project-analysis/` 保存本地草稿。指定 Notion／Confluence 后，按 [文档维护](../integrations/document-maintenance.md) 更新对应页面或章节，不再强制建立同名本地正式副本。各阶段写入文件的约定均受此配置覆盖。先确认被分析项目，不能把业务材料默认写到技能包里。临时问答不强制落盘；持续分析或需要交接时逐步保存。

本契约及各能力文件中的“写入／更新”要求仅在本轮确需保存且符合用户授权时执行；临时问答在对话中交付相同内容即可。按需要逐步建立，禁止启动时生成一批空文档。

新建产物统一使用能说明内容的中文文件名；阶段和条目可用数字编号，扩展名沿用实际格式。独立图源、图片、表格及其他导出文件也遵循此规则，例如 `系统架构图.mmd`、`系统架构图.svg`、`验收用例.xlsx`。文件名与正文中的稳定 ID 分开，`用户故事-001.md` 的故事仍可使用 `US-001`。用户指定名称时按其要求；已有文件按实际路径复用，需要改名时同步维护配置、索引、链接和任务引用。

信息、操作、规则、协作等共享定义优先用已有文档章节；确需拆分时按 [通用分析规格](analysis-spec.md) 组织到 `requirements/` 或配置的正式位置。设计交接索引和就绪检查也可内嵌到当前产物，不强制新增文件。

小项目可以合并需求、模型、架构等阶段文档，用章节索引交接；故事和任务按 [第四阶段保存规则](../stages/delivery.md#保存与任务落地) 维护：本地每故事独立文档，任务系统作为正式来源时维护系统正文及关联任务。已有独立场景文档满足相同深度时复用，不能以总表替代。共享定义只引用规范所在位置。

旧项目的 `02-feasibility.md`、`03-outline.md`、`05-delivery.md` 及已有场景文件继续有效，分别索引到第一阶段子方法或第四阶段即可。第二、第三阶段调换前的模型与架构文件也可沿用。恢复时按内容与有效版本识别用途，不根据旧编号推断新阶段，不强制改名、迁移或重建。

`项目上下文.md` 管“任务建到哪里、文档维护在哪里、按什么规则更新”；`项目概览.md` 管“当前项目要做什么、进行到哪”；`交接记录.md` 管“下次继续什么”。概览中的产物索引记录实际文档和任务关联及版本，不重复维护目标系统的配置。

## 需求基线

基线是当前有效的业务结论集合，可以分布在上述文件中。按本轮需要记录：
目标及成功标准、用户与场景、范围和优先级、业务概念和规则、状态及协作关系、外部依赖、质量要求、验收案例，以及事实／假设／待决事项。

核心需求不使用特定模型的字段作为必填项。技术约束如确实存在，应记录来源和约束性质；它们不是凭空排除业务需求的理由。

概要与细化按 [通用分析规格](analysis-spec.md) 判断维度覆盖，需求进入设计时使用 [设计输入与追溯](design-input.md)。有效需求定义是业务依据，设计是带版本的承载方案；已有实现是现状证据。三者冲突要定位并处理，不能用任意一层的“唯一真相”覆盖其余层。

建模方法与技术方案分别记录选择、状态（候选／评估中／已选择／已替换）和适用范围；“未选择”与“不需要额外建模”也都是有效结论。状态不用来替代业务确认或技术验证证据。

## 内容归属与当前正文

各阶段主体按当前用途组织有效结论，必要候选、假设和待决项明确标识。需求说明目标、场景、能力、行为与边界；模型说明概念语义、关系及规则承载；架构说明问题如何落实为分层、模块、技术、基础设施、协作和部署，并解释取舍；交付说明用户结果、故事、验收及执行安排。每项定义有一个维护位置，概览、专题和下游通过摘要及引用关联；主文档及必要规范引用应足以理解本轮结果，不能只剩索引，也不要求读者通过聊天、历史、样例或运行日志拼出当前结论。

表格、图或契约本身足以表达本轮语义与关联时可以直接使用，不强制改为长篇叙述或补齐其他阶段。阶段整理以内容充分性判断完成；本地故事须独立维护，但拆成文件本身不证明达到交接深度，不要求固定标题或段落数。

| 内容 | 维护责任与位置 |
|---|---|
| 产品问题、目标、用户场景、能力、范围、成功判据及明确约束 | 当前需求正文；具体表达深度由本轮用途决定 |
| 来源、确认依据、关键取舍和未决选择 | 条目元数据、来源索引或决策记录，关联需求 ID／位置；正文保留必要状态与条件 |
| 组件、算法、schema、存储和执行配置等承载方案 | 架构、模型或专项设计，引用所支撑的需求；明确的技术约束仍留需求 |
| 样例领域对象、字段、接口绑定、账号类别与测试数据 | 样例分析或验证方案，标明适用对象；通用设计可引用例子，但不能依赖该例子才有定义。产品本身的领域概念和已纳入范围的外部契约仍属于正式需求／设计，不能因其具体而移走 |
| 用户故事、验收条件、研发测试任务与批次 | 故事与任务以任务系统或本地独立故事文档为唯一正式来源，总览维护索引、批次与跨故事依赖；引用需求及设计，测试用例展开具体输入和步骤，执行结果另行关联 |
| 环境、快照、执行过程、实际结果和限制 | 验证报告及材料，关联被检验的需求或假设；不代替产品定义 |
| 被替代结论、变化理由、修订范围及下游处理状态 | 修订摘要、变更记录或历史归档，保留追溯关系，与当前规范分隔 |

这些是内容职责，除本地按故事独立维护外，不要求逐项新增文件。共享需求与设计可用章节，复用已有来源、验证和变更材料。需求中的成功判据和验证问题可以留在正文，具体样例与执行细节不承担通用需求定义。样例产生的新能力建议仍须经目标和范围判断，不能直接成为承诺。

新结论整合到对应主题，同时消解被替代表述、重复定义、旧范围与已解决问题；不要用“本轮补充”不断覆盖旧正文，或要求读者按修订先后判断哪条有效。保留历史不表示把完整旧规范并列在阅读主线中。原有文档需大幅重组且缺少版本历史时，先保存可恢复快照；保留无关内容及其他人的有效修改，不每轮复制整套文档。

## 图示与阅读说明

第二阶段的模型设计与第三阶段的架构设计用图辅助理解，具体视图分别遵循 [模型图输出](../stages/modeling.md#模型图输出) 和 [架构图输出](../stages/architecture.md#架构图输出)。图覆盖本轮范围；已有图适用时复用并更新，不因每轮对话重复新增图。

- **先说明图要回答什么。** 图题或相邻说明标明对象、范围及现状／目标／候选状态。沿用正文术语，连线标明关系或交互含义；箭头、基数及特殊样式需要时附图例，不能只靠颜色区分含义。未知关系及约束保持待确认。
- **结合场景带读。** 图后用简短文字沿一个代表性场景解释涉及哪些对象或组件、关系如何使用、变化或数据如何传递，以及关键规则和失败边界。图中元素关联正文定义或稳定 ID，具体规则引用其维护位置；图不能代替语义、取舍或验证证据。
- **保持可读。** 总览先呈现主要边界与关系，字段、分支或连线过多时拆成局部图，并保留与总览的对应关系。视图类型按问题选择，不为凑齐图种添加设计或引入基础设施。
- **格式与展示。** 默认在对应文档或对话中嵌入 Mermaid 图，保留可编辑图源；用户或项目指定格式时沿用。交付到不支持 Mermaid 的位置时，优先使用该位置支持的原生图或由可用工具导出的 SVG／PNG，并关联图源。工具受限时明确只提供了图源或尚不能展示预览，不把原始代码块描述成已展示的图。
- **保存与核对。** 需要保存时按项目配置嵌入正文或引用独立图源及图片，无约定可放 `design/`，使用中文文件名。检查语法、方向、基数和图文一致性；有渲染条件时预览，确认文字可读、关系可辨。没有渲染条件时说明未预览，不宣称渲染检查通过。定义变更时同步相关图及带读说明。

## 区分来源与确认状态

两个维度分别记录，不把“有出处”或“未被反对”当作“已确认”：

- 来源：用户明确陈述、指定文档（含路径／版本／章节）、现状观察、AI 推测。
- 状态：已确认、待验证假设、待决问题、已撤销／被替代。

用户的明确要求可以直接记为已确认，无须让用户再确认一次。未经确认的材料推导、AI 建议或默认值仍为假设。业务描述中事实与建议混杂时分开登记。

对话和材料先提炼为产品结果与边界，再用简短来源引用保留依据；等价整理不改变确认状态。原话在解释歧义、决策理由或用户要求保存访谈时按需保留，标明用途，不默认复制完整聊天。“用户要求”等来源措辞可以使用，但不能代替需求定义或成为正文组织方式。

影响范围、规则、架构或验收的条目使用稳定 ID，例如 `DEC-001`、`ASM-001`、`OPEN-001`、`REQ-001`、`SCN-001`、`US-001`、`AC-001`；不为每句话编号，不重用废弃 ID。

决策条目最小格式：

| ID | 内容 | 来源 | 状态 | 适用范围／影响 | 验证或解决方式 |
|---|---|---|---|---|---|

来源不足时明确写“依据不足”，不杜撰指标、访谈、预算、确认人或验证结果。历史方案放在与当前正文分隔的归档章节、平台历史或文件中，按需链接；恢复时优先读当前有效项。

## 版本、完成标准与变更

需要保存的阶段产物记录状态、更新日期及采用的输入位置与可定位版本，阶段和已有修订标识按项目约定保留。对话或观察没有文档修订号时记录可定位来源，不虚构版本，也不为每次保存或对话自动分配一个需求基线号。正文不需要复制全部上游内容。

| 变化性质 | 正文与记录方式 |
|---|---|
| 措辞、结构、编号或引用等价整理 | 原位修改，保持需求／设计含义和确认状态，同步受影响图表及引用；使用编辑时间或平台历史，不强制发布基线 |
| 补充事实、解决未知，产品行为及设计不变 | 更新事实及问题状态；必要时记录澄清摘要，检查是否改变设计成立前提 |
| 能力、规则、范围或验收含义改变 | 已确定变化整合进有效正文，提议保留为候选；按变更主题归并变化范围、理由及影响，需要交接时固定可追溯修订 |
| 模型语义、结构、映射，架构责任、依赖或关键链路等设计改变 | 在对应设计维护修订与影响，即使需求未变也不能当作措辞整理；检查关联视图、兼容迁移及下游任务／证据，不因此自动发布新需求基线 |
| 任务进展或批次安排改变 | 更新对应状态、依赖与计划；完成判断保留实际证据。若改变承诺范围或验收含义，另处理相应需求／交付变更，不因进度更新给全部阶段升版 |
| 评审、交接或约定的基线发布 | 保存完整有效内容及其状态，按项目机制固定版本；不额外增加审批要求 |
| 样例、验证环境或实际结果变化 | 更新验证材料及证据版本；仅当改变产品结论或成立前提时传播到需求／设计 |

编辑历史、内容修订、需求基线和验证记录各有用途。已作为固定基线的标识不能继续用于指代改变后的内容；未发布基线的草稿交接可用平台修订、提交或更新时间与保存快照定位，不编造发布状态。同一变更可以跨多轮对话，也可在一轮内形成实质修订，以内容变化和交接需要决定记录粒度。

局部变化在文末保持简短修订摘要；跨多个产物或需要持续跟踪时按 [变更分析](../changes/impact.md)复用独立记录。记录变化及理由、受影响的 ID／章节、替代关系、来源与决定状态、下游处理情况及历史位置，不在修订区再复制一遍完整需求。

- 草拟中：结构或内容仍在形成。
- 待关键决策：存在影响本阶段结论的未决问题。
- 可供下阶段使用：当前交付范围足够明确，关键阻塞已解决；可以携带不影响下一阶段的待办。
- 需复核：引用的上游结论已发生相关变化。

状态表示准备程度，不代表用户对所有内容作了确认。完成标准依项目和阶段判断，不追求所有未知清零；记录剩余未知为什么不阻塞下一步，以及何时必须解决。

阶段协作采用 [就绪检查](readiness.md) 的适用项及证据，不固定为单向流水线。第二、第三阶段可以往返；第四阶段的规则细化和交付反馈可触发设计修订。复杂需求不能仅凭“主路径已写完”标记可用；小任务也不因没有全套图表而被阻塞。交接准备状态与实现、测试及交付状态分别记录。

上游变更已确定时（提议尚在讨论时不覆盖有效基线）：
1. 修改对应主题中的有效结论，在变更记录／历史中保留被替代项、承接关系及理由；清理当前正文中的失效表述和已解决待决项。
2. 按引用关系找出受影响的场景、用户故事、架构、模型、验收及研发测试任务，标为“需复核”。
3. 更新概览和交接，明确哪些内容仍然有效。
4. 不自动重写所有下游文档，不假装已经完成复核。

## 每轮恢复与保存

恢复顺序：技能入口 → 本地或远端项目配置 → 配置指向的概览与交接 → 相关有效决策与关联任务 → 当前能力和必要输入章节。配置缺失时从用户已给出的位置和历史材料补建配置，不重建已有需求或任务；纯远端项目按实际页面／任务链接恢复，不要求本地文件先存在。发现版本不一致，先评估变化是否影响本轮，不让旧交接覆盖新文档。只读有效条目及其必要依据，不把历史备选方案整份带入。

持续分析或需要交接时，结束前按配置保存足以独立恢复的信息；临时问答只交付本轮结果和必要的后续说明，无需逐项建立交接档案：

```text
分析对象与当前阶段：
本轮完成：
本轮产物及修订号：
当前有效决策：
仍未解决的问题及是否阻塞：
下一步任务及完成标准：
下一步必读路径／章节／修订号：
可按需读取的补充材料：
建模方法与技术方案、对应适配器及状态：
```

交接摘要负责导航，不替代原始业务规则。规模增长时，把已关闭问题和废弃方案移至归档文件并保留链接，不在后续每轮重新加载。没有文件写入能力时，提供可复制的交接内容并明确尚未保存。

文件本身不会因对话压缩而改变，但不能假定其内容一直完整驻留上下文。方法不清楚时重读当前 reference；业务事实不清楚时读有效产物，不只依赖聊天摘要。宿主不能访问文件时明确限制。

## 对话与范围控制

先利用已有信息给出本轮理解与可评审草稿，再处理最影响推进的缺口。先有范围和关键链路，逐步展开近期细节；技术命名、编号、格式和等价表达由 AI 完成，不让用户承担整理工作。

区分三类内容：

| 内容 | 处理方式 |
|---|---|
| 有效事实、明确要求或已授权决定 | 提炼并整合为有效定义，或执行已授权动作；保持来源、确认状态与适用范围，不重复确认 |
| 通用知识支持的候选或低影响表达选择 | 主动形成草稿；命名与整理可自主完成，新增字段或规则若改变行为则保留为建议，不因常见就视为项目事实 |
| 会改变业务结果的专属事实或取舍 | 先查已有材料；仍无依据时针对性提问或登记待决，相关结论保持条件性 |

判断是否必须补证，关注错误假设是否会改变业务行为、数据含义或交付结果。例如审批、删除与历史保留、失败后果、角色权限、金额口径及统计口径，不能仅凭行业惯例定案；仅在本轮相关且尚无有效依据时追问，不强制每个项目回答全部问题。

通常每轮聚焦 1～3 个相关问题，优先给可快速选择的答案及影响。有依据时逐题给建议和理由；无依据的企业事实直接说明需要什么信息，不为满足“每题必须推荐”而猜测。允许用户选择、修改建议或补充事实，不把建议、沉默或超时记作确认。

获得回复或验证结果后，更新对应有效定义、待决项及受影响引用，再继续相关工作，避免结论仅散落在聊天中。需保存时遵循本契约和项目配置；临时咨询更新对话中的草稿即可，不强制创建文件或发布远端文档。

把界面描述中的业务意图和体验约束提取出来：批量操作、排序含义、反馈、无障碍或离线要求不能一律丢弃。颜色、布局等表现选择可单列；原型仅在本轮需要且符合授权时使用，不强制图型、控件或固定 UI 结构。

交付节奏遵循本轮请求：只分析一个场景或一个阶段时，到该范围完成即交接；已授权连续分析时可以继续。不因存在独立的待决事项停下全部分析，但依赖该事项的结论保持条件性。

用户只提出想法时，不把候选功能默认纳入范围。目标可通过流程调整、采购或更小改动实现时，应纳入比较。分析任务本身不授权开发、部署、发送消息、购买服务或改动业务系统配置；分析材料的维护配置按前述 `项目上下文.md` 约定处理。
