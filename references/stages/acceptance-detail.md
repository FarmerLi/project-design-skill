# 行为与验收细化

本文件用于 Issue 或复杂故事的行为与验收细化，也可独立处理用户指定故事／AC。最低输入为场景、预期结果、范围及约束；需要精确表达时查 [分析规格](../shared/analysis-spec.md) 的相关维度。

## 工作单元

拆分与细化前，先按 [本期需求边界决议](issue-delivery.md#开始前先决议本期需求边界) 明确本期业务范围，再选择当前需求或场景，按交付结果细化。需求边界决议不预先固定故事清单或数量。用户直接指定一个边界明确的场景或故事时即复用该边界，不要求先补全项目范围；仅给出宽泛目标时先交付需求边界建议。

每轮聚焦一个场景或一组紧密关联的场景，不加载所有场景文件。简单需求直接在执行 Issue 表达目标、行为与验收；跨流程或跨多个执行项的复杂需求按需保留故事／场景总览，不强制每项另建故事。先读概要中相关章节、当前场景涉及的有效决策和共享定义。沿用已有故事编号与格式；新故事可用 `US-xxx`，角色可以是业务用户或真实调用方，不为了句式虚构人物。

故事描述角色在具体情境下要取得的结果和价值，例如“作为……，在……时，我希望……，以便……”。句式可调整，但不能只有功能名称或一句愿望。场景承载过程，故事承载可交付价值，任务承载执行安排；它们可以一对多或多对多，不强制一场景一故事。

按实际复杂度探索：

1. 谁在何时因为什么触发任务，进入条件和输入是什么。
2. 正常步骤、输出与可观察结果。
3. 业务规则、口径与限制；同一规则只维护一个定义，其他位置引用。
4. 相关信息和状态如何变化，是否影响其他模块或外部系统。
5. 权限与数据可见范围；有审批时区分操作权限和审批决策。
6. 有意义的失败、重复、取消、撤回、修改、部分完成等路径。
7. 与当前场景相关的体验或质量要求。
8. 可具体判断通过或失败的验收案例。

不机械问完所有问题。简单功能可以简述；审批、金额、跨系统协作等高影响场景再展开。不自动增加报表、审批或 AI 功能。

## 逐步收敛

先从已有材料形成可评审草稿，按信息依赖补足：共同术语与信息 → 操作与规则 → 协作及失败后果 → 查询、权限、质量和验收。该顺序用于发现依赖，不是固定访谈轮次；已有明确定义直接引用。

涉及跨对象或系统的连锁后果时，按 [协作与影响链](../shared/cross-boundary-analysis.md) 检查失败和反向路径。简单本对象变化直接说明效果，不默认生成逐操作影响记录。

存在共享信息时补关系与历史策略，有生命周期时补迁移条件，有查询时补粒度与口径，有外部交接时补契约。各维度的展开程度由下游是否仍需猜测关键业务决定；不以文档篇幅或表格数量作为完成标准。

每轮把明确回复更新到规范定义及待决记录，再修正关联视图。已回答的问题不重复问；未回答的高影响问题保留条件性结论，只暂停依赖它的部分。

将回复提炼为已有故事、规则和 AC 的当前定义，合并重复、消解失效条件，不按对话次数追加故事或新建验收清单。等价整理沿用稳定 ID 和确认状态；行为或验收含义改变时，记录替代关系及设计、任务、旧测试结果的影响，按 [版本约定](../shared/working-contract.md#版本完成标准与变更)维护，未复核项不冒充已适配。

## 中立表达

跨功能影响先问业务后果和时效要求。例如“收款成立后，汇总更新失败是否影响收款成立，多久必须恢复”，不要先要求同步调用、同一事务或事件队列。

界面描述可能携带真实需求。批量处理、错误反馈、无障碍、离线等有业务价值的交互约束先进入需求或 [交互与 UI 设计](interaction.md)，故事和 AC 引用其有效定义；颜色和布局偏好可由该阶段的设计规范承接，不简单丢弃全部 UI 信息，也不在本阶段重做页面设计。

需要详细设计时，依据问题进入 [交互与 UI 设计](interaction.md)、[架构验证](architecture.md) 或 [模型设计](modeling.md)，直接复用已选方法与技术约束。模块、接口、表结构、模型编号、交互与 UI 设计规范写入设计产物，引用场景、故事及需求 ID。已有设计直接关联，不重新选择方法。

## 故事正文与最小产物

故事先解释结果与价值、边界，再沿主流程与关键异常展开规则、状态和验收，之后关联设计、执行任务及阻塞。复杂且可独立复用的细节进入相应专题，专题沿用 [整体到局部的组织原则](../shared/document-structure.md#从整体到局部)，不以来源转述、确认顺序或任务表代替故事主线。

Issue 或故事及其必要引用应提供以下适用内容；按 [第五阶段维护规则](issue-delivery.md#保存与任务落地) 确定归属。长期规则与场景归需求／设计正文，执行详情归唯一任务来源；本地文件或章节可作等价来源，已有充分的场景文档原位复用，不以文件数量判断交接深度：

- 关联需求／场景、角色、业务价值、触发与前置条件，以及本次包含与排除的范围；已有稳定 ID 继续复用，需要跨项引用时再增加。
- 正常路径、结果、关键规则与相关信息；
- 必要的异常／恢复路径、协作影响、权限与质量要求；
- 验收条件：给定条件、动作、可观察结果及必要验证方式；已有 AC ID 与有效规则引用继续保留，固定版本交接时标明输入修订。
- 影响当前行为的依据、建议与未决问题，必要设计引用、依赖和阻塞。
- 完整研发交接时，按[Issue目标表达与内容标准](issue-delivery.md#issue-规范入口与目标表达)明确交付结果、范围、输入输出、依赖、强制约束及验证方式，代表场景说明必要环境、操作和预期；具体实现方案和测试清单在执行阶段细化，不把代码动作作为需求，也不提前固定普通实现选择。无需分别建立 DEV／TEST 条目；故事总览只引用任务，状态与 PR 在任务来源维护。仅细化故事时保留后续执行入口，不伪造已创建任务。

共享规则在原主题或公共章节维护，故事保留自己的行为与可判断 AC 并具体引用。覆盖关系多且不易掌握时再用 [追溯方法](../shared/design-traceability.md)，不默认输出全维度覆盖表。

用于研发交接的执行 Issue 或等价条目必须在正文说明本次目的、目标需求、关键行为及验收；引用标明所用设计版本、具体章节和用途，不能只有整篇文档链接。大故事可拆成子故事并保留父项及原 ID，拆分后的每项都有自己的结果和验收边界；不按技术层次机械拆故事，也不将共享基础任务在每个故事中重复创建。

案例要覆盖重要边界而非只重复功能名称。例如“重复提交同一请求不产生第二笔业务记录”比“支持幂等”更便于确认和验收，但是否需要此规则必须有场景依据。

## 可验证的验收条件

使用 `给定条件 → 执行动作 → 可观察结果`，可采用 Given / When / Then，不强制英文或工具语法。结果应包括相关输出、状态变化、拒绝原因及不应发生的副作用；“正常工作”“体验良好”不能单独作为通过标准。

按实际风险覆盖主路径、重要边界、权限拒绝、失败恢复及质量要求。质量条件记录负载、环境、指标口径和目标来源；数值未定时登记缺口，不填默认阈值。长期业务验收定义持续成立的业务结果；Issue AC 将其落实到本次切片，记录覆盖或未覆盖的部分，不重复另一份完整规范。多个 Issue 可以共同覆盖一项业务验收，单项通过不代表整个场景已验收。测试用例将 AC 展开为具体数据、步骤和预期；两者不要求一对一，测试可按风险补充回归用例。

AC 来自有效需求和规则，不能由演示账号或一次响应倒推。具体用例可以就近表达，脚本、运行输出和证据沿测试或实验已有位置引用；保留业务本就限定的角色、字段、阈值和实际契约，不因归类丢失必要条件。

| 验收条件（已有 ID 可沿用） | 必要规则引用 | 给定条件与输入 | 动作 | 可观察结果 | 验证方法／环境 |
|---|---|---|---|---|---|

按实际用途说明未决条件和执行结果；普通故事无需维护多套状态列。未执行测试不写为通过，真实结果需对应所测版本和范围。

一个 AC 包含不同结果时写清各结果的触发条件，不以“失败或部分成功”等未分情况的选择代替判据。交接场景至少明确前置状态／代表性输入、操作、预期输出与必要副作用、验证方式；测试脚本可以后续编写，业务行为及通过标准必须在交接前确定。

## 完成与回退

分别判断本轮产出与下游准备程度：

- **故事细化完成：** 本轮故事的意图、范围、关键业务规则、主路径与重要异常有依据，验收条件可判断。仅请求故事与验收条件时，到此即可完成；未开展的架构、模型或任务拆分记为后续工作，不为完成故事细化自动展开。会改变预期行为或验收结果的业务未决项仍阻塞相关部分，不能只登记缺口就宣称细化完成。
- **可交付研发和测试：** 在故事细化基础上，执行项及必要设计引用足以判断成功并形成实施与测试计划，按 [第五阶段的交接标准](issue-delivery.md#两类完成判断) 判断；不要求建单时先填实施安排和具体测试清单。必要交互或 UI 设计缺失可能阻塞研发测试交接，但不倒推为已明确的故事与验收条件尚未完成。

未执行测试时只称“验收条件／案例已定义”；两类判断都不代表实际交付完成。

发现概要遗漏核心用户或闭环、价值假设不成立时，带着具体证据回交第一阶段；交互、架构或模型冲突回交对应设计，局部规则缺口在本阶段解决。任务拆分、批次和实际交付跟进见 [第五阶段主方法](issue-delivery.md)，不将故事细化完成当成已完成交付。
回读本轮规则、关键场景与验收，确认判据可观察且重要分支有依据。正式研发交接时按需使用 [就绪检查](../shared/readiness.md)；保存优先更新当前主题或任务，附加交接与报告按实际需要增加。
