# 技术架构探索与验证

## 阶段目标与输入

依据需求与实际约束，形成可据以实现系统的技术方案：明确系统如何分层，有哪些模块、组件和基础设施，采用什么技术，如何组织运行、协作和部署，以及这些选择怎样解决需求提出的问题。阶段结束时，技术层应能承接后续交互与 UI 设计及实现拆分，无需重新决定系统基本结构和核心技术路线。通过查证、推演或最小 demo 验证影响方案成立的技术假设；设计完成、已实现和运行验证分别报告。

本轮仅要求技术比较、现状解释、概念讨论或局部验证时，按实际范围交付。完成这类局部任务不等于系统实现方案已经完成；关键实现选择尚未收敛时保留架构草案及阻塞范围。

最低输入为本轮需求或用户结果、相关约束及已知环境。复用相关模型的边界、规则与一致性要求，无需先完成完整需求或模型；缺口保留条件。跨人或复杂交接时按需使用 [输入与追溯](../shared/design-traceability.md)。

## 工作方法

1. **确定设计范围与证据。** 从相关文档、依赖版本和关键实现入口识别已有环境、外部契约与限制，遵守仓库探索预算。既有项目先解释相关实现与复用能力，再确定改造边界；没有应用代码也要形成明确的待实现方案，不虚构已存在的模块、接口或运行能力。
2. **从问题推导解决机制。** 关联核心场景、领域与逻辑模型中的责任边界和一致性要求，以及规模、时效、可靠性、安全、环境、团队和成本条件。先解释每个主要问题通过什么机制解决，再将机制落实到分层、模块及技术；只展开会改变选择的因素，目标数值必须有来源。
3. **收敛技术路径。** 尚未选定时读取 [技术选型](../selection/technology.md)；已明确沿用时，直接依据实际版本、现有模块和契约定位复用、改动及兼容边界。比较有实质差异的复用、扩展、自研或替换方案，选定主方案并解释收益、复杂度和代价，已定选择不无故重开。具体版本能力、维护状态或费用使用实际版本及必要的当前官方来源核实。
4. **落实实现方案。** 按下表明确分层、模块组件、运行单元、基础设施、技术及接口与数据协作，并输出相应视图。沿关键场景逐步检查输入输出、正常、失败与恢复路径；同步、异步和事务边界由业务后果与时效决定。仅比较或验证局部链路时，只展开支撑该决定的设计与证据。
5. **验证关键假设。** 优先复用有效证据；证据不足且影响选择时，按下方契约组织最小 demo。只比较方案时可交付验证计划；要求制作 demo 或执行技术验证时，完成授权范围内的实现、运行和结果记录，不停在建议清单。
6. **反馈与收敛。** 依据结果更新选择、协作和部署方案。模型的一致性、关系和读写需求会影响架构，必要时与 [模型设计](modeling.md) 往返；无法满足有效需求时返回具体取舍，不静默降低目标。影响系统结构、核心技术、执行或部署方式的未决项未关闭时，不判相应范围的实现方案完成。

## 系统实现方案

本轮要求完整系统实施方案时落实下列内容；探索或局部模块设计只展开影响当前决定的部分，可逆且不影响当前工作的选择可以后置。选择要关联需求／约束、解决目的和代价。

| 设计内容 | 实现所需说明 |
|---|---|
| 分层与边界 | 按系统实际划分各层的责任、依赖方向与跨层规则，说明业务规则和技术实现的归属；不套用固定层数或只给“表现／业务／数据层”等空泛名称 |
| 模块与组件 | 各层包含什么模块、组件，承担什么能力，提供什么接口，维护什么数据，依赖谁；区分逻辑职责、复用组件和实际运行单元 |
| 技术与实现方式 | 为相关前后端、核心处理、存储和集成选择语言、框架、核心库、协议或产品，说明落在哪个模块、如何接入、为何适合；明确复用／配置／扩展／自研范围及成本 |
| 基础设施 | 按实际需要确定数据库、文件存储、任务／消息机制、缓存、网关、身份服务、日志监控等的采用、复用或暂不引入及理由；说明使用者、保存内容和运行责任，不为填表引入设施 |
| 接口与数据协作 | 明确跨模块调用或事件的生产者／消费者、用途、主要输入输出与错误，数据的权威归属和读写路径，以及相关同步／异步、事务、一致性、权限和重试边界 |
| 运行与部署 | 将模块和组件映射到进程／服务／后台任务及目标主机或运行环境，说明合并／拆分依据、基础设施连接、隔离、配置与秘密引用、持久化及启动依赖；落实本轮需要的资源、观测和恢复安排 |
| 实现路径 | 说明先搭建哪些基础能力、再打通哪些场景、后续扩展的依赖和必要迁移；用户流程与交互状态交给第四阶段，故事、任务与 AC 交给第五阶段，不把核心技术或服务组织方式留给研发临时决定 |

跨模块接口和数据契约应足以安排独立实现与对接。逐字段规格和内部类函数设计可继续细化，但影响调用、状态、权限、一致性或失败后果的决定必须明确。单进程、无持久化或不需要独立基础设施时直接说明，不默认微服务、消息队列或数据库。

完整实施交接应收敛影响当前实现的核心技术、模块及运行部署选择。尚未收敛时说明限制，可继续无依赖工作；探索、比较或验证可以按自身用途完成，不以完整实施交接的标准扩大范围。

## 架构正文与专题组织

- **建立需求到实现的关联。** 将输入整理为“需求问题／约束 → 解决机制 → 承载模块与协作 → 技术及基础设施选择 → 效果与验证”。对话中的技术建议按实际决定状态处理，不直接成为组件要求；已有明确技术约束保留其来源和效力。解释为何这样组织、需要承担什么代价，以及如何观察需求得到满足。
- **先整体后展开。** 主文先说明整体解决思路、系统边界和主方案，再沿场景解释结构、协作及技术。组件、协议与流程由对应专题展开；专题也先说明自身责任、主要组成及与整体的关系，再进入接口、数据、算法和配置。过深且有独立维护责任时继续拆子专题，主文保留概貌和入口，不复制全部细节。局部任务只维护必要上下文，遵循 [从整体到局部](../shared/document-structure.md#从整体到局部)。
- **按责任归属。** 内部机制归组件，公共契约在合适的公共章节维护，各方保留本方交接与失败责任。技术选择融入实际方案，关键理由可就近说明；无恢复价值的工具和讨论过程无需保存。
- **分开设计与实验。** 实际集成契约进入对应设计；样例接口、测试账号、硬编码绑定、替身及为缩小实验而省略的机制放在验证材料，标明能检验的环节。若这些安排拟用于正式方案，另说明适用依据和限制；绕过明确执行或安全约束的实验不能证明约束已满足，也不能静默改写目标方案。
- **整合反馈。** 新证据先判断改变的是实验记录、设计成立条件还是设计本身，再更新相关主题及图、责任、链路和模型引用。替代方案退到历史，已解决问题退出清单；仍成立的决定不无故重开。按 [版本约定](../shared/working-contract.md#版本完成标准与变更)记录实质设计变化，不以每次试验或对话新增一版方案。

验证的命题、结论、限制及其对设计的影响在正文中简述，环境快照、执行步骤、输出和测量记录通过证据引用关联。读者不应翻遍实验日志才能判断当前采用什么方案、为什么采用以及哪些条件尚未成立；计划、推演与实际运行保持各自状态。

## 架构图输出

本轮包含架构设计时，交付覆盖该范围的架构总览图及关键链路带读。完整系统实现方案须覆盖以下三种视角；简单系统可以合图，按可读性拆分，不强制固定图数或文件数。仅做技术比较、局部 demo 或验证结果核对时，按需要使用比较表、链路说明或局部图，不强制总览图，也不扩大任务范围。

| 视角 | 图要回答的问题 |
|---|---|
| 分层与模块结构 | 系统由哪些层和主要模块构成，职责、边界、依赖方向是什么，外部系统在哪里 |
| 关键运行链路 | 一次业务请求或任务如何经过模块协作完成，接口／事件及数据怎样传递，关键等待、失败和恢复在哪里发生 |
| 部署与基础设施 | 模块落在哪些进程／服务和环境上，采用的基础设施如何连接、持久化和隔离；单进程也明确其运行及外部依赖 |

- **保持视图层次。** 总览聚焦主要职责及协作，避免把功能模块、进程、底层库和内部校验步骤混作同一层节点。授权、模型调用、日志审计等共享支撑按职责概括，详细连接在相关视图展开。图题说明要回答的问题，各视图名称与映射一致，不靠删掉必要组件或基础设施简化设计。
- **表达关系。** 连线标明调用、事件或数据流的方向与含义；相关同步／异步、数据归属和信任边界应可辨识。顺序关系与依赖关系分别表达，不能把可独立触发的功能串成必经步骤。局部图通过名称或稳定 ID 与总览对应，不为凑齐图形虚构设施。
- **区分状态。** 既有项目区分现状与目标，标明复用、新增、改造和迁移边界；差异较大时分图展示。节点命名与正文、模型及实际实现保持一致，候选方案不画成已落地事实。
- **关键链路带读。** 选择能覆盖核心机制的场景，逐步说明入口、处理模块、主要输入输出、调用与读写、校验点和返回结果，关联重要失败／恢复路径及未决项。建模或编译类系统还要解释业务概念如何转成可执行表示及实际操作，不能用“自动处理／受控执行”跳过关键转换。
- **格式、展示与检查。** 遵循 [Mermaid 与 SVG 的选择](../shared/document-structure.md#mermaid-与-svg-的选择)，按整体概览与运行链路的表达用途选择格式，以读者能看懂组件如何支撑业务、沿链路理解协作为目标。保留权威图源，检查方向及图文一致性；有渲染条件时在实际展示尺寸检查文字、交叉连线与主路径可辨性，拥挤时按需拆图并补带读。没有渲染条件时说明未预览及展示限制，不把语法通过当作可读性通过。

## 最小 demo 与验证契约

围绕会影响决定的命题做实验，不要求每项技术各做一个演示或搭建完整应用。

| 内容 | 要求 |
|---|---|
| 命题与决定 | 说明验证什么、它影响哪个技术选择或需求范围 |
| 通过条件 | 执行前写明可观察成功／失败信号，区分硬约束、候选阈值与尚待确定的目标 |
| 环境与输入 | 记录版本、数据来源及规模、依赖是真实服务还是替身，说明样本代表性与限制 |
| 最小实现 | 仅覆盖待验证链路，保留运行入口和必要配置说明；已有合适验证可复用 |
| 运行证据 | 记录实际操作、观察结果、输出或测量及失败；区分未执行、通过、未通过、证据不足 |
| 决策影响 | 关联被支持或否定的技术／架构决定及需求，说明尚不能证明什么；失败时调整哪部分或转向什么备选，哪些实现工作被阻塞 |

明确的本地 demo 请求包含完成该验证所需的常规可逆工作，无需再按阶段索取确认；已有授权直接沿用。仅分析请求不扩大为应用开发；外部服务、生产操作和资源投入遵循实际授权与环境限制。遇到边界或工具限制时交付已有证据和具体缺口，不伪报运行成功。

新增依赖、项目准入要求或具体风险需要时，按 [核验深度](../selection/technology-admission.md#按使用范围确定核验深度) 补查相关项；复用项目环境的普通试验不默认增加专项审计或准入报告。

替身只证明被替代环节之外的行为，不能证明真实外部契约。小样本跑通不能证明容量、安全或生产可靠性；没有运行只能报告代码或设计已完成。demo 代码不默认成为生产实现。

## 最小产物

完整系统架构设计交付上述实现方案、覆盖结构／运行／部署的视图与带读，以及需求到实现的关联、验证结论或计划、未决项和受影响范围。既有项目说明复用、改造和迁移边界。局部模块设计、技术比较或验证按本轮范围交付，不补做全系统方案，也不将局部完成扩称为阶段整体完成。

正文解释问题、整体机制、关键协作及必要实现细节；完整实施方案再落实运行部署。组件专题按实际复杂度展开，不重复公共文档规范；关键选型理由就近说明，长比较和运行证据按需引用。

需要保存时更新原架构主题。demo、环境及原始结果在项目已有实验位置维护，正文引用结论与必要证据；没有位置时选本次最小合适位置即可，无需先建配置和辅助目录。其他材料遵循 [文档规则](../shared/document-structure.md)。

## 完成标准与交接

- 系统架构设计已形成可据以实施的主方案：分层、模块组件、运行单元、基础设施、技术选择、接口与数据协作及部署方式明确，技术层可据此承接交互与 UI 设计及后续实现拆分，关键决定未留作“后续选型”。
- 主要需求能沿“问题 → 机制 → 模块协作 → 技术及基础设施 → 可观察效果”得到解释；关键场景覆盖正常和重要失败／恢复路径，设计元素有需求或必要技术依据。
- 图覆盖本轮结构、关键运行及部署组织，图文一致，关键组件及关系清晰；需要保存时保留可编辑图源，渲染及可读性检查状态如实记录。局部任务按其范围判断所需视图。
- 核心选择与准入状态分开，有效证据、待验证项和影响明确。决定核心方案成立的技术假设未获支持、关键选型或准入缺口阻塞实施时，相应范围仍为条件性草案，阶段未完成；已清晰且无依赖的部分可以继续。
- 要求执行的验证已有实际结果；未执行或未完成的原因及影响明确，不以验证计划替代结果，也不以设计完成宣称系统实现或生产可用。
- 与相关模型及业务规则没有未解释的冲突；远期设计不阻塞已明确的切片。
- 当前正文与必要规范引用足以解释系统如何实现、组织工作及满足需求，无需读聊天、被替代方案或实验日志拼出方案；图、技术、职责、链路与部署一致，样例和实验简化未成为无依据的正式架构约束。

说明本轮设计结论、真实验证与可继续范围。正式实施交接时按需使用 [就绪检查](../shared/readiness.md)，将有关技术和验证结果反馈到模型及 [交互设计](interaction.md)；失败或证据不足的 demo 也是有效验证结果，不能据此将原方案判为可行。
