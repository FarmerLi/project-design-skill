# 技术架构探索与验证

## 阶段目标与输入

依据需求与实际约束选择技术路径，形成关键架构设计，并通过查证、推演或最小 demo 验证会影响方案成立的技术假设。既有项目先解释相关实现和可复用能力，再判断是否需要改造。

最低输入为本轮需求或用户结果、相关约束及已知环境。读取 [工作契约](../shared/working-contract.md) 和相关 [设计输入](../shared/design-input.md)。不要求完整需求或模型先行定稿；缺口保留条件，不默认选择技术栈或建模方法。

## 工作方法

1. **确定设计范围与证据。** 从相关文档、依赖版本和关键实现入口识别已有环境、外部契约与限制，遵守仓库探索预算。没有仓库时形成候选架构，不虚构模块、接口或运行能力。
2. **识别架构驱动因素。** 关联核心场景、数据规模、时效、可靠性、安全、运行环境、团队及成本条件。只展开会改变选择的因素；目标数值必须有来源。
3. **评估技术路径。** 尚未选定时读取 [技术选型](../selection/technology.md)；已明确沿用时直接读取 [技术适配](../adapters/technology.md)。比较复用、扩展或替换的收益、复杂度和迁移代价，已定选择不无故重开。具体版本能力、维护状态或费用使用实际版本及必要的当前官方来源核实。
4. **形成所需设计。** 本轮包含架构设计时，说明模块／服务责任、关键链路、接口与外部集成、数据归属、部署和运行条件，并按下方要求输出架构图。仅比较技术或验证局部链路时，只展开支撑该决定的设计与证据，不补做完整架构。沿相关场景检查正常、失败与恢复路径；同步、异步和事务边界由业务后果与时效决定，不按框架习惯直接填入。
5. **验证关键假设。** 优先复用有效证据；证据不足且影响选择时，按下方契约组织最小 demo。只比较方案时可交付验证计划；要求制作 demo 或执行技术验证时，完成授权范围内的实现、运行和结果记录，不停在建议清单。
6. **反馈与收敛。** 依据结果更新取舍及适用条件。模型的一致性、关系和读写需求会影响架构，必要时与 [模型设计](modeling.md) 往返；无法满足有效需求时返回具体取舍，不静默降低目标。

## 架构图输出

本轮包含架构设计时，至少交付一张覆盖该设计范围的架构总览图，与方案说明一起输出；职责表和链路描述用于补充图，不替代图。仅做技术比较、局部 demo 或验证结果核对时，按需要使用比较表、链路说明或局部图，不强制总览图，也不因进入本阶段而扩大任务范围。

- **表达范围。** 标明系统边界、主要模块／服务及职责、相关外部系统与数据存储。连线标明调用、事件或数据流的方向与含义；影响方案的同步／异步、数据归属和信任边界应可辨识。没有依据的组件或关系标为候选／待确认，不为凑齐图形虚构基础设施。
- **按需补图。** 总览图不足以解释关键交互时补充时序图；部署拓扑、网络隔离或容灾安排影响选择时补充部署图。按本轮决策需要选择视图，不强制绘制全部类型。
- **区分状态。** 既有项目区分现状与目标，标明复用、新增、改造和迁移边界；差异较大时分图展示。节点命名与正文、模型及实际实现保持一致，候选方案不画成已落地事实。
- **格式与保存。** 默认在架构文档中嵌入 Mermaid 代码块，保留可编辑图源；项目或用户指定其他格式时沿用其约定。独立图源及导出图片按项目配置保存，无约定可放 `design/` 并从架构文档引用。图附简短说明，解释关键链路、边界及未决项。
- **检查。** 检查图语法、连线方向及图文一致性；有渲染条件时预览确认可读性，无渲染条件时说明未预览。

## 最小 demo 与验证契约

围绕会影响决定的命题做实验，不要求每项技术各做一个演示或搭建完整应用。

| 内容 | 要求 |
|---|---|
| 命题与决定 | 说明验证什么、它影响哪个技术选择或需求范围 |
| 通过条件 | 执行前写明可观察成功／失败信号，区分硬约束、候选阈值与尚待确定的目标 |
| 环境与输入 | 记录版本、数据来源及规模、依赖是真实服务还是替身，说明样本代表性与限制 |
| 最小实现 | 仅覆盖待验证链路，保留运行入口和必要配置说明；已有合适验证可复用 |
| 运行证据 | 记录实际操作、观察结果、输出或测量及失败；区分未执行、通过、未通过、证据不足 |
| 决策影响 | 说明支持或否定了什么，尚不能证明什么，以及是否调整方案或追加必要验证 |

明确的本地 demo 请求包含完成该验证所需的常规可逆工作，无需再按阶段索取确认；已有授权直接沿用。仅分析请求不扩大为应用开发；外部服务、生产操作和资源投入遵循实际授权与环境限制。遇到边界或工具限制时交付已有证据和具体缺口，不伪报运行成功。

涉及第三方依赖时，按 [使用范围与核验深度](../selection/technology.md#按使用范围确定核验深度) 判断本次试验能否执行，复用仍适用的证据。实验准入与正式采用分开记录，不为一次隔离的本地 demo 补做无关生产审计。

替身只证明被替代环节之外的行为，不能证明真实外部契约。小样本跑通不能证明容量、安全或生产可靠性；没有运行只能报告代码或设计已完成。demo 代码不默认成为生产实现。

## 最小产物

按本轮请求交付相关技术取舍、需求／约束映射、验证记录或计划及限制、未决项与受影响范围。包含架构设计时另交付架构总览图、必要的补充视图、责任和关键链路；既有项目按相关性说明复用、改造和迁移边界。仅比较或局部验证时，交付对应结论与证据即可。

按项目配置保存；本地默认 `02-技术架构探索与验证.md`，详细设计可放 `design/`。需要保留 demo 时使用目标项目约定的实验目录；无约定可用 `experiments/`，记录路径、运行方法和证据，不把业务 demo 写入技能包。

## 完成标准与交接

- 相关技术取舍有依据，本轮所需责任、依赖、集成及运行条件足以支持当前决定。
- 包含架构设计时，总览图已交付，关键组件、系统边界与链路清晰，图文一致；需要保存时已按配置保留必要视图及可编辑图源。仅比较或局部验证时不以总览图作为完成条件。
- 当前范围的关键场景有承载落点或验证结论；无法满足的需求和缺口可定位，候选与已定选择分开。
- 要求执行的验证已有结果，或明确未完成的原因；决定方案成立的假设未获支持时，方案保持条件性。
- 与相关模型及业务规则没有未解释的冲突；远期设计不阻塞已明确的切片。

依据 [就绪检查](../shared/readiness.md) 分别报告架构设计完成情况、技术验证状态和可交付范围。交给模型设计或研发测试的内容引用实际输入版本；失败或证据不足的 demo 可以形成有效的验证结论，但不能据此将原方案判为可行。
