# 交付规划

读取 [工作契约](../shared/working-contract.md)。只读当前交付范围的概要、场景、相关设计和待决事项。

围绕可验证的用户结果切分批次。数据库、后端、前端工作可以作为实现任务，但不能替代业务交付目标；纯技术前置工作说明解锁哪个业务结果以及如何验证。

每批按需明确：

- 目标、包含场景及明确排除的范围；
- 依赖、关键风险和未决事项；
- 验收案例来源及准备程度；
- 必要的集成、迁移、上线与运行条件。

使用 [设计输入与追溯](../shared/design-input.md) 将批次关联到有效需求、相关设计和验收案例；没有设计需要时说明理由，不强制增加模型。按 [就绪检查](../shared/readiness.md) 区分“可以开始”“待业务决定”“待技术验证”及受影响范围。一个关键链路仍有未定失败后果时，不能仅因任务已拆完就宣布该链路可开发。

区分业务价值优先级和技术依赖顺序。团队产能未知时不承诺日期；估算说明依据、区间与不确定性，负责人只使用已知信息。

形成交付计划，使研发和测试能回答本批做什么、为什么做、依赖什么、如何判断完成、还有哪些阻塞。不要求所有远期场景都细化完毕。需要保存时按项目配置的正式文档位置维护；未配置时使用 `05-delivery.md` 的本地约定。只请求临时拆分建议时可直接在对话中交付。

用户要求将拆解建入 Jira 等系统，或已有明确持续落地约定时，读取 [任务落地](../integrations/task-tracking.md)，依据根目录 PROJECT_CONTEXT.md 创建或更新关联任务并记录实际 key／URL。只要求拆分建议时不直接创建远端任务。

如本轮涉及已确定需求或方案的改变，先读 [变更分析](../changes/impact.md)，然后按已确定的影响更新计划。交付规划不承载全流程变更规则。

“可进入开发”不等于已实现、测试通过或用户验收。任务创建完成也不等于任务已完成。开发、发布及状态更新遵循用户实际任务范围和已存在的授权。
