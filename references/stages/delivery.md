# 需求细化与交付推进

## 阶段目标与输入

将已明确的需求和设计整合为可供研发实现、测试验证的用户故事与验收条件，并据此组织任务、安排批次、跟踪结果和处理反馈。读者应能理解本批交付什么用户结果、如何验收、有哪些依赖以及实际进展；本阶段包括开发前准备与交付跟进，不以任务拆解或文档完成代替实际交付。

完整第五阶段的默认产物是当前范围的研发测试交接包：每个故事能够独立说明本次目标、具体工作和验证标准，研发无需再次拆解业务范围或猜测关键行为即可开展工作。批次表、故事摘要和任务目录只能作为总览。用户仅要求故事、拆分建议或进展核对时按指定深度交付，明确尚未完成的交接内容，不将部分成果标为完整第五阶段就绪。

最低输入为本轮场景、预期结果、范围和相关约束；已有需求、模型、架构及必要的[原型与交互设计成果](prototype-interaction.md)直接引用，跟进时补任务状态及实际实现／测试证据。读取 [工作契约](../shared/working-contract.md)，只读当前批次的相关材料，不要求补齐前四阶段文件。

## 开始前先决议本期需求边界

第五阶段开始前，先明确本期需要建立故事的需求边界：本期覆盖哪些业务目标、能力和场景，哪些需求暂缓或排除。依据有效需求与设计形成可评审的边界草案；此时不预先决定故事数量、清单、编号、拆分粒度或逐故事推进顺序。

需求边界草案说明：

- **本期目标与需求依据。** 说明本期要取得什么业务结果，关联有效需求、能力或场景，不把全部需求默认纳入本期。
- **覆盖与排除。** 明确本期哪些需求需要建立或完善故事，哪些暂缓、哪些排除，以及必要的角色、业务流程或能力边界。例如本期覆盖个人收藏与回看，分组和分享暂缓；具体拆成几个故事在边界决议后确定。
- **取舍与待决项。** 记录纳入或暂缓的理由、结论来源及状态；会改变本期需求覆盖范围的选择先收敛，其余问题注明影响和后续处理位置。

用户已明确本期需求边界、已有有效决议，或已委托在明确约束内选择时，复用或在委托内形成决议并继续，不重复确认。只有“完成第五阶段”等宽泛推进要求时，先给需求边界建议，集中处理必要取舍；决议未完成前，不进入故事拆分、详细 AC 或任务建立，沉默不代表采纳。直接指定一个边界明确的需求、场景或故事时，可简述已有边界后推进，不要求补全项目范围。仅请求本期范围建议时交付边界草案即可；仅核对已有进展时沿用有效边界，不重新决议。

需要持续维护时，将本期需求边界决议保存到现有决策记录或交付总览，互相引用。决议后随故事拆分维护推进清单、当前项、完成／受阻／待推进状态及下一项；恢复时先核对有效需求边界，再继续当前项。后续增减本期需求或改变覆盖边界时，先复核受影响的决议；仅调整边界内的故事拆分、数量或顺序，不重开需求边界决议。

## 围绕交付切片推进

本期需求边界决议完成后，在边界内选择当前需求或场景，按可独立交付的用户结果拆分故事，并逐项细化至本轮要求的深度。故事清单随拆分完善，不要求在边界决议时固定，也不强制一项需求只对应一个故事。一次推进一个故事或一组不可分的紧密关联故事，完成适用步骤后再处理下一项。每项结束说明结论、达到的深度、未决项及阻塞；当前项受阻时，记录后可转向无依赖的下一项，不把受阻项标为完成。已有连续推进授权时继续，无须每个故事另行确认。

1. **选择当前需求并拆分故事。** 按价值、风险和依赖，从本期需求边界内选取当前需求或场景，拆分可验收的用户结果，明确各故事边界与推进顺序；已有故事沿用 ID 和有效内容。数据库、后端、前端是实现任务，不代替业务结果；技术前置工作关联所解锁的故事或质量目标，定义自己的验证方式，不伪造用户角色。拆分若需引入本期边界外的需求，先返回需求边界决议，不静默扩张。
2. **形成用户故事与验收条件。** 使用 [用户故事与验收细化](detail.md) 补齐规则、状态、权限、异常及质量要求。一个场景可包含多个故事，一个故事可对应多个研发与测试任务。先有可讨论草稿，避免一次性细化全部远期需求。
3. **补齐必要设计。** 有用户操作面的故事必须关联已走查的可操作或可模拟执行原型，以及本轮适用的交互与设计规范；架构、模型、接口或直接实现说明用于补充技术承载，不能替代原型与相关规范。用户任务流程、页面／终端状态、反馈和视觉／组件规则引用 [原型与交互设计](prototype-interaction.md)，未决问题只阻塞相关故事。需要验证的技术问题返回 [架构验证](architecture.md)，语义与数据冲突返回 [模型设计](modeling.md)，局部业务规则在细化中解决。
4. **拆分研发与测试任务。** 按故事拆出实现、测试设计与执行、集成以及必要迁移任务。每项任务写清实施范围、输入／契约、输出、依赖、完成判据及证据；测试任务另写 AC 覆盖、必要数据／环境、验证步骤和预期。将仍需再次拆分才能实施的条目标为工作包，不冒充执行任务。共享技术任务只维护一份，由相关故事关联并说明解锁条件，不伪造用户角色。
5. **安排批次并检查就绪。** 每批明确用户结果、故事范围、交互与设计及外部依赖、验收来源、准备程度和阻塞。区分价值优先级与技术依赖顺序；无产能依据不承诺日期，无负责人信息不填人。必要交互或设计缺失不能被任务列表掩盖。
6. **跟进与反馈。** 请求推进或核对交付时，读取当前任务及实现、测试证据，核对完成与受阻部分。缺陷关联原故事和验收条件；需求或设计变化按 [变更分析](../changes/impact.md) 复核关联产物，更新剩余任务与计划。没有实际进展材料时只交付准备结果和待核实状态，不编造进展。

仅请求故事细化、批次建议或一次进展核对时，到对应范围结束；“交付推进”不自动创建长期监控、远端任务或部署应用。本期需求边界决议完成后沿用已有执行和同步授权，不追加阶段或逐项确认；写入授权本身不代表本期需求边界已经明确。

## 交付正文与故事组织

- **按结果归并。** 将跨轮输入中的角色、情境、规则和预期结果并入已有故事及其验收条件，不把每条聊天、接口或实现步骤各建一个故事。必要拆分依据独立价值、验收或依赖，保留原条目承接关系；任务与技术前置工作按执行责任组织，不取代故事的业务说明。
- **区分规范与用例。** 故事和 AC 定义范围内的行为与判据，测试用例将其展开为具体数据、步骤和预期，执行记录说明实际版本、环境与结果。样例中的业务角色、固定 ID、字段值和接口绑定只在确属交付范围时进入规范；教学或试点数据不自动成为产品限制。具体边界数值可以用于说明 AC，但测试通过不能反向定义或缩减故事范围。
- **维护同一计划。** 把新决定和进展整合到现有故事、AC、批次、依赖与任务映射。交付正文说明用户结果及其承接关系，任务清单和证据索引用于追溯；讨论过程、每日汇报和旧安排放在辅助交接／变更记录，不能让读者自行拼出当前计划。沿用稳定 ID 和已有任务关联，不因新一轮讨论重建条目。
- **按变化复核。** 措辞整理不自动发布基线；规则、AC 含义、设计依赖或批次范围改变时记录影响，按请求及授权更新相关部分。已关闭或已通过的任务和测试仍保留原执行版本及结果，涉及新定义时标为需复核；不能改写旧证据，或只在文末追加一条新规则而保留相反的当前 AC。

按 [内容与版本约定](../shared/document-structure.md#先判内容性质再判维护责任)处理正文、来源、历史和证据。只更新进展时不自动改写需求基线；样例新增也不等于新增业务能力或完成交付。

## 研发与测试交接包

每个故事在自己的正式维护位置组织以下内容；格式可沿用项目现状，复杂度决定展开程度：

| 内容 | 下游能回答什么 |
|---|---|
| 用户故事 | 谁在何种场景下完成什么、为什么做，范围内外是什么 |
| 详细需求 | 前置条件、业务规则、主要流程、相关状态／权限和必要异常是什么 |
| 验收条件 | 给定条件、执行动作、可观察结果及必要副作用；关键边界和质量要求如何判断通过或失败 |
| 设计与依赖 | 相关原型、交互与设计规范、架构、模型、接口和版本在哪里；其对本故事的用途、哪些已确定、哪些仍阻塞 |
| 研发任务 | 本次具体实现或迁移什么，使用什么输入／契约，交付什么，依赖什么，怎样判定任务完成 |
| 测试任务 | 覆盖哪些 AC 和回归影响，用什么数据／环境，怎样操作和判断结果，完成后保存什么证据 |
| 批次与状态 | 本批包含哪些故事，当前可推进范围、阻塞及后续安排是什么 |

使用 [设计输入与追溯](../shared/design-input.md) 关联需求、故事、规则、设计、验收条件、研发／测试任务与实际证据；已有定义以引用为准。

总览先解释交付目标、本期需求边界及主要依赖，再引出批次和独立故事，不从任务编号表开始。故事正文先说明本次用户结果及边界，再给行为、验收、设计依赖、研发测试任务和阻塞。引用共享规则及设计的有效版本与具体章节，写明它们在本故事中的用途；不要求复制全部上游正文，但读者不能依靠聊天或自行拼接总表来确定本次工作。大故事按可独立交付、验收及依赖拆分，保留原 ID 的父项或承接关系，不能仅复制同一摘要。复杂的共享交互、契约或测试设计按主题展开，可继续分子专题；每篇仍先交代整体关系，再展开局部。实际执行步骤、结果和工具过程归辅助验证／交接，不混入需求与 AC 定义。

验收中的不同结果必须有明确触发条件。例如“澄清或返回部分结果”应说明缺什么信息时澄清、哪种缺失允许部分返回，以及必须展示的限制。交接时至少提供覆盖主路径和重要风险的代表性验证场景及明确预期；完整测试脚本可由后续任务完成，关键行为不能留给测试人员决定。

## 两类完成判断

**可交付研发和测试：** 逐故事检查目标与边界、详细行为、必要设计、可执行任务和明确验收，而非给整个任务目录盖章。分别说明研发准备、集成条件与验收准备，记录依据、阻塞项、影响任务及解除条件。业务规则或必要设计未定可阻塞研发；真实凭证未提供可能只阻塞真实集成，不阻塞已有明确契约的离线实现。部分任务可先做不等于整个故事就绪。按 [公共检查](../shared/readiness.md) 记录证据，不要求远期故事同时就绪。

**已完成交付：** 实现已具备，约定验收条件有对应执行结果，必要的集成、迁移、回归及运行条件已有证据，遗留问题已按项目约定处理；需要业务验收或上线时引用相应实际结果。不得将 demo 通过、文档完成、任务创建或任务关闭直接等同于交付通过。未运行的测试标为未执行，不把用例定义当成测试结果。

分别报告交接准备程度、实现状态、测试结果和实际交付状态；准备就绪不意味着已经实现，测试通过也只覆盖实际版本、环境和执行范围。

文档交接按 [独立阅读评审](../shared/document-structure.md#交付前的阅读检查)，由不继承主会话历史的子 Agent 以一个故事及其必要引用检查：能否直接回答本次目标、要执行的任务及产出、验证条件及预期、依赖与阻塞。只有编号、摘要、链接或“支持某能力”不能通过。再核对总览中的批次及跨故事依赖；实际交付判断另读取执行证据，阅读评审不替代运行验收。故事、AC、任务与批次之间无未解释冲突，局部测试和 demo 的通过不扩张为整个故事或批次通过。

## 保存与任务落地

按项目配置确定故事与任务的唯一正式维护位置：

- **任务系统维护：** 已接入且本轮或既有约定授权维护时，按 [任务落地](../integrations/task-tracking.md) 在系统中维护完整故事、AC、研发及测试任务、依赖和状态。适配实际类型与层级，不强制 Story／Sub-task。总览保留批次、跨故事依赖、实际 key／URL 及证据入口，本地不再并行维护另一份正式故事／任务正文。
- **本地维护：** 每个可交付故事使用独立文档，目录与命名遵循项目上下文的组织约定，在其中维护详细行为、AC、研发测试任务、依赖和状态。已有独立场景文件满足相同交接深度时原位复用并索引；多个故事挤在一张表或同一总文档中不算按故事维护。共享技术任务可单独成文，由各故事引用。

项目约定的交付总览负责交付目标、本期需求边界决议或其引用、决议后逐步形成的故事索引、当前推进项、批次、跨故事依赖和逐故事就绪摘要，不承担全部故事正文。旧项目中的 `04-需求细化与交付推进.md` 按内容和有效版本识别，不因本阶段编号顺延自动迁移。临时咨询仍可在对话交付，不强制落盘；明确只要拆解草稿时不自动创建远端任务。

配置了系统地址但没有维护授权时，完成可评审草稿并注明待写入。工具不可用或部分失败时保留草稿及真实成功映射，明确尚未落地的部分，不擅自建立另一套正式来源，也不把草稿当远端维护完成。迁移时复用既有 ID、任务及有效正文，更新索引和来源约定，不能重建重复任务。正文、交接、验证和附属文件按 [文档结构规范](../shared/document-structure.md) 分区；已落地且无保留价值的任务中间草稿按维护范围清理，保留真实成功映射和未落地缺口。
