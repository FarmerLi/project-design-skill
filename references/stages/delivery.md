# 需求细化与交付推进

## 阶段目标与输入

将已明确的需求和设计整合为可供研发实现、测试验证的用户故事与验收条件，并据此组织任务、安排批次、跟踪结果和处理反馈。读者应能理解本批交付什么用户结果、如何验收、有哪些依赖以及实际进展；本阶段包括开发前准备与交付跟进，不以任务拆解或文档完成代替实际交付。

最低输入为本轮场景、预期结果、范围和相关约束；已有需求、架构、模型直接引用，跟进时补任务状态及实际实现／测试证据。读取 [工作契约](../shared/working-contract.md)，只读当前批次的相关材料，不要求补齐前三阶段文件。

## 围绕交付切片推进

1. **选择近期结果。** 根据用户价值、风险和依赖切分可验收范围。数据库、后端、前端是实现任务，不代替业务结果；技术前置工作关联所解锁的故事或质量目标，定义自己的验证方式，不伪造用户角色。
2. **形成用户故事与验收条件。** 使用 [用户故事与验收细化](detail.md) 补齐规则、状态、权限、异常及质量要求。一个场景可包含多个故事，一个故事可对应多个研发与测试任务。先有可讨论草稿，避免一次性细化全部远期需求。
3. **补齐必要设计。** 将故事关联有效架构、模型、接口或直接实现说明；未决问题只阻塞相关故事。需要验证的技术问题返回 [架构验证](architecture.md)，语义与数据冲突返回 [模型设计](modeling.md)，局部业务规则在细化中解决。
4. **拆分研发与测试任务。** 按故事拆出实现、测试设计与执行、集成以及必要迁移任务。标明各任务输入、输出、依赖和完成证据，测试任务关联验收条件，并按风险补充回归范围、数据和环境准备。纯技术任务可以采用技术验证条件，不强制改写为业务故事。
5. **安排批次并检查就绪。** 每批明确用户结果、故事范围、设计与外部依赖、验收来源、准备程度和阻塞。区分价值优先级与技术依赖顺序；无产能依据不承诺日期，无负责人信息不填人。必要设计缺失不能被任务列表掩盖。
6. **跟进与反馈。** 请求推进或核对交付时，读取当前任务及实现、测试证据，核对完成与受阻部分。缺陷关联原故事和验收条件；需求或设计变化按 [变更分析](../changes/impact.md) 复核关联产物，更新剩余任务与计划。没有实际进展材料时只交付准备结果和待核实状态，不编造进展。

仅请求故事细化、批次建议或一次进展核对时，到对应范围结束；“交付推进”不自动创建长期监控、远端任务或部署应用。已有执行和同步授权沿用，不追加阶段确认。

## 整理故事与当前交付计划

- **按结果归并。** 将跨轮输入中的角色、情境、规则和预期结果并入已有故事及其验收条件，不把每条聊天、接口或实现步骤各建一个故事。必要拆分依据独立价值、验收或依赖，保留原条目承接关系；任务与技术前置工作按执行责任组织，不取代故事的业务说明。
- **区分规范与用例。** 故事和 AC 定义范围内的行为与判据，测试用例将其展开为具体数据、步骤和预期，执行记录说明实际版本、环境与结果。样例中的业务角色、固定 ID、字段值和接口绑定只在确属交付范围时进入规范；教学或试点数据不自动成为产品限制。具体边界数值可以用于说明 AC，但测试通过不能反向定义或缩减故事范围。
- **维护同一计划。** 把新决定和进展整合到现有故事、AC、批次、依赖与任务映射。交付正文说明用户结果及其承接关系，任务清单和证据索引用于追溯；讨论过程、每日汇报和旧安排放在相应记录，不能让读者自行拼出当前计划。沿用稳定 ID 和已有任务关联，不因新一轮讨论重建条目。
- **按变化复核。** 措辞整理不自动发布基线；规则、AC 含义、设计依赖或批次范围改变时记录影响，按请求及授权更新相关部分。已关闭或已通过的任务和测试仍保留原执行版本及结果，涉及新定义时标为需复核；不能改写旧证据，或只在文末追加一条新规则而保留相反的当前 AC。

按 [内容与版本约定](../shared/working-contract.md#内容归属与当前正文)处理正文、来源、历史和证据。只更新进展时不自动改写需求基线；样例新增也不等于新增业务能力或完成交付。

## 研发与测试交接包

按项目已有格式组织，最小内容如下，可合并在故事或交付计划中：

| 内容 | 下游能回答什么 |
|---|---|
| 用户故事 | 谁在何种场景下完成什么、为什么做，范围内外是什么 |
| 详细需求 | 前置条件、业务规则、主要流程、相关状态／权限和必要异常是什么 |
| 验收条件 | 给定条件、执行动作、可观察结果及必要副作用；关键边界和质量要求如何判断通过或失败 |
| 设计与依赖 | 相关架构、模型、接口和版本在哪里，哪些已确定、哪些仍阻塞 |
| 研发任务 | 实现或迁移什么、依赖什么、完成后提供什么证据 |
| 测试任务 | 覆盖哪些验收条件和回归影响，需要哪些数据、环境及验证方法 |
| 批次与状态 | 本批包含哪些故事，当前可推进范围、阻塞及后续安排是什么 |

使用 [设计输入与追溯](../shared/design-input.md) 关联需求、故事、规则、设计、验收条件、研发／测试任务与实际证据；已有定义以引用为准。

交接包先说明本批用户结果、故事及边界，再给验收、设计依赖、研发测试安排和当前状态，细节通过规范引用展开。结构可沿用项目现状，故事可与计划合并；不能只有任务名、状态表或链接，也不要求重抄上游需求和设计。

## 两类完成判断

**可交付研发和测试：** 当前故事的业务意图与范围明确，关键规则有依据，必要设计及依赖足以执行，验收结果可判断，研发与测试任务能据此准备和开展工作。关键未决项未解决的故事保留草稿或阻塞；就绪判定按 [公共检查](../shared/readiness.md) 记录证据，不要求远期故事同时就绪。

**已完成交付：** 实现已具备，约定验收条件有对应执行结果，必要的集成、迁移、回归及运行条件已有证据，遗留问题已按项目约定处理；需要业务验收或上线时引用相应实际结果。不得将 demo 通过、文档完成、任务创建或任务关闭直接等同于交付通过。未运行的测试标为未执行，不把用例定义当成测试结果。

分别报告交接准备程度、实现状态、测试结果和实际交付状态；准备就绪不意味着已经实现，测试通过也只覆盖实际版本、环境和执行范围。

两类判断前都回读当前交付正文及关联故事，确认不看聊天、旧计划和测试数据也能说明本批结果、范围、关键验收、依赖和阻塞；实际交付判断另读取执行证据。故事、AC、任务与批次之间无未解释冲突，已解决问题退出当前清单；局部测试和 demo 的通过不扩张为整个故事或批次通过。

## 保存与任务落地

按项目配置保存故事、验收与任务计划；本地默认 `04-需求细化与交付推进.md` 和 `stories/用户故事-编号.md`，已有场景文件或任务正文可承载故事，不强制拆成多份文件。交付计划维护故事清单、批次、依赖、任务映射及结果证据。

用户要求创建／更新任务或已有持续同步约定时读取 [任务落地](../integrations/task-tracking.md)，按目标系统实际层级维护故事与研发测试任务，回查结果并记录 key／URL。仅要求拆解时交付草稿。延续已有任务与文档，不因更换阶段结构重建业务项目材料。
