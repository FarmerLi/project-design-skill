# 用户故事与验收细化

本文件是第五阶段的细化方法，也可独立使用。读取 [交接契约](../shared/working-contract.md) 和 [通用分析规格](../shared/analysis-spec.md) 中相关维度。最低输入为本轮场景、预期结果、范围和已知约束。独立调用时从用户材料补足这些内容即可。

## 工作单元

故事拆分与细化前，先按 [本期需求边界决议](delivery.md#开始前先决议本期需求边界) 明确本期哪些需求需要建立故事，再在边界内选择当前需求或场景，逐项拆分和细化。需求边界决议不预先固定故事清单或数量。用户直接指定一个边界明确的场景或故事时即复用该边界，不要求先补全项目范围；仅给出宽泛目标时先交付需求边界建议。

每轮聚焦一个场景或一组紧密关联的场景，将其组织为可交付的用户故事，不加载所有场景文件。先读概要中相关章节、当前场景涉及的有效决策和共享定义。沿用已有故事编号与格式；新故事可用 `US-xxx`，角色可以是业务用户或真实调用方，不为了句式虚构人物。

故事描述角色在具体情境下要取得的结果和价值，例如“作为……，在……时，我希望……，以便……”。句式可调整，但不能只有功能名称或一句愿望。场景承载过程，故事承载可交付价值，任务承载执行安排；它们可以一对多或多对多，不强制一场景一故事。

按实际复杂度探索：

1. 谁在何时因为什么触发任务，进入条件和输入是什么。
2. 正常步骤、输出与可观察结果。
3. 业务规则、口径与限制；同一规则只维护一个定义，其他位置引用。
4. 相关信息和状态如何变化，是否影响其他模块或外部系统。
5. 权限与数据可见范围；有审批时区分操作权限和审批决策。
6. 有意义的失败、重复、取消、撤回、修改、部分完成等路径。
7. 与当前场景相关的体验或质量要求。
8. 可具体判断通过或失败的验收案例。

不机械问完所有问题。简单功能可以简述；审批、金额、跨系统协作等高影响场景再展开。不自动增加报表、审批或 AI 功能。

## 逐步收敛

先从已有材料形成可评审草稿，按信息依赖补足：共同术语与信息 → 操作与规则 → 协作及失败后果 → 查询、权限、质量和验收。该顺序用于发现依赖，不是固定访谈轮次；已有明确定义直接引用。

对会改变其他对象、模块或系统的操作，单独执行 [协作与影响链](collaboration.md)。对所有本轮变化操作保留检查结果，不能只写几条显眼联动。普通局部改动可用一句“仅改变本对象，无下游业务影响，依据……”记录。

存在共享信息时补关系与历史策略，有生命周期时补迁移条件，有查询时补粒度与口径，有外部交接时补契约。各维度的展开程度由下游是否仍需猜测关键业务决定；不以文档篇幅或表格数量作为完成标准。

每轮把明确回复更新到规范定义及待决记录，再修正关联视图。已回答的问题不重复问；未回答的高影响问题保留条件性结论，只暂停依赖它的部分。

将回复提炼为已有故事、规则和 AC 的当前定义，合并重复、消解失效条件，不按对话次数追加故事或新建验收清单。等价整理沿用稳定 ID 和确认状态；行为或验收含义改变时，记录替代关系及设计、任务、旧测试结果的影响，按 [版本约定](../shared/working-contract.md#版本完成标准与变更)维护，未复核项不冒充已适配。

## 中立表达

跨功能影响先问业务后果和时效要求。例如“收款成立后，汇总更新失败是否影响收款成立，多久必须恢复”，不要先要求同步调用、同一事务或事件队列。

界面描述可能携带真实需求。批量处理、错误反馈、无障碍、离线等有业务价值的交互约束先进入需求或 [原型与交互设计](prototype-interaction.md)，故事和 AC 引用其有效定义；颜色和布局偏好可由该阶段的设计规范承接，不简单丢弃全部 UI 信息，也不在本阶段重做原型或页面设计。

需要详细设计时，依据问题进入 [原型与交互设计](prototype-interaction.md)、[架构验证](architecture.md) 或 [模型设计](modeling.md)，直接复用已选方法与技术约束。模块、接口、表结构、模型编号、原型与设计规范写入设计产物，引用场景、故事及需求 ID。已有设计直接关联，不重新选择方法。

## 故事正文与最小产物

故事先解释结果与价值、边界，再沿主流程与关键异常展开规则、状态和验收，之后关联设计、执行任务及阻塞。复杂且可独立复用的细节进入相应专题，专题沿用 [整体到局部的组织原则](../shared/document-structure.md#从整体到局部)，不以来源转述、确认顺序或任务表代替故事主线。

每个用户故事交付以下内容；需要保存时按 [第五阶段维护规则](delivery.md#保存与任务落地) 选择唯一正式位置。任务系统中维护完整故事及关联任务；本地按故事拆成独立文档，默认 `stories/用户故事-编号-主题.md`。已有独立场景文档满足同等深度时可复用，总览中的一行不能替代故事正文：

- 稳定 ID、关联需求／场景、角色、业务价值、触发与前置条件，明确包含与排除的范围；
- 正常路径、结果、关键规则与相关信息；
- 必要的异常／恢复路径、协作影响、权限与质量要求；
- 验收条件：稳定 AC ID、给定条件、执行动作、可观察结果，必要的测试数据、环境及验证方法；
- 来源、确认状态、设计版本与依赖、未决事项及阻塞范围；
- 完整研发交接时列出或关联可执行的研发与测试任务：各自的范围、输入、输出、依赖、完成判据及证据，测试任务包含数据／环境、验证步骤和明确预期；分别判断研发、集成及验收准备状态。仅细化故事时可保留后续任务拆分入口，不伪造已创建任务。

共享定义可放同一文档的公共章节或 `requirements/` 下，遵循项目实际文档配置；故事及场景引用其 ID 与位置，不重复维护。独立故事保留自己的行为和可判断的 AC，共享规则的摘要／应用与重复规范按 [主题分工规则](../shared/document-structure.md#主题边界与唯一维护位置) 区分，不为自包含复制整套设计，也不为去重删掉预期结果。对完整范围输出分析维度覆盖表；局部场景只注明相关缺口。需要交给设计／研发测试时补 [设计输入与追溯](../shared/design-input.md)，不要求切换某种建模方法。

用于研发交接的独立故事必须在正文说明本次结果、关键行为、任务及验收；引用标明所用设计版本、具体章节和用途，不能只有整篇文档链接。大故事可拆成子故事并保留父项及原 ID，拆分后的每项都有自己的结果和验收边界；不按技术层次机械拆故事，也不将共享基础任务在每个故事中重复创建。

案例要覆盖重要边界而非只重复功能名称。例如“重复提交同一请求不产生第二笔业务记录”比“支持幂等”更便于确认和验收，但是否需要此规则必须有场景依据。

## 可验证的验收条件

使用 `给定条件 → 执行动作 → 可观察结果`，可采用 Given / When / Then，不强制英文或工具语法。结果应包括相关输出、状态变化、拒绝原因及不应发生的副作用；“正常工作”“体验良好”不能单独作为通过标准。

按实际风险覆盖主路径、重要边界、权限拒绝、失败恢复及质量要求。质量条件记录负载、环境、指标口径和目标来源；数值未定时登记缺口，不填默认阈值。验收条件定义通过标准，测试用例将其展开为具体数据、步骤和预期；两者关联但不要求一对一，测试可按风险补充回归用例。

AC 的适用范围来自需求和规则，不能由某个接口响应、演示账号或一次成功样例倒推。可用具体例子解释边界，同时说明判定规则；固定数据、接口参数及运行步骤归相应用例。业务本就限定某角色、字段、阈值或外部契约时保留其规范含义，不把所有具体内容都移出 AC。具体用例及执行结果放辅助验证区，通过引用关联，不用测试日志取代验收定义；故事中的验收摘要仍说明如何判断通过。

| AC ID | 需求／规则引用 | 给定条件与输入 | 动作 | 可观察结果 | 验证方法／必要环境 | 定义与执行状态 |
|---|---|---|---|---|---|---|

记录“已定义／待业务决定”等定义状态；有实际执行时另附版本、环境和结果，未执行明确写未执行。一个条件存在关键未决项时，不通过模糊措辞使故事看起来已经就绪。

一个 AC 包含不同结果时写清各结果的触发条件，不以“失败或部分成功”等未分情况的选择代替判据。交接场景至少明确前置状态／代表性输入、操作、预期输出与必要副作用、验证方式；测试脚本可以后续编写，业务行为及通过标准必须在交接前确定。

## 完成与回退

分别判断本轮产出与下游准备程度：

- **故事细化完成：** 本轮故事的意图、范围、关键业务规则、主路径与重要异常有依据，验收条件可判断。仅请求故事与验收条件时，到此即可完成；未开展的架构、模型或任务拆分记为后续工作，不为完成故事细化自动展开。会改变预期行为或验收结果的业务未决项仍阻塞相关部分，不能只登记缺口就宣称细化完成。
- **可交付研发和测试：** 在故事细化基础上，必要原型走查、交互与设计规范及研发测试任务足以执行，按 [第五阶段的交接标准](delivery.md#两类完成判断) 判断。原型或设计缺失可能阻塞研发测试交接，但不倒推为已明确的故事与验收条件尚未完成。

未执行测试时只称“验收条件／案例已定义”；两类判断都不代表实际交付完成。

发现概要遗漏核心用户或闭环、价值假设不成立时，带着具体证据回交第一阶段；原型、交互、架构或模型冲突回交对应设计，局部规则缺口在本阶段解决。任务拆分、批次和实际交付跟进见 [第五阶段主方法](delivery.md)，不将故事细化完成当成已完成交付。
按 [就绪检查](../shared/readiness.md) 核对本轮规则、状态、协作、权限、查询、验收和版本，记录证据与未通过项，不对全项目做无关深审。需要持续维护或交接时更新场景索引和交接；临时咨询在回复中交付结果与阻塞即可。
