# 需求探索与澄清

## 阶段目标与输入

将零散想法、对话和材料综合为可独立阅读的需求概要，或从已有项目中还原相关能力、业务流程与实现依据。读者应能理解为谁解决什么问题、目标是什么、需要哪些能力及如何协作、当前范围和成功标准，而无需重放对话或比较历史补丁。本阶段同时处理业务价值、范围取舍和核心闭环，不要求达到逐项可开发的详细程度。

最低输入为想法、问题、目标或已有项目的位置与材料。读取 [工作契约](../shared/working-contract.md)，先利用已有信息形成理解草稿；已有项目按 [现状分析](../entry/context.md) 定向取证，不以全仓阅读作为开始条件。用户只要求了解现状时交付现状与缺口，不强制提出改造目标。

## 工作方法

1. **明确本轮对象。** 区分问题、预期变化、候选方案与已定约束。新项目先识别用户、使用情境和核心任务；已有项目区分实际行为、有效约定与目标行为。辨明正在设计的产品、依赖的外部系统与验证样例，确定角色和术语分别属于谁，不从样例结构直接定义产品能力。
2. **建立总体理解。** 先给业务或能力全景、代表性流程及本轮范围草稿，再补关键缺口。理解“如何实现”时先说明业务如何完成、由哪些能力承接及受什么限制；框架、调用和数据结构只深挖到足以解释当前问题，领域与数据模型设计交给第二阶段，技术架构与验证交给第三阶段，通过原型验证用户操作与反馈交给第四阶段。
3. **明确目标与价值。** 将功能诉求还原为可观察的改善，说明不改变的后果和投入理由。基线或目标数值缺失时记录测量方式，不编造收益。需要投入比较或关键成立条件判断时读取 [价值与可行性](feasibility.md)，允许形成缩小范围、先验证或暂缓建议。
4. **综合并收敛需求。** 按下方方法将输入提炼、合并并消歧，从触发、角色、输入走到可观察结果，关联目标、场景、能力和关键规则。按目标贡献、约束和风险区分纳入、延后与不做，裁剪后重新检查闭环；范围方法见 [需求概要与范围](outline.md)。已有方案在相关主题内整合新结论，不按对话顺序追加正文。
5. **登记约束与验证问题。** 识别会改变范围和方案的质量、资源、数据及外部条件。将未知分为业务事实、待决选择与待验证技术假设，说明影响、补证方式和解决节点。已有要求直接复用，行业惯例只能支撑建议，不能代替项目事实。

以上为依赖关系，不是固定访谈轮次。总体信息先有草稿，近期范围逐步深入；不要求每个项目都有审批、报表或持久化对象，也不按模板制造需求。提问、草稿更新及交互需求的处理遵循 [工作契约](../shared/working-contract.md#对话与范围控制)。

## 从输入提炼需求

- **归类与提取。** 将输入中的问题、目标、能力诉求、硬约束、设计建议、现状证据和样例分开；同一段话可包含多类。提炼谁在什么情境下要完成什么任务，产品应提供什么行为、结果和边界。价值解释缺乏依据时保留为假设，不用润色把建议升级为已确认要求。
- **归并与消歧。** 对照已有定义判断新增、补充、纠正或替代，合并同义要求，分开同名不同义。冲突不能自行解决时指出影响并登记待决，不能让两条矛盾定义同时充当有效规范。
- **关联与推演。** 将能力关联到目标或用户任务，将场景关联到所需能力和关键规则；检查核心路径的输入、协作与结果。缺失能力显式记录，无目标依据的功能先作为候选，不因材料中有接口就自动纳入范围。
- **整合与回读。** 把已确定结论归入对应主题，处理旧措辞、重复范围和已解决问题。按 [内容归属](../shared/document-structure.md#先判内容性质再判维护责任)维护正文与依据，再从陌生读者视角回读当前需求，确认无需查看聊天、旧版或验证样例就能理解产品。

单项能力可用“角色／情境 → 任务或问题 → 产品行为与可观察结果 → 关键边界”表达；来源、状态和稳定 ID 按追溯需要附加，不要求每项都套长表格。明确要求经等价整理后继续有效，无须重新确认；新增行为或取舍仍按建议或待决管理。需要校准表达时可读 [输入整理示例](../examples/analysis-slices.md#示例四多轮输入与样例材料整理)。

对于平台、工具或集成项目，按相关性区分产品自身能力、接入系统的领域语义和验证样例的具体对象／字段。例如识别出某样例的业务对象，只能证明该样例有相应声明；是否需要通用建模能力还要关联产品目标。平台使用者、外部业务角色与实际执行身份不能仅凭同名合并。若该领域本来就是产品的设计对象，其业务概念可以直接属于正式需求，不机械套三层模型。

## 正文组织与最小产物

按本轮请求交付，优先在一份需求概要中建立阅读主线。推荐按下列逻辑组织，已有合理结构可以沿用，局部请求只维护相关主题：

1. 产品定位、问题、价值与目标；已有项目说明相关现状和目标差距，仅做现状探索时保持现状用途。
2. 目标用户、核心场景与必要术语，分清产品和外部系统边界。
3. 从触发到结果的核心流程、能力责任及协作关系；能力需求和关键规则关联目标与场景。
4. 产品目标范围、近期交付范围、优先级与排除项及理由，裁剪后的闭环检查；验证切片另行说明。
5. 成功信号、质量要求和测量方式、成立条件及关键依赖；无依据不编造收益和阈值。
6. 当前待决与阻塞范围、下一步对象，以及来源、设计、验证和修订记录的必要索引。

来源及确认依据在辅助记录中维护，正文直接说明产品行为和边界，不以“用户提出”等来源转述组织需求。按 [文档结构规范](../shared/document-structure.md) 从整体展开场景、能力和规则；某项能力或共享规则需要独立维护时再拆专题，专题仍先说明自身范围与整体关系。主文保留概貌和关键约束，不复制专题全部细节。

需要保存时按项目上下文的入口与组织约定维护，例如在已有需求主文中归并本阶段内容，不预设阶段文件名。持续复用的现状可在项目约定的现状专题维护；价值比较、概要方法的产物可以作为章节，不要求另建阶段文档。持续更新按 [文档维护](../integrations/document-maintenance.md) 归并定义、分离来源及验证材料，并处理已整合中间草稿；修订按 [版本约定](../shared/working-contract.md#版本完成标准与变更) 执行。

## 完成标准与交接

按本轮范围及用途给出依据：

| 检查项 | 可交接条件 |
|---|---|
| 对象与事实 | 用户任务或现状探索对象明确，产品、外部系统及样例的术语归属清楚，观察、约定、目标和假设可区分 |
| 目标与价值 | 需要改变时能说明为何做、改善什么及如何观察；仅做现状分析时可注明不适用 |
| 能力与闭环 | 当前范围能力有目标或用户任务依据，核心场景有能力承接，结果无未解释断点，不把未知人工承接当作已有安排 |
| 范围与证据 | 纳入与排除的边界有理由，产品范围、交付范围与验证覆盖可区分，样例结果未被外推为通用支持 |
| 约束与依赖 | 有效约束可定位，关键成立前提有支持证据或明确验证任务与受阻范围 |
| 整体可读与一致 | 当前正文能形成本轮产品认知，每项定义有唯一维护位置；无需要读历史才能解释的矛盾、重复定义或陈旧待决项 |
| 后续用途 | 当前结论足以支持指定的架构探索、模型探索或故事细化；剩余未知的影响及解决节点明确 |

按 [就绪检查](../shared/readiness.md) 分开报告“本轮探索完成”“可供后续使用的范围”和“实际验证状态”。有依据的暂缓或先验证也是分析结果；前提未证实的范围只可用于条件性探索，不能当作确定的设计或交付依据。

仅做目标澄清、价值判断或现状探索时，在对应范围结束，不要求为满足整阶段标准补跑其他子工作。已授权连续推进时只继续可推进部分；技术问题交给 [架构验证](architecture.md)，模型问题交给 [领域与数据模型设计](modeling.md)，用户任务与反馈的组织及验证交给 [原型与交互设计](prototype-interaction.md)，近期场景可直接进入 [需求细化与交付推进](delivery.md)。
