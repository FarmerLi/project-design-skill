# 需求探索与澄清

## 阶段目标与输入

将新项目想法形成可供设计和验证的需求概要，或从已有项目中还原相关能力、业务流程与实现依据，明确现状、目标及本轮要解决的问题。本阶段同时处理业务价值、范围取舍和核心闭环，不要求达到逐项可开发的详细程度。

最低输入为想法、问题、目标或已有项目的位置与材料。读取 [工作契约](../shared/working-contract.md)，先利用已有信息形成理解草稿；已有项目按 [现状分析](../entry/context.md) 定向取证，不以全仓阅读作为开始条件。用户只要求了解现状时交付现状与缺口，不强制提出改造目标。

## 工作方法

1. **明确本轮对象。** 区分问题、预期变化、候选方案与已定约束。新项目先识别用户、使用情境和核心任务；已有项目区分实际行为、有效约定与目标行为，记录相关代码、文档或运行证据。
2. **建立总体理解。** 先给业务或能力全景、代表性流程及本轮范围草稿，再补关键缺口。理解“如何实现”时先说明业务如何完成、由哪些能力承接及受什么限制；框架、调用和数据结构只深挖到足以解释当前问题，专项设计分别交给第二、第三阶段。
3. **明确目标与价值。** 将功能诉求还原为可观察的改善，说明不改变的后果和投入理由。基线或目标数值缺失时记录测量方式，不编造收益。需要投入比较或关键成立条件判断时读取 [价值与可行性](feasibility.md)，允许形成缩小范围、先验证或暂缓建议。
4. **收敛需求概要。** 从触发、角色、输入走到可观察结果，说明能力责任、外部依赖与必要承接。按目标贡献、约束和风险区分纳入、延后与不做，裁剪后重新检查闭环；详细方法见 [需求概要与范围](outline.md)。已有方案只补差距，不重复梳理。
5. **登记约束与验证问题。** 识别会改变范围和方案的质量、资源、数据及外部条件。将未知分为业务事实、待决选择与待验证技术假设，说明影响、补证方式和解决节点。已有要求直接复用，行业惯例只能支撑建议，不能代替项目事实。

以上为依赖关系，不是固定访谈轮次。总体信息先有草稿，近期范围逐步深入；不要求每个项目都有审批、报表或持久化对象，也不按模板制造需求。提问、草稿更新及交互需求的处理遵循 [工作契约](../shared/working-contract.md#对话与范围控制)。

## 最小产物

按本轮请求交付，可在一份文档中组织：

- 新项目的用户、问题、目标与成功信号，或已有项目的能力与流程现状、实现证据及材料差异；有改造目标时说明现状与目标的差距。
- 核心场景、能力责任、本轮／首期范围及取舍、裁剪后的闭环检查。
- 业务价值及成立条件，相关约束、依赖与来源。
- 关键未知、验证方式、阻塞范围、下一步设计或细化对象。

需要保存时按项目配置维护，本地默认 `01-discovery.md`。持续复用的现状可放 `baseline.md`；价值比较、概要方法的产物可以作为章节，不要求另建第二、第三份阶段文档。

## 完成标准与交接

按本轮范围及用途给出依据：

| 检查项 | 可交接条件 |
|---|---|
| 对象与事实 | 用户任务或现状探索对象明确，观察、约定、目标和假设可区分 |
| 目标与价值 | 需要改变时能说明为何做、改善什么及如何观察；仅做现状分析时可注明不适用 |
| 范围与闭环 | 纳入与排除的边界有理由，核心结果无未解释断点，不把未知人工承接当作已有安排 |
| 约束与依赖 | 有效约束可定位，关键成立前提有支持证据或明确验证任务与受阻范围 |
| 后续用途 | 当前结论足以支持指定的架构探索、模型探索或故事细化；剩余未知的影响及解决节点明确 |

按 [就绪检查](../shared/readiness.md) 分开报告“本轮探索完成”“可供后续使用的范围”和“实际验证状态”。有依据的暂缓或先验证也是分析结果；前提未证实的范围只可用于条件性探索，不能当作确定的设计或交付依据。

仅做目标澄清、价值判断或现状探索时，在对应范围结束，不要求为满足整阶段标准补跑其他子工作。已授权连续推进时只继续可推进部分；技术问题交给 [架构验证](architecture.md)，模型问题交给 [领域与数据模型设计](modeling.md)，近期场景可直接进入 [需求细化与交付推进](delivery.md)。
