# 交互与 UI 设计

## 目标与输入

把当前用户任务转为可理解、可讨论或可实施的交互方案，深度按用途确定。最低输入是用户结果、相关场景和关键规则；复用已有界面、模型状态、技术约束及公共规范。

先解决当前任务。局部页面调整从受影响区域进入；新产品先给主要入口和任务关系，再深入近期场景。无需先完成其他阶段或建立整套设计系统。没有图形界面时设计实际命令、输出或会话行为，不虚构页面。

## 推进流程

1. **定位任务与边界。** 明确为谁完成什么结果、从哪里进入、与哪些已有能力衔接，区分既定范围和候选。
2. **形成整体思路。** 多任务或多页面时，用结构说明或必要总览解释主要区域、入口、职责和任务关系；单一局部请求保留足够上下文即可。
3. **设计关键场景。** 先走通主路径，再补会改变结果的分支与状态。说明前置条件、可用操作、必要校验、反馈、退出与恢复。所需信息和状态须有业务与技术依据。
4. **复用与提炼共性。** 有适用规范时直接引用；没有时随当前设计形成必要公共约定，重复模式稳定后再提炼规则。需要正式实施或多页面一致性时，补足真正影响实现与验收的取值和行为约束。
5. **场景核对并交付。** 检查任务是否能完成，关键状态和恢复是否有承接；修订冲突，说明关键未知及其影响。

这些步骤可以往返，规范不构成探索方案的前置门槛。原型只在用户要求或需要验证体验时制作；文字、流程／状态图和已有规范足够说明时即可交付。

详细程度依本次用途决定：实施交接时补明确字段、校验、文案和组件状态；探索时可以保留低影响视觉选择。涉及来源返回或跨入口操作时，检查过滤条件、状态刷新和失效项；键盘操作需要考虑对象移除、返回及权限失效后的焦点。

## 规范约束

已有交互与 UI 规范继续约束相关设计，候选不得覆盖有效规则。局部例外说明理由与影响；共性变更在原规范更新，再同步受影响页面。

| 遇到的实际需要 | 应明确的约定 |
|---|---|
| 跨页面操作和恢复反复出现 | 导航返回、校验、提交、等待、权限呈现、取消与恢复的公共行为 |
| 需要实施或检查视觉一致性 | 当前使用的布局、字体、颜色语义、间距、组件状态及必要响应式／可访问性规则 |

按本期实际使用部分展开，可放在当前设计的小节；没有独立维护需要就不另建两份规范。探索中的品牌与样式选择作为建议，不能虚构既定标准；“统一美观”不足以指导实际实现。

业务行为与状态归原需求／模型，实现机制归架构；交互设计说明用户怎样看到、操作及接收反馈。发现新业务动作或失败政策时返回具体取舍，不用控件默认值代定。

## 完成标准与交接

- 当前用途所需的任务位置、入口、主要操作和结果清楚；多任务方案能解释彼此关系。
- 主路径及重要的空、等待、权限拒绝、失败、重复、中断和恢复状态有合理承接，按实际风险展开；可逆操作检查必要反向路径。
- 与已有规范及相关模型／架构没有未解释冲突。实施交接涉及的行为和视觉约束足够明确，低影响后续选择与阻塞可区分。
- 当前方案和限制可从正文及必要引用理解；设计核对不等于实际运行或用户验证。

结论与简短核对结果优先放在现有设计或任务中，保存与额外评审按 [文档规则](../shared/document-structure.md) 处理。交给任务拆分时引用必要设计，无需复制规范或另建交接包。
