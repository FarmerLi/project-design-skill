# 交互与 UI 设计

## 目标与输入

将本期需求转为受规范约束、可供实现和验收的总体与详细设计。推进顺序为：**确定范围 → 交互与 UI 规范 → 总体设计 → 详细设计与场景核对 → 整体检查与交接**。

最低输入是当前用户结果、场景与规则，以及支撑本轮决定的模型状态和技术约束。不要求前三阶段全部定稿；缺口只阻塞依赖它的设计。已有范围、规范和总体设计直接复用，局部修改不补做全产品规范或全站结构。无图形界面时设计实际命令、输出或会话交互，说明 UI 不适用部分，不虚构页面；API 契约仍归架构。

从 [项目上下文](../shared/project-context.md) 定位文档入口，从相关设计文档读取规范、组件库和已有设计依据。本阶段以设计说明、流程／状态图及规范引用承载成果，不要求配置原型工具、制作可操作原型或执行原型走查；缺少这些内容不阻塞阶段完成或研发测试交接。用户另行要求原型时，按该请求的范围和授权处理。

只讨论推进方案时给步骤、产出和推进条件，不宣称设计或验证完成。已授权执行时按依赖推进，不为每步重复确认。来源与确认状态沿用 [工作契约](../shared/working-contract.md)，需求关联与缺口归属按 [设计输入与追溯](../shared/design-traceability.md)，需要检查分析维度时读取 [通用分析规格](../shared/analysis-spec.md)。

## 推进流程

开始时说明本轮目标、安排和当前处理项，再按下表推进；正文也先整体后局部，不直接从单条流程的操作细节开始。

| 环节 | 动作与产出 | 进入下一步的条件 |
|---|---|---|
| 确定范围 | 复用已定边界，明确用户、终端、本期功能与场景、暂缓及排除项，识别可复用设计和缺口 | 范围与输入足以支持当前决定；实质取舍未定时先给草案，不默认纳入候选能力 |
| 建立规范 | 按下节建立、复用或补齐本期交互规范和 UI 规范，标明来源、有效定义与待定项 | 能据规范选择公共模式、应用样式并检查是否符合；影响当前决定的待定项先解决，无依赖部分可继续 |
| 总体设计 | 在规范约束下形成信息架构、功能区域、入口导航、页面／工作区或命令职责及任务间关系，提供结构总览和必要场景带读 | 各主要任务有明确位置、承接与返回路径；单条流程、页面清单或工作计划不能代替总体设计，无须先定全部字段和控件 |
| 详细设计与场景核对 | 按场景引用规范，细化信息、操作、状态、反馈和恢复，核对流程、状态及规范符合性并修订冲突 | 当前场景符合规范，核心路径及关键分支有明确承接；未解决的断路阻塞依赖它的设计，无依赖场景可继续 |
| 整体检查与交接 | 回到总体核对需求覆盖、跨场景衔接及设计与规范一致性，交付有效设计、核对结论及剩余缺口 | 满足下述完成标准；第五阶段可据此细化故事和验收，不再代定关键体验规则 |

详细设计须说明入口与前置条件、页面／命令职责、字段与校验、状态和可用操作、反馈文案及恢复路径。权限、取消和异常中会改变流程的行为在流程设计时处理，不推迟为视觉细节。涉及来源返回或跨入口操作时，明确过滤条件、状态同步、失效条目移除及空状态；键盘交互还要落实状态刷新、对象移除、返回和权限失效后的焦点去向。必要的终端适配和质量要求按本期依据展开，不以界面默认值新增业务动作、状态或失败政策。

按代表性场景核对总体方案和规范的应用，覆盖从入口到可观察结果的主路径，以及适用的空、加载、权限拒绝、失败、重复、中断与恢复；可逆操作同时覆盖正反向及重要失败路径。依据设计说明、流程和状态定义检查前后条件与分支承接，记录冲突及修订结论；代表性场景不能替代总体设计和公共规范。

设计核对不等于运行测试或用户验证，不据此声称实际操作、服务行为或体验已验证。图文保持术语、状态和关系一致，图的选择与展示检查沿用 [图示约定](../shared/document-structure.md#图示辅助理解)。

## 规范约束

两类规范是具体设计的前置依据，只覆盖本期适用范围；已有设计系统引用其有效规则和令牌，不另建重复定义。没有规范时主动形成可评审草案，区分建议、已确定依据和待验证项，不虚构品牌标准或将规范形成等同于验证通过。

| 规范 | 必须能够约束的内容 | 可检查的表达 |
|---|---|---|
| 交互规范 | 导航返回、输入校验、提交确认、等待反馈、权限呈现、取消与恢复等公共行为 | 适用条件、触发动作、状态变化、反馈及恢复规则；说明怎样用场景检查 |
| UI 规范 | 布局与栅格、字体层级、颜色语义、间距密度、组件及状态、内容表达，以及适用的响应式和可访问性 | 可应用的令牌、数值、组件变体或明确选择条件；说明怎样检查详细设计及后续实现 |

规范不能停留在“统一美观”“操作友好”或待编写目录。详细设计通过章节、规则标识或组件引用说明具体应用，检查行为、文案、状态和样式是否符合；公共取值由权威源维护，页面不自行重定，也无需逐字段复制规范。

偏离规范时说明原因、适用范围和影响，区分有依据的局部例外与公共规则调整。共性修订先在权威规范形成有效定义，再同步受影响的总体设计、页面说明和验证项；候选不能覆盖有效规则，未解决的冲突阻塞相关设计就绪。业务行为与状态归需求／模型，保存与恢复机制归架构；交互与 UI 设计定义用户如何看到、操作及接收反馈，发现上游缺口返回对应阶段。

## 完成标准与交接

完整阶段交接须同时满足以下条件；局部请求按实际范围复用并检查必要依据。

- **总体完整。** 本期任务在总体结构中有明确位置，入口、跨页面承接与终点可解释，主要需求均有设计落点；不能以单条流程代替整体。
- **细节符合规范。** 两类规范可执行，详细设计有引用、符合性检查及有依据的例外；影响实现和验收的规则已收敛，共性修订已同步，设计、规范与组件库没有冲突。
- **场景与状态明确。** 核心任务及关键分支的入口、操作、状态、反馈和恢复均有设计定义并已核对；必要数据、权限反馈、状态恢复与时效有技术承载，关键行为不留给研发或测试临时决定。
- **阻塞已处理。** 核心断路、需求歧义或规范冲突已修复，或经用户明确缩小交接范围；回退上游的相关范围仍未就绪，解决并复核后才能交接。非阻塞待办说明保留原因。

正式正文按范围与依据、规范入口、总体设计、场景细节及核对结论组织；具体规则只在权威位置维护。保存位置、专题拆分、附件和历史处理沿用 [文档结构](../shared/document-structure.md)。交付前按 [独立阅读评审](../shared/document-structure.md#交付前的阅读检查) 执行。

按 [就绪检查](../shared/readiness.md) 分别报告设计规范就绪、设计核对、业务／用户验证和实现状态，未执行项如实记录。交给 [第五阶段](issue-delivery.md) 时引用设计与规范的有效版本；故事及 AC 定义行为与验收，不复制整套规范。
