# 交付范围确认与 Issue 拆分

## 阶段目标与输入

把有效需求与设计转为本期可执行、可验收的交付切片。第五阶段总览只维护本期目标、覆盖与排除范围、优先级／依赖及 Issue 索引；长期业务规则、用户场景和设计决策留在需求与设计正文。执行 Issue 建立时说明本次目标、范围、AC、必要约束与验证依据；执行时再关联实施方案、具体测试及交付证据，不维护第二套任务详情。

这里的 Issue 指项目采用的执行任务。已有其他任务平台或本地任务记录时使用轻量等价来源，不强制接入特定平台、建立独立故事或批量创建 Issue。仅要求故事／AC、范围建议或进展核对时按请求结束；完整交接才检查执行所需信息，不把拆分、任务关闭或文档完成当成实际交付。

最低输入是本期场景、预期结果、范围和约束；复用相关需求、模型、架构及[交互与 UI 设计](interaction.md)，只读取当前切片涉及的材料，不要求补齐前四阶段。跟进时另读实际任务和实现／测试证据。共同状态与版本规则见 [工作契约](../shared/working-contract.md)。

## Issue 规范入口与目标表达

建立、拆分或改写前，从项目指令、规范索引或已有上下文的 `standards` 定位项目 Issue 规范，按本次任务读取；项目没有独立规范时使用本节方法，不要求先建规范或安装其他技能。项目特有的时长、PR、编号与审批要求留在项目，不复制到通用技能。

Issue 正文先表达问题、目的、完成后的能力或行为及范围，再给验收、约束和依据。代码分析用于核实差距与依赖，不能把文件、函数、Hook 的处理步骤逐项翻译为目标需求。重构可表达职责、协作与状态归属的目标，例如“列表与详情各自承担内容职责，场景协调浏览，业务规则统一管理”；不得只写“提取组件”“提高可维护性”或为了句式虚构用户角色。明确的业务细节和已定技术契约仍须保留；普通实现拆法留给执行阶段，代码入口可作附加定位。

## 开始前先决议本期需求边界

确认的是业务范围：本期取得什么结果、覆盖哪些能力与场景、哪些暂缓或排除，以及取舍依据。此时不固定故事或 Issue 数量、清单、编号和粒度。已有明确范围、有效决议或委托选择时直接复用并继续；已有执行和同步授权也沿用，不增加阶段或逐项批准。

只有宽泛目标且范围仍有实质取舍时，先给可评审的范围建议，收敛影响本期覆盖的选择后再详细拆分相关任务；沉默不代表采纳。直接指定边界清楚的局部需求时可立即推进，不扩大为全项目规划。仅核对进展沿用有效范围，不重新决议。

范围可以直接在当前任务或已有交付总览说明，关键取舍就近保留理由。仅当业务范围改变时复核影响；调整任务粒度不重复决议，不另建逐轮范围记录。

## 任务边界控制

按本次已明确的目标、范围和验收组织任务。父项、兄弟任务或引用中的其他目标不自动进入当前切片；现状分析发现的独立缺陷、优化和未来能力只记录影响及后续承接，按授权建单，不因发现就纳入实施。每项新增要求或技术前置须能说明对本期目的的必要性，不能用“顺便统一”扩大范围。

必要支撑不自动属于同一执行项：有用途、可检验的前置产物按下述粒度判断，不可分的支撑随本项完成；新增支撑明显增加工作量时重核边界。改变业务结果、范围、验收或重大方案时沿用有效决定，缺失时只就变化项取得决定。同步覆盖、依赖及受影响下游正文的目标和验证前提，保留迁出要求；无依赖部分继续。扩大回归不授权优化被测模块。

正文满足本次目的、验收、粒度和交接要求后收敛，不自动开展代码实现、下一阶段或额外治理。实际变更传播按[变更分析](../changes/impact.md)，不另建重复台账。

## 围绕交付切片推进

1. **按结果拆分。** 在本期边界内按可交付结果、验收和依赖选取切片，复用已有条目与 ID。简单需求可直接形成一个包含实现和验证的 Issue；不强制先写独立故事。跨角色、跨流程或跨多个 Issue 的复杂需求保留必要的故事／场景总览，解释完整业务过程、边界及 Issue 关联，不重复执行任务状态。技术前置项关联所解锁的结果或质量目标，不伪造用户角色，不规定固定数量。
2. **明确行为与验收。** 使用 [行为与验收细化](acceptance-detail.md)，补齐本次需要的规则、状态、权限、失败后果及可观察判据。长期定义归原需求／设计主题，Issue 给出本次适用条件与预期并精确引用，不复制全规范。发现新业务决定时先整合规范再更新应用它的 Issue，避免决定只留在关闭的任务里。
3. **定位必要设计。** 关联影响成功结果的交互、架构、模型及接口契约，说明用途。只补会改变需求、验收或强制约束的缺口，普通实现选择留到执行时，不为建单补完整实施设计。按问题使用 [架构验证](architecture.md)、[模型设计](modeling.md) 或 [交互与 UI 设计](interaction.md)；缺口只阻塞依赖它的工作，不以原型制作或走查为交接前提。
4. **形成执行 Issue。** 先写目标需求和完成后的结果，再说明范围、输入／契约、依赖、约束、AC 与必要验证场景；实现动作不替代任务目的。实现与对应验证按结果保持闭环，拆分按下节判断；有依赖不等于必须合并，也不单独构成拆分理由。仍需业务拆解的条目标为工作包，不能凭标题判为可执行；已有 DEV／TEST 工作包只保留组织关系与任务链接，不复制执行详情及状态。
5. **安排优先级与依赖。** 总览解释本期结果、范围、先后依赖及 Issue 索引，可按需要分批。价值优先级与技术先后分开；无依据不填负责人、不承诺日期。逐切片按下述交接标准判断就绪，不要求所有远期项同时细化。
6. **读取证据并反馈。** 按请求跟进 Issue 中的实现、测试、PR、阻塞与状态；缺陷关联原 AC。需求或设计改变时按 [变更分析](../changes/impact.md) 复核相关任务与证据。没有实际进展材料时只报告准备结果及待核实状态，不编造实现或测试通过。

已有连续推进授权时完成当前切片后继续；受阻项保留真实状态，可处理无依赖项。交付整理不自动授权开发、部署、长期监控或新增远端任务；只有拆分建议时交付可评审草稿即可。

## 粒度判断

先识别结果，再判断依赖与工作量；同一总目标可由父项承接，不等于同一执行项。对多结果或预计过大的任务，检查某部分能否先验证、其余延期后是否仍保有有效成果，不按 AC 编号切分。

- 结果可以分别成立、接受或延期时拆分；共享基础能力、各业务结果与不同主题的回归迁移分别判断，不能因都属一次退役就合为大任务。A 有可验证产物、B 依赖 A 时仍可分项，说明消费的契约／产物、版本或定位及可用判据；共享文件不自动构成阻塞。
- 主张不能拆时，说明拆开会破坏的具体契约或不可接受的中间状态，以及为何无合理可验收阶段；“耦合”“完整结果”不构成依据。同一行为的正常、拒绝、恢复、实现及验证通常一起交付；循环依赖重划边界，共享前置只建一次。
- 按实际代码、测试基础和未知复核大小，采用项目的规模约定。明显过大时寻找可验收阶段，过碎步骤并入所属结果；独立小缺陷不强行扩大。没有项目阈值时不臆造统一时限，不通过减测试或交付半成品压缩工作量。
- 关键未知足以改变范围或验收时先做有界澄清／调研；普通实现选择不阻止就绪。范围迁出须保留父项待办与旧 AC 承接，不能靠缩范围宣布完成。

## 父 Issue 与 sub-issue

父子关系用于组织交付，不是额外的任务类型。简单需求可保持单层；较大且有边界的业务目标用父 Issue 承接目标、总体包含／排除范围、子项分解、跨子项依赖及整体验收。执行 Issue 或执行型 sub-issue 承接可独立交付的行为，维护自己的范围、AC、测试、PR 与状态；调研或验证型子项则说明待解问题、结果产物及完成判据，不伪装成产品交付。

父项与执行子项使用不同内容标准，不套同一份详细清单：

| 角色 | 正文重点 | 完成判断 |
|---|---|---|
| 父项 | 整体问题与目的、总体范围、整体验收、子项覆盖、依赖及未拆分范围 | 必要子项交付且整体与跨子项验证成立 |
| 执行子项／独立执行项 | 本次目标需求、范围、结果判据、必要约束、依赖产物及验证依据 | 本项结果、验证及项目交付条件满足 |

父项不复制子项实现、完整测试清单或实时状态；执行项不把通用工作流程复制成主体。既有子项仍过大时，可保留编号和原 AC 转为汇总，再建立执行项及承接映射，不强制新增层级。远期子项可以暂不细化，但必要范围必须可追查。父子关系表示归属，依赖表示前置，两者分别记录。

复杂目标应建立可查询的父子关系，平台支持原生 sub-issue 时优先使用；跨仓来源或补充关联可用链接，平台不支持时明确记录等价关系及限制，不把普通链接称为原生子项。根据独立目标与验收价值决定是否继续拆分，不固定层数、不仅按前后端或数据库层拆分。

父目标／整体验收与子项范围／AC 维护覆盖映射，检查遗漏、重叠和跨子项依赖；父项保留整体判据及引用，不镜像每个子项的详情或状态。父项完成须有必要子项完成、整体 AC 与跨子项验证证据，全部子项关闭不能自动证明父目标完成。延期或取消子项时复核父目标、范围和验收覆盖，记录有效调整依据，不把未实现结果当成通过。只修改方法规则时不自动创建或重组项目里的真实任务。

实际委派按[子代理协作](../shared/agent-collaboration.md)判断依赖和修改边界；父子关系不直接决定代理数量，整体覆盖与交付判断由主 agent 保留。

## 交付正文与故事组织

- **长期定义与执行范围分工。** 需求／设计正文说明稳定的业务目标、场景、规则、设计决定及业务验收；复杂故事用于理解整体行为。第五阶段总览说明本期选择及依赖，执行 Issue 承载这一轮具体工作与可验证结果。独立理解以 Issue 正文和必要引用为单位，不能只有标题与整篇文档链接。
- **AC 说明本次适用判据。** 表达本次条件、动作和结果，引用必要规则；已有稳定 ID 沿用，固定版本交接才补明确修订。整体业务验收可由多个任务共同覆盖，具体执行数据与结果沿测试材料关联。
- **沿用既有关系。** 不按聊天轮次重建故事或任务；复杂故事、DEV／TEST 工作包与追溯表保留必要关系和引用，不重复维护 Issue 详情、PR 或状态。实际状态查询执行来源；需保存报告时标明它是某时点快照及证据来源。
- **区分变化与历史。** 等价整理保留原语义和 ID。行为、AC 或设计依赖改变时记录影响，保留旧执行版本与结果；新定义下未复核的项明确标记，不能改写历史证据或让已关闭任务自动证明新规则成立。

## 研发与测试交接包

交接包可以是一个 Issue 及其必要引用，不要求每项另建故事文件或单独的 DEV／TEST 条目。其深度应足以回答：

| 内容 | 下游能回答什么 |
|---|---|
| 本次目标与范围 | 为谁解决什么问题，本次包含／排除什么，与需求或复杂场景的关系是什么 |
| 行为与设计依据 | 正常、边界、权限、状态及重要异常如何处理，采用哪版规则／接口／交互规范，引用的具体章节有什么用途 |
| 实施边界与约束 | 需要交付什么能力或结果，依赖产物、输入输出及哪些已定约束不可改变；普通实现选择留给执行阶段 |
| Issue AC | 给定何种条件、执行什么、观察什么，如何映射长期业务验收，哪些边界仍不在本 Issue 内 |
| 验证依据 | 用什么方式判定成功，代表性条件、操作与预期是什么，哪些环境或依赖尚不可用 |

建单提供主路径与重要风险的代表场景和通过判据；“记录回归结果”只是证据要求。退役、迁移或替换说明消失、保持及受影响存续能力的预期结果，不能以“最小适配”代替业务决定；“保持现状”给出关键行为或可复核基线，并以有效规则裁定旧测试的预期。区分正式入口可达行为、模型／组件能力与替身数据证明范围，不把隔离测试写成真实集成，也不为测试迁移新增未授权能力。要求移除专用实现／资源时验其实际退出及存续依赖，不只验入口不可达；未完成的前置迁移由原项承接。跨主题回归按各自断言及共同场景明确责任，避免重复或遗漏。AC 不设通用数量，也不合并独立结果凑数；分支结果各有触发条件。

执行阶段据此形成方案、具体测试数据与脚本，按项目要求确认，再关联进展、PR 与证据。已有必要测试设计和共享契约可直接引用；建单不要求提前填执行安排或未发生的状态。覆盖复杂时使用 [设计输入与追溯](../shared/design-traceability.md)，不另建执行台账。

## 两类完成判断

**可交付研发和测试：** 单个执行项及必要引用足以复述目标、判断成功、形成测试场景，且粒度与依赖有依据。包含多个可分别交付结果时重新切分或作为汇总项；关键行为未定标明问题和受影响部分；规模缺乏依据补必要调查。普通实现方案未定不阻塞建单，内容详尽不等于就绪。已有授权内可解决的直接处理，只询问缺失的业务决定，不新增审批或必填表。

分别判断研发、真实集成和验收准备：凭证缺失可能只阻塞真实集成，无依赖部分可继续，但不把整个切片标为就绪。等价本地任务或独立故事可作入口；仅请求故事／AC 时按 [细化标准](acceptance-detail.md#完成与回退) 结束。

**已完成交付：** 当前实现达成原始目的与约定 AC，不能仅因按计划改完代码或测试全绿判定目标已实现；必要的集成、迁移、回归及运行条件有实际证据，遗留问题按项目约定处理；要求业务验收或上线时读取相应结果。创建或关闭 Issue、PR 合并、demo 通过、文档完成均不能单独证明交付通过。未执行的测试明确标为未执行，测试结果只覆盖实际版本、环境及范围。

交接前按以上判断回读，并核对父子覆盖与联合验收归属，不用栏目或链接替代缺口。复杂交接按需使用 [公共检查](../shared/readiness.md) 与 [独立阅读检查](../shared/document-structure.md#交付前的阅读检查)，不另建常规检查报告。

## 保存与任务落地

按项目已有约定或用户指定目标选择执行来源，已有配置可帮助定位；不限定平台或层级：

- **采用 Issue／任务系统：** 在既有或本轮授权范围按 [任务落地](../integrations/task-tracking.md) 维护本次范围、AC、约束、测试、PR 和状态；系统支持何种字段与关联就用何种表达。需求与设计正文继续维护长期定义，总览仅维护目标、范围、优先级／依赖及实际 Issue 索引，不建本地执行副本。
- **采用本地记录：** 沿用本地任务文件或章节作为轻量等价来源，可直接容纳简单需求的实施与验证；复杂度与维护责任决定是否拆文件，不强制每故事独立文档。已有充分的场景文件原位复用，不为符合新形式重建。

临时咨询可在对话交付。配置中只有系统地址不代表写入授权；未授权时准备可评审草稿，已有授权则不重复索取。平台不可用、返回不明确或部分失败时保留草稿与真实成功映射，查询后再重试缺失项，不编造 key、不切换正式来源、不宣称已落地。

迁移时先核对旧故事、AC、DEV／TEST 及远端任务的实际内容和关系，复用已有 Issue，记录旧 ID → 新 Issue／规范章节的映射；拆分、合并或不再适用的旧项说明承接关系，不静默丢弃历史语义。将长期规则与场景归入原需求／设计主题，执行详情归入唯一任务来源，旧文档保留必要上下文、映射或历史入口，停止双份更新状态。旧测试结果、PR 和执行版本保留原关联，不自动算作新 AC 通过。没有等价映射依据的项标为待核实。
