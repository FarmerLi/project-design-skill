# 需求概要与范围

本文件是第一阶段“需求探索与澄清”的范围收敛方法，也可独立形成概要。价值判断和概要属于第一阶段内部工作，不恢复为额外主阶段。

## 方法目标与输入

将目标、关键场景和有效判断转为可评审的业务方案，回答围绕哪些核心结果、由哪些能力协作、纳入哪些范围，以及下一步细化什么。本方法支持业务方案与范围取舍，不以功能清单代替闭环，不承诺交付日期，也不要求完成详细故事或技术设计。

最低输入为目标、关键场景、有效约束及已有判断；可来自对话、文档和相关现状，不要求前序阶段文件齐全。读取 [交接契约](../shared/working-contract.md)，按需补足相关依据；已有概要时只补差距。缺口不阻止开始分析，但依赖缺口的结论保持条件性，不能因独立运行而将未验证的成立前提视为已满足。

完整项目确定首期范围；既有项目新增能力或局部分析确定本轮范围及其与现有能力的衔接，不重做全项目规划。下文的范围、闭环和交接判断均限于本轮分析对象。

## 工作方法

先形成有依据的草稿，再按以下依赖补足并收敛；已有答案直接复用，不将步骤变成固定访谈轮次。

1. **明确分析对象。** 说明本轮要形成什么方案与范围决定，复用目标用户、核心任务、可观察成功信号及有效约束，区分已定决定与候选。既有项目只补与本轮有关的现状和预期变化。
2. **推演核心场景。** 从触发、主要角色和输入走到可观察结果，说明关键协作及业务终点。检查可能改变核心结果、范围、责任或依赖判断的异常与边界；多个独立影响分别覆盖，没有实质影响时说明依据，不以数量凑检查项。
3. **归纳能力与责任。** 从场景归纳所需能力、主要责任、外部系统边界和依赖，关联目标与场景，不先从菜单或数据库表反推需求。依赖既有系统或人工流程时，说明由谁或哪个角色承接什么结果，以及承接依据或缺口，不虚构负责人或可用能力。
4. **裁剪范围并复核闭环。** 根据目标贡献、闭环必要性、有效约束和依赖，说明必须纳入、可以延后和明确不做的内容及理由，区分建议与已定范围。重新推演裁剪后的核心场景：移出某项能力后，结果由何处承接；没有承接依据时，修订范围或标明阻塞，不隐含假设人工兜底。
5. **检查质量约束与未知。** 识别可能改变方案或范围的性能、规模、可靠性、安全、使用环境等要求，记录相关场景、目标或约束及来源，有依据才填数值。说明未知的影响、解决方式、最迟解决节点与阻塞范围；影响闭环或范围的发现返回前述步骤修订，局部细节留待细化。
6. **确定细化对象。** 列出下一步细化的场景、预期结果、相关范围与约束，并根据用户结果、风险和依赖说明优先理由。按下方完成标准分别判断概要完成情况、可细化范围和验证状态。

## 分析约束

- **按概要深度分析。** 明确会改变闭环、范围与责任的规则和边界，不要求全部字段、详细权限矩阵、所有异常恢复规则或验收案例。模块是初步责任划分，允许细化后调整；远期能力保留高层描述即可。
- **保留有效约束。** 不为缩小范围而静默放宽目标、硬约束或删除必要协作。新证据推翻价值假设或已有判断时，指出依据、影响和需回交的部分，不擅自重做其他阶段；无依赖部分可以继续。
- **按实际对象选择表达。** 业务对象只是可用视角之一；数据处理、工具、SDK 等项目优先识别数据来源、调用方、输入输出和契约。原型、流程图、状态图仅在能消除歧义且符合实际授权时使用，不强制生成。

完整项目概要使用 [通用分析规格](../shared/analysis-spec.md) 的维度表记录已覆盖、需细化和不适用项；局部分析只说明相关覆盖与缺口，不将未知写成不适用。复杂协作先给全景及责任边界，必要时进入 [协作与影响链](collaboration.md)，不预选同步或异步实现。

## 产品结论与技术结论分开

产品概要描述需要达到的业务效果。技术概要描述如何承载这些需求，标明需求依据和设计选择。

如果当前任务需要技术概要，进入 [技术架构探索与验证](architecture.md)；领域与数据结构问题进入 [模型设计](modeling.md)。按当前用途选择相关适配器，不默认轻量方法、本体方法或某技术栈。

适配器发现需求与能力冲突时，保留原需求，返回取舍问题。不要为迎合现有框架删掉外部接口、异步任务或其他业务需求。

## 最小产物

交付以下内容，可合并为章节或简述，不以文件数量衡量完成：

1. 本轮对象、目标关联、有效约束及来源，既有项目的相关现状与预期变化；
2. 核心场景索引与业务全景，覆盖触发、主要参与者、关键步骤、结果及影响方案判断的边界；
3. 能力责任、外部边界与关键依赖，包含既有系统或人工承接的依据与缺口；
4. 本轮／首期范围及取舍理由，裁剪后的闭环推演结论；
5. 影响方案的质量要求、重要未知及其解决节点、方式和阻塞范围；
6. 建议细化的场景及优先理由、概要完成情况、可交接范围与验证状态。

需要保存时遵循项目配置，本地默认写入 `01-discovery.md` 的需求概要章节；已有 `03-outline.md` 可以沿用，技术设计另放 `design/` 并引用；临时咨询可在回复中分别说明，不混进业务事实。

## 完成标准与交接

按本轮范围检查以下六项并给出依据，不以功能数量、图表齐全或远期设计完成衡量充分性。

| 检查项 | 本项分析达到什么程度即可 |
|---|---|
| 目标关联 | 核心场景及纳入范围的能力能说明服务于哪个用户任务或目标，候选未混入已定范围 |
| 核心闭环 | 触发、主要参与者、关键步骤和可观察结果明确；在已说明的前提下推演无未解释的关键断点，影响方案的异常与边界已有处理方向或明确阻塞 |
| 范围取舍 | 纳入、延后和不做的边界及理由明确；裁剪未隐含破坏核心结果，必要承接有依据或明确缺口 |
| 能力与依赖 | 主要责任及交接关系明确；关键依赖的成立依据或缺口可定位，未知承接责任未被当作已有安排 |
| 约束与未知 | 会改变方案或范围的约束已检查；未知说明影响、解决方式、节点与阻塞范围，不把待验证前提写成已成立 |
| 细化交接 | 下一步细化的场景、预期结果、相关范围与约束可定位，优先理由明确，可推进与受阻部分可区分 |

与公共 [就绪检查](../shared/readiness.md) 配合使用，分别报告：

- **概要分析是否完成：** 六项得到有依据的回答，足以支持本轮方案与范围取舍时，可以完成本轮概要分析；有依据的闭环缺口和调整建议也是分析结果。若关键缺口使方案或范围结论仍无法形成，交付条件性草稿并标明未完成部分，不能仅列出未知就宣称完成。
- **哪些范围可进入细化：** 仅将核心结果、范围和责任边界明确，且不存在会推翻这些结论的未决前提、约束冲突或未解决的闭环断点的场景标为可细化。其余场景保持条件性；待细化的局部规则、字段和验收细节不自动构成概要阻塞，须说明为何可留待细化及解决节点。
- **检查与验证状态：** 说明实际做过文档核对、哪些场景推演或运行验证，以及证据适用范围。“场景走通”仅表示在明确前提下逻辑闭合，不代表真实系统已实现、外部依赖已验证或业务已确认。

独立运行时交付本轮结果即可结束；本轮结束不等于概要完成，概要完成不等于全部范围可细化。仅请求概要时到此结束，已授权连续分析时仅继续可推进部分。需要持续维护或交接时按配置更新概览、相关决策和交接。
