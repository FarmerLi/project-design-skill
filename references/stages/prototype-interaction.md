# 原型与交互设计

## 阶段目标与输入

依据当前需求、领域与数据模型及技术架构，先建立任务与信息结构，用低保真原型验证核心交互，再建立或复用公共 UI 基线，按场景细化并实际走查。交互规范与设计规范从基线开始维护，随原型验证逐步收敛，使研发能够落实页面、命令或会话行为，后续故事能够引用具体流程、状态、反馈和视觉／组件规则进行验收。

完整第四阶段的默认产物不是单纯页面说明或视觉稿，而是当前范围的可操作或可模拟执行原型、实际走查结果和交互／设计规范：关键用户结果都能在原型中走通，需求缺口、多余步骤、断路、权限或异常状态问题已有明确处理，交互动作、页面或终端状态、反馈与恢复规则清楚，视觉层级、布局、组件和内容规则足以指导实现和评审。原型可运行、画面精细或文件数量多都不等于验证完成；未走查、未核对需求或核心流程仍有关键断路时只能是草稿。

最低输入为当前范围的用户结果或任务、相关场景与规则，以及支撑当前决定的概念模型、数据状态和技术约束。已有界面、原型、设计规范、组件库和真实使用证据按需复用。先从 [项目上下文](../shared/project-context.md) 定位原型设计工具和正式原型源，沿相关设计文档确认预览方式、设计规范来源和可维护范围；再读取 [工作契约](../shared/working-contract.md)、[设计输入与追溯](../shared/design-input.md) 和 [通用分析规格](../shared/analysis-spec.md) 的相关维度。不要求前三阶段全部定稿，缺口保留条件并只阻塞相关原型与流程。

原型工具可由项目上下文指定。用户或项目配置了 Figma、即时设计、Axure、Miro、HTML 原型或其他工具时，沿用实际位置、文件／页面 ID、组件库和操作授权，不擅自换成不兼容的另一套正式来源。指定的工具或权限不可用时，说明无法完成的部分及影响；可以制作条件性替代稿，但不能冒充指定工具中的原型、已发布原型或团队已评审版本。

本轮仅要求梳理一个流程、评审现有页面或调整局部反馈时，按指定范围完成必要原型和走查，不补做整个产品的信息架构和全部页面。无图形界面的工具、SDK、命令行或后台系统也应识别实际交互面，可以使用命令行结果、状态模拟页、事件时序或会话原型验证任务能否完成；API 契约本身仍归架构，不能为了满足“界面”形式虚构图形产品。

## 工作方法

1. **界定范围、工具与设计依据。** 明确服务的用户或调用方、使用情境、终端或入口、本轮目标及范围外内容，从项目上下文读取原型工具和正式源，从相关设计文档读取交互规范、设计系统、组件库和预览方式，识别可复用部分与本轮缺口。确认可操作范围、缺失权限及替代限制，区分现状、目标与候选；已有问题只是视觉修正时不扩张为业务流程重构。
2. **建立任务与信息结构。** 从用户目标出发组织入口、信息层级、导航、对象与操作关系，说明用户如何找到对象、理解当前上下文、完成主要任务并返回或继续。用任务流程与必要的页面／终端关系说明整体，复杂任务按阶段和信息依赖组织，不从组件清单或数据库结构拼页面，不以页面数量代替结构。达到能讲清完整任务路径的深度后进入交互设计。
3. **设计交互基线并验证核心流程。** 明确页面、容器或命令的职责，建立或复用导航返回、输入与提交、等待反馈、错误恢复和来源同步等公共交互模式。用线框或低保真可操作／可模拟执行原型走查核心任务，验证入口、步骤、可观察结果及影响任务成立的权限、异常、取消和恢复分支；会改变流程的行为在此处理，不推迟为页面细节。将已成立的公共模式维护为交互基线，未验证的候选保留状态；核心断路未处理时不批量展开依赖它的精细页面。
4. **建立 UI 基线并验证代表页面。** 图形界面优先复用已有设计系统，补充本轮缺少的布局、视觉层级、字体与颜色语义、间距与密度、组件及状态样式、内容表达，以及适用的响应式和可访问性规则。选能代表当前布局、信息密度和关键状态的页面验证组合效果，使公共规则足以支持后续细化；不要求先建完整产品设计系统。基线注明来源、复用与扩展边界，不把个人偏好冒充品牌规范。无图形界面时按实际交互面落实输出层级、状态和内容表达，不虚构视觉组件或另建 UI 系统。
5. **按场景细化并逐项验证。** 在公共基线下，选择一个任务或一组紧密关联的场景，补齐页面／终端、区域、字段、校验、状态、文案、微交互、焦点和适用的终端适配，再实际操作对应原型。核心任务须能从入口走到结果，覆盖代表性空结果、加载、权限拒绝、失败、重复、中断与恢复；可逆操作同时覆盖正向、反向及重要失败路径。每项修订并复测后再展开下一项，无依赖场景可继续；共性问题回写公共基线，页面只维护自身应用和有依据的例外。原型数据、账号和外部调用使用经授权的样例或替身，并标明不能证明的真实条件。
6. **收敛规范并完成交接。** 核对当前范围需求覆盖、跨页面承接，以及原型、交互规范、设计规范和组件库的一致性，记录实际走查步骤、预期、观察、结论、发现及修订复测。按问题归属返回需求、模型、架构或本阶段更新；已确定的变化同步相关原型与规范，候选不覆盖有效定义。阻塞当前核心流程或验收的问题必须修订、明确回退到对应阶段，或经用户明确缩小范围，不能只登记后宣称完成；不阻塞流程与交接的待办说明保留原因。当前影响实现或验收的规则在本阶段收敛，第五阶段引用设计形成故事、AC 与任务，不把关键体验决定留给下游。必要时邀请目标用户或业务方评审，并区分原型走查、业务评审、真实用户测试和应用实现。

以上按依赖推进，不要求先完成全产品交互规范、再完成全产品 UI 规范，最后才做页面。完整范围通常先选一条代表性任务贯穿交互、UI 和细节，验证公共基线后再展开其他场景；已有有效原型或基线时直接复用，局部调整从受影响处进入，不强制重做低保真版本，也不为每步追加用户确认。静态稿可用于局部阅读或专家评审，但不能替代核心任务的可操作／可模拟执行原型和实际走查。

## 规范分工与细化边界

设计规范包含图形界面适用的 UI 规范及其他交互面的表达规则。按以下职责维护，避免同一规则在公共规范和页面说明中重复定义：

| 层次 | 负责的决定 | 与场景细化的关系 |
|---|---|---|
| 交互规范 | 用户怎样操作、系统怎样反馈及任务怎样衔接；维护公共模式及其适用条件 | 场景引用模式并说明具体行为；新增共性模式经验证后回写，不以单个控件定义业务规则 |
| UI 规范 | 信息与状态怎样呈现；维护公共布局、视觉、组件和表达规则 | 代表页面验证规则组合，具体页面按规则应用；已有设计系统为共同依据，具体值只在权威源维护 |
| 场景细化 | 当前任务具体有哪些页面、信息、操作和状态，以及如何使用公共模式 | 维护本场景的字段、文案、校验呈现、焦点与例外，关联原型和规则；关键权限、异常、取消与恢复在交互设计时即处理，不等最后补漏 |

## 原型验证与设计规范

按当前范围落实下列内容；简单流程可合并为一段或一张表，不要求每一项单独成文。每项原型和规范决定应能关联用户结果、业务规则、模型状态、技术约束或既有设计规范，并说明对实现和验收的影响。

| 设计内容 | 方案与下游所需说明 |
|---|---|
| 原型与走查范围 | 正式原型位置、工具、文件／页面 ID、预览方式、可操作范围、样例数据和不可验证条件 |
| 用户任务与入口 | 谁在何种情境进入，使用哪个页面、命令、消息或调用入口；前置条件和用户看到的起点是什么 |
| 信息与操作结构 | 主要信息层级、导航或检索方式、对象与操作的关系及跨步骤承接；说明用户如何理解范围和当前上下文 |
| 主流程与分支 | 从触发到可观察结果的步骤、责任主体、条件分支、来源与返回路径、跨入口后的状态同步和任务终点 |
| 页面、容器与命令 | 关键页面、区域、弹层、步骤、命令或消息承担的职责及相互关系；不把组件清单冒充流程 |
| 关键状态 | 初始、空、加载、草稿、等待、成功、拒绝、失败、过期、部分完成等适用状态；状态来源及可执行操作 |
| 操作与反馈 | 输入、校验、提交、更新、取消和重复操作的用户可见结果，成功／失败提示及副作用边界 |
| 权限与可见性 | 无权限、不可见、不可操作时用户看到什么、能做什么；区别隐藏、禁用、拒绝及权限变化后的恢复 |
| 体验与质量约束 | 本轮适用的可用性、可访问性、响应式、国际化和终端限制；可测要求须有测量方式或明确待验证 |
| 规范与场景应用 | 公共交互与 UI 基线的来源、适用条件和有效定义；代表页面与具体场景如何使用，哪些扩展或例外需要回写，避免并行维护具体值 |
| 验证结果 | 已走查场景、通过／未通过结论、需求或流程缺口、修订及复测状态；区分专家走查、用户测试和实现验收 |

同一业务操作可以有多种入口和表现，但语义与结果应一致。表单字段、按钮、筛选器和提示文案不能单独定义业务规则；新增动作、状态或失败后果若尚无需求依据，返回需求澄清或后续故事细化，不靠界面默认值定案。

## 原型构建与走查

完整原型范围至少有一条可从入口走到终止或明确等待状态的核心流程，并有与原型对应的任务流程和关键状态说明。原型应覆盖需求中会改变用户判断或任务完成的页面、命令和分支；单页局部修改、纯文案整理或证据核对按需要缩小，不补全全站，也不为凑齐画面虚构功能。采用事件时序或图表原型模拟时，需给定具体场景输入、依动作和条件实际推进状态并记录观察结果；仅阅读预设图示不构成模拟执行。

- **工具来源一致。** 项目上下文指定工具时，在原工具中维护正式原型及可编辑源；只有截图或导出预览不构成可维护原型。没有指定工具时，可复用现有工具，或用本地可运行的 HTML／图表原型；不安装额外软件或访问外部服务，除非本轮确有相应授权。
- **先整体再局部。** 先说明用户目标、入口、主要步骤和跨页面关系，再展开页面区域、字段、控件和微交互。复杂流程按可独立理解的任务阶段拆图或拆原型，父层保留概貌和入口。
- **图文与原型同源。** 图中页面、步骤、状态和操作与正文、原型使用相同名称；条件分支、失败、返回和系统等待可辨识。视觉稿变化但业务含义未变时同步画面与图，不重写已成立的业务规则。
- **数据与边界透明。** 硬编码样例、测试账号、替身接口、临时跳转和省略的后端步骤必须在原型说明或验证记录中标明。原型可运行不等于产品实现、真实业务链路或生产条件已通过。
- **实际走查。** 按代表性场景实际操作原型，记录起点、操作、预期、观察、发现和修订。不能实际点击的静态稿只能进行阅读或专家走查，不能宣称流程已跑通；有条件时在实际展示尺寸检查布局、可读性和交互反馈。

流程与状态图通常使用 Mermaid，复杂多区页面关系或无法清楚自动布局的图可使用 SVG；选择依据和可读性检查遵循 [图示格式选择](../shared/document-structure.md#mermaid-与-svg-的选择)。原型工具内已有有效的流程、页面和组件说明时直接维护，不在本地复制第二套正式设计。

## 正文与专题组织

正文先说明用户目标、原型工具与覆盖范围、入口与整体任务路径，再说明公共交互与 UI 基线及其来源，然后按场景展开页面／终端的信息结构、关键状态、操作反馈、权限与环境约束，关联具体规范，最后给出走查结论与缺口。页面细节复杂且具有独立维护责任时可建原型或交互专题，专题先说明它在整体流程中的位置，再展开布局、状态和组件规则，不从一个控件清单开始。组织顺序服务阅读，基线随验证更新，不按制作轮次另存多套正式规范。

共享导航、容器模式、状态表达、反馈规则和设计规范只在权威位置维护；具体页面引用并说明自己如何使用。模型状态、业务规则、技术接口和交互表现各自保留责任：模型定义对象可以处于哪些状态，架构定义状态如何保存与恢复，原型与交互设计定义用户如何看到、操作和验证这些状态。若原型需要新的状态、动作、错误类别或权限分支，先形成具体需求缺口，不把它直接写入界面规范。

按项目上下文的入口与组织约定保存原型与交互设计主文及规范专题，不预设阶段文件名或专题子目录。项目上下文指定的原型工具和文件／页面是该原型的正式源；导出预览、截图和走查记录放附件或验证区。没有指定工具且采用本地原型时，保存可编辑源及运行说明。旧项目的第 4 阶段交付文件按内容识别，不因技能升级自动改名。

## 完成标准与交接

- 当前范围的主要用户结果已有可操作或可模拟执行的原型；核心任务能从明确入口走到可观察完成，主路径、关键分支、返回与任务终点完整，没有依赖未说明的人工承接。静态稿和“拟实现”说明不能替代核心流程原型。
- 原型已按代表性需求场景实际走查，记录起点、操作、预期、观察和结论；阻塞核心流程或验收的断路、多余步骤、需求歧义、权限或异常状态缺口已修复、回退到对应阶段或经明确缩小范围，不能只登记后宣称完成。非核心待办可以保留并说明不阻塞原因。
- 关键页面、命令或消息的信息与操作职责清楚，空、加载、成功、拒绝、失败、重复、中断和恢复等适用状态有用户可见结果与后续动作。
- 涉及从列表、搜索或上下文进入详情／子任务时，返回来源后的过滤、移除、刷新和空状态可预期；新开页面、页面缓存或跨入口操作不会让来源列表继续显示已失效结果。
- 权限、可见性和操作许可与需求一致，界面可见不冒充有权操作，拒绝、不可见和错误的原因及可恢复路径可验收。
- 交互中的输入、动作和反馈能追溯到需求、规则、模型状态或必要技术约束；没有通过原型默认值引入新的业务能力、审批或失败后果。
- 交互规范明确控件或命令语义、状态、反馈、恢复、返回与来源同步；设计规范明确信息布局、视觉层级、组件及状态、内容规则、响应式和可访问性中本轮适用的部分。影响实现或验收的规则已收敛，未定项明确不影响本轮交接。
- 公共交互与 UI 基线已在代表性任务／页面中验证，当前场景有明确应用与必要例外，共性修订已回写权威规范；已有设计系统及非图形交互按适用范围复用或说明，无须补建完整产品设计系统。只有公共规范而没有场景落点，或页面齐全却各自定义冲突规则，均不能判定设计就绪。
- 涉及布局、可访问性、响应式、国际化、离线或性能反馈的要求在当前范围有依据；定量目标说明测量方法，未验证的体验假设明确保留。
- 图示、正文、原型和设计规范使用同一术语与状态；原型正式源、可编辑版本和预览入口可定位，实际渲染、点击走查、业务评审、用户测试和实现状态分别记录。
- 原型、交互规范、设计规范及既有组件库中的控件名称、状态文案、关键尺寸、令牌和适用条件一致；存在多处摘要时以已声明的权威源为准，具体值没有互相冲突。
- 涉及图形界面键盘交互时，状态提交、对象移除、返回来源、进入 404 或登录失效等适用场景的焦点去向明确；键盘操作不仅触发成功，也要检查刷新后的焦点是否到达可预期、可操作或可程序化聚焦的目标。
- 架构能承载必要的页面数据、状态恢复、权限反馈和交互时效；发现接口、持久化或运行机制缺口时返回 [技术架构探索与验证](architecture.md)，不隐藏在设计稿中。

完整原型与交互设计阶段交接时，读者应能打开或查看指定原型，按场景理解本轮用户如何操作并判断流程能否跑通，说明关键状态、反馈、异常恢复和设计规范，以及还剩哪些需求或实现决定；仅凭页面列表、组件名或静态视觉稿无法判断。按 [就绪检查](../shared/readiness.md) 分开报告原型完成、流程走查、业务／用户验证、设计规范就绪和实现状态。交付给 [需求细化与交付推进](delivery.md) 时引用原型、流程、页面／命令、状态、反馈和设计规范的有效版本；故事和 AC 继续定义具体行为与验收，不复制整套规范。

需要保存的原型说明与规范正文交付前，按 [独立阅读评审](../shared/document-structure.md#交付前的阅读检查) 由不继承主会话历史、未参与编写的子 Agent 读取当前正文、原型入口及必要引用，检查用户任务、关键状态、异常恢复、需求到原型的可追溯性、图文与原型一致和仍存缺口。局部流程按本轮范围评审；独立阅读不替代实际原型走查或用户测试。
